DocMind · Phase 7 · agents and tool calling · built 2026-10-22 → 11-04

Decide what to do before doing it

Before Phase 7, every chat message went down one fixed path: embed it, grab the top 3 chunks, paste everything into one prompt, call Gemini once. Phase 7 puts two deciders in front of the answer. A router labels the message, and for document questions an agent lets the model choose what to search, while code keeps control of who, what and how many times.

03

The words

vocabulary

Five terms do all the work in this phase. Each one has a concrete home in the code.

Router

Puts the message in one of a few boxes, then code runs a fixed path for that box. The model only labels; it never acts.

router.service.ts → routeMessage()

Tool calling

The request declares functions (name, description, parameters). The model may reply with a functionCall part instead of text. Our code runs it and sends back a functionResponse. The model never executes anything.

tools/ + llm.service.ts

Agent

Tool calling in a loop: ask, run what it asked for, send results, ask again, until it answers with text. Code decides when to stop (AGENT_MAX_STEPS = 3).

agent.service.ts → streamAgent()

Kind A tool

Read-only, cheap, safe to repeat. The model may call it whenever it likes. Both DocMind tools are Kind A.

searchDocuments, listDocuments

Kind B action

Has a side effect or spends real quota. Never declared as a tool. It can only be proposed; a human confirms; code runs it. The test: "if the model called this at the wrong moment, could I undo it for free?"

the quiz → offer + button

Pipeline

For contrast: code decides every step in a fixed order. Upload, the ingest job, auth and the quiz are still pipelines. Only the document-question path became an agent.

everything else

    05

    The router

    AG.1 build + eval · AG.2 live

    Two deciders, used together. The vector router compares the message's embedding (already computed for search, so free) with 28 example phrases. The LLM classifier asks Flash-Lite for one JSON word. vectorMayDecide() says when the vectors are trusted alone. Pick a real message from the logs; flip the switch to see the fallback.

    Margin = winner's score − runner-up's score. Scale 0 to 0.40. Only the smalltalk branch looks at it.

    The code that decides

    src/services/router.service.ts

    export function vectorMayDecide(route: VectorRoute, minMargin: number = ROUTER_MIN_MARGIN): boolean {
  if (route.intent === 'quiz_request') return false        // always a second opinion
  if (route.intent === 'document_question') return true    // any margin: the safe default anyway
  return route.margin >= minMargin                         // smalltalk only when clearly ahead
}

    The errors aren't thrown, they're returned: prepareChat prints each one with console.error('[router] …'). A routing problem must never break a chat, but it mustn't be silent either.

    How the vector half works

    Example phrases, not descriptions

    Each intent gets several short, different phrasings (10 smalltalk, 10 document, 8 quiz). An intent's score is its single best-matching phrase (nearest neighbour), not the average: "hi" and "what can you do?" are both smalltalk but nothing alike, and averaging them would blur both.

    The phrases are kept different from the eval messages, otherwise the eval would only measure memory.

    Embedded once, lazily, as one promise

    getExampleVectors() embeds all 28 phrases in one batchEmbedContents call on the first message, not at boot (Render restarts on every wake; a boot shouldn't spend quota). It caches the promise, so two messages on a cold process share one in-flight call. On failure the cache is cleared and the next message retries.

    Cosine similarity, in plain JS

    dot / (|a| × |b|) over 3072 numbers, ~28 times per message: microseconds, no DB. pgvector's <=> is the opposite number (distance = 1 − similarity).

    Why the margin, not the top score

    Similarities of short texts sit in a narrow band (real questions score ~0.5 against every phrase), so "is the best score above 0.8?" is fragile. "Is the winner clearly ahead of the runner-up?" says more about how sure it is.

    prepareChat now

    src/services/chat.service.ts

    Both routes call prepareChat({ …, mode: 'agent' }). Steps 1–4 are shared; after the router, each intent leaves through its own exit. Pick an intent to light its path.

    Failures stay before any Gemini call

    400 for a bad documentId or missing message, 404/409 from checkDocumentReady (not yours / still processing / failed), and on the agent path "All documents with nothing ready" → 404. All plain JSON, before the stream opens.

    Three result kinds, one type

    ChatPreparation is a union: kind: 'prompt' (a finished prompt string; today only smalltalk), kind: 'agent' (the agent's input), kind: 'offer' (text + action). TypeScript overloads make sure a caller that didn't ask for mode: 'agent' never has to handle the agent kind. The route switches on prep.kind.

    Where did buildChatPrompt go? It's still there, after all three exits, reachable only with mode: 'prompt'. No route passes that. It's kept as the baseline the agent was measured against (8/9 vs 9/9). Its rules moved into buildSystemInstruction(), its pasted history became real turns, and its fixed top-3 context became the searchDocuments tool.

    07

    The smalltalk path

    AG.2

    The cheapest path: no search, no tools, no chunks, and no 404 for a user with no documents ("hi" from a brand-new guest used to fail).

    What runs

    Save the user message → buildSmalltalkPrompt(history, message) → kind: 'prompt' with sources: [] → the route calls streamAnswer (or generateAnswer on /chat) once → save the reply. SSE: meta → text… → done, never a status.

    What the prompt guards against

    It lists what DocMind really does (answer from PDFs with passages, one or all documents; 5-question quizzes), so "what can you do?" isn't invented. A general-knowledge question that slipped in here ("capital of France?") gets "I only answer from your documents". A typed "yes" to a quiz offer gets "click the Create quiz button".

    Live, AG.6: "hi there!" with zero documents → smalltalk by vector (margin 0.100), streamed in 3.4 s.

          src/services/agent.service.ts

          The heart of the phase, slightly abridged (log lines removed). The circled numbers are explained below.

          export async function* streamAgent(input: AgentInput): AsyncGenerator<AgentEvent, AgentResult> {
  const searchAll = input.documentId === undefined
  const systemInstruction = buildSystemInstruction({ searchAll, filename: input.filename })   ①
  const contents = historyToContents(input.history, input.message)                          ②

  let embedCalls = 0
  const ctx: ToolContext = {                                                               ③
    userId: input.userId,
    documentId: input.documentId,
    sources: [],
    embed: async (text) => {
      if (text.trim() === input.message.trim()) return input.messageEmbedding           ④
      embedCalls++
      return getEmbedding(text)
    },
  }
  const tools = input.tools ?? makeToolSet(ctx)
  let streamed = ''                                                                          ⑤

  for (let stepNo = 1; stepNo <= AGENT_MAX_STEPS; stepNo++) {
    const lastStep = stepNo === AGENT_MAX_STEPS
    const { turn, usage, finishReason } = yield* streamTurn({                                  ⑥
      systemInstruction,
      contents,
      tools: lastStep ? undefined : tools.declarations,                                       ⑦
    })
    contents.push(turn)                                                                       ⑧

    const calls = turn.parts.filter((p) => p.functionCall).map((p) => p.functionCall!)
    const text = textOfTurn(turn).trim()
    streamed += textOfTurn(turn)

    if (calls.length === 0) {                                                                 ⑨
      const gaveUp = text.length === 0
      if (gaveUp) yield* giveUp()
      return { answer: streamed.trim(), sources: ctx.sources, steps: stepNo, toolCalls, totalTokens, gaveUp, embedCalls }
    }
    if (lastStep) break                                                                     ⑩

    const responses: Part[] = []
    for (const call of calls) {                                                               ⑪
      toolCalls.push({ step: stepNo, name: call.name, args: call.args ?? {} })
      yield { type: 'status', text: tools.statusText(call.name, call.args ?? {}) }
      const result = await tools.run(call.name, call.args ?? {})
      responses.push({ functionResponse: { id: call.id, name: call.name, response: result } })   ⑫
      if (call.name === 'searchDocuments') yield { type: 'sources', sources: [...ctx.sources] }
    }
    contents.push({ role: 'user', parts: responses })                                         ⑬
  }

  yield* giveUp()                                                                             ⑭
  return { answer: streamed.trim(), sources: ctx.sources, steps: AGENT_MAX_STEPS, toolCalls, totalTokens, gaveUp: true, embedCalls }
}

          One loop for both routes

          // POST /chat (JSON) runs the SAME generator and throws the events away
export async function runAgent(input: AgentInput): Promise<AgentResult> {
  const run = streamAgent(input)
  let next = await run.next()
  while (!next.done) next = await run.next()
  return next.value                 // the AgentResult: only reachable via .next()
}

          Why .next() by hand: a for await loop only sees the yields and silently drops a generator's return value, which is exactly where the result lives. /chat-stream uses the same hand-written loop, sending each event as an SSE frame.

          The full system instruction (buildSystemInstruction, one-document version) 
          You are DocMind, an assistant that answers questions about the user's uploaded PDF documents.
This conversation is about one document, "velmora_guide.pdf"; searchDocuments only searches that document.

Rules:
- For ANY question about the documents' content, call searchDocuments first and answer ONLY from what it returns.
- Never answer from your own general knowledge, even when you know the answer. That includes general questions
  unrelated to the documents (geography, trivia, coding…): search, and if the documents don't cover it, say so.
- Write each search query as a standalone question: resolve "it", "that", "the second one" etc. from the conversation first.

- If the results don't contain the answer, say so plainly and briefly. Don't guess.

              Why merge same-role turns?

              If saving an assistant reply fails in /chat-stream (tolerated: the user already saw the answer), two user rows end up in a row. Turns should alternate, so they're joined with a blank line.

              What is NOT stored

              Tool calls and tool results are not saved. The next turn sees the previous answer, not the chunks behind it. That's why a follow-up has to search again, with a query the model rewrites from the history.

              11

              The two tools

              src/tools/

              A tool is three things: a declaration (what the model reads), a statusText (what the user sees while it runs) and a run (what code does). Scope never comes from the model.

              searchDocuments({ query })

              Model writes: a standalone query, 1–500 chars (Zod, trimmed).

              Code does: ctx.embed(query) → searchSimilar(embedding, SEARCH_TOP_K = 3, ctx.userId, ctx.documentId), which only returns this user's ready documents. New chunks are added to ctx.sources, deduped by document + content.

              Model gets back: { results: [{ filename, content }] }, or { results: [], note: 'Nothing relevant was found in the documents.' }. Not the distance: a number it would only be tempted to over-read.

              Status: Searching for "<the model's query>"… (cut at 60 chars), so the user watches the follow-up rewrite happen.

              listDocuments()

              Model writes: nothing (no parameters at all).

              Code does: listDocuments(ctx.userId): every status, so a file still processing is listed (the model can say it isn't searchable yet).

              Model gets back: { documents: [{ filename, status, chunkCount, uploadedAt }] }.

              Status: Checking your documents…. No sources event follows.

              Why it exists: chunk search can't answer "which files do I have?" (the Step 3.3 tradeoff). Allowed in one-document chats too: it only ever shows the caller's list.

              Scope is closed over by code

              src/tools/types.ts

              export type ToolContext = {

              Streaming the loop

              AG.4 · llm.service.ts

              Every model call is a streaming call. streamTurn() yields answer text the moment it arrives, quietly collects everything else, and when the stream ends it returns the whole turn, rebuilt so it's identical to what a non-streamed call would have returned.

              Rebuilding the turn from stream pieces

              Gemini's stream delivers a turn in pieces. Sent back as 40 one-word text parts, the turn would still work, but a signature separated from its part would get a 400. So addPart() follows the rule AG.0 worked out. Pick a turn and press Play.

              SSE events from Gemini

                turn.parts (pushed into contents)

                  function addPart(parts: Part[], part: Part) {
  if (isPlainText(part)) {              // only text: no call, no signature, not a thought
    if (!part.text) return                // empty plain text carries nothing → dropped
    const last = parts[parts.length - 1]
    if (last && isPlainText(last)) last.text += part.text   // neighbours joined
    else parts.push({ text: part.text })
    return
  }
  parts.push(part)                        // a call or a signature: kept EXACTLY as sent
}

                  readSseJson: one parser, used twice

                  The byte → event → JSON loop that used to live inside streamAnswer moved into readSseJson() so streamTurn could share it. Three details carried over: \r\n is normalised to \n on the whole buffer (Gemini ends lines with \r\n, and a pair can be split across two reads), events are split on the blank line, and the trailing partial event stays in the buffer for the next read. AG.4's fake-Gemini tests cut the bytes mid-\r\n, mid-UTF-8 and mid-JSON: 26/26.

  case 'action':  handlers.onAction(data)           // AG.5
  case 'done':    finish('done')
  case 'error':   finish({ error: data.error || 'Streaming failed' })
  // no default: an event this version doesn't know is skipped. That's what made every new event safe to add.
}

                  Why not a createQuiz tool?

                  A quiz is something the app does (it spends a generate call), not something the model needs to read. Router labels, code proposes, a human confirms, code acts. The model never gets to start it.

                  Why a template, not the LLM?

                  Same sentence every time, instant, free, and it can't be talked into promising something the app can't do. Every offer logs "0 model calls".

                  Why a button, not a typed "yes"?

                  "yes" arrives as a new request, so the server would have to remember the pending offer between requests (a row per session, a timeout, "yes" to what?). That's suspend/resume: Phase 8. The button already carries the documentId, so it needs no memory.

                  Known gaps (by design): the offer is saved as plain text, so after a reload it shows without a button. Every offer waits on the classifier first, because a vector quiz_request always gets a second opinion, even "let's do a quick quiz" at score 1.000 (ISSUES #24).

                  What bit

                  real problems, not hypothetical

                  The missing signature (AG.0)

                  Resending a call turn without its thoughtSignature → 400 "Function call is missing a thought_signature". Hence: never rebuild a model turn from its text.

                  NONE didn't mean none (AG.0)

                  mode: 'NONE' still called a tool on a fresh question, 2 out of 2. The fix is structural: omit tools.

                  Batch embeddings count per text (AG.1)

                  Running the eval twice in a minute → 429. A batch of 70 texts uses 70 of the 100 per-minute requests. A batch saves round trips, not quota.

                  Vectors read words, not intent (AG.1)

                  "what is a quiz?" → quiz at margin 0.141. Hence the "quiz always gets a second opinion" rule.

                  The misread margin (AG.2)

                  Real questions looked like low-margin document questions; they were actually low-margin smalltalk. The guard was right; the explanation was wrong, and the log now says so.

                  for await eats the return value (AG.4)

                  The AgentResult only exists as the generator's return. Both routes call .next() by hand.

                  Saved ≠ shown (AG.4)

                  Text written before a tool call is already on screen, and the give-up line has to be yielded to appear at all. Saved answer = everything streamed.

                  Gemini's mood (AG.5 vs AG.6)

                  The same classifier call took 25–53 s one day and 1.7–3.4 s replies two days later, with the odd 503 "high demand". Don't redesign over one slow run.

                  Test traps

                  A fake-stream helper with unsorted cut points looked like a parser bug. "Thinking row gone" isn't "answer finished" (it goes at the first word). A bare headless page load creates a guest that must be deleted. The browser tool wanted Chromium 1248; the installed 1243 was launched by path.

                  A shell trap (AG.2)

                  A script piped through a bash heredoc turned a written \n into a real line break inside generated TypeScript. Edits with backslash escapes go through the editor tool.

                  Check yourself

                  say it out loud, then open
                  Why does a vector quiz_request always go to the LLM, even at a big margin?

                  Vectors match shared words. "compare the two pdfs" looked like "quiz me about the pdf" (0.101), "what is a quiz?" looked like "give me a quiz" (0.141). A quiz offer replaces the answer with something else, and real quiz requests are rare, so a second opinion on them is cheap.

                  Why is every unsure path document_question, never smalltalk?

                  A real question routed to smalltalk gets no search and a confident wrong reply. Smalltalk routed to the agent just gets a document-flavoured reply, which was the old behaviour anyway.

                  How does the agent know whose documents to search, and could a PDF change that?

                  userId and documentId live in the ToolContext, set from the verified token and the session before the loop starts. The tool only takes { query }, so there is no argument an injected sentence could steer. searchSimilar also filters on documents.user_id.

                  How is "answer now" enforced on step 3?

                  The request is sent without tools. mode: 'NONE' was ignored on this model in AG.0. As a guard, a call that comes back on the last step is never run.

                  What happens if you rebuild the model's turn from its text before sending it back?

                  The thoughtSignature is lost and Gemini answers 400. Turns go back exactly as received; streamed turns are rebuilt by addPart, which never separates a signature from its part.

                  Why do the routes call .next() by hand instead of for await?

                  The AgentResult is the generator's return value, and for await discards return values. yield* is how streamAgent gets streamTurn's return value.

                  What exactly is saved as the assistant's reply on the agent path?

                  Every text piece streamed across all steps, including any sentence before a tool call and the give-up line if it was used. What's saved equals what the user saw. Tool calls and results are not saved.

                  Why did the follow-up "and who founded it?" get better?

                  The old pipeline embedded the raw words before loading history. The agent reads the history as real turns and writes the query itself: "who founded the Lantern Festival". The right chunk went from a 0.002 lead to a clear one at 0.366.

                  Why is the quiz a button and not a tool or a typed "yes"?

                  It spends quota, so it's Kind B: never a tool. A typed "yes" needs the pending offer remembered between requests, which is Phase 8's suspend/resume. The button carries the documentId itself, so no server memory is needed.

                  How could the old frontend keep working against the new API?

                  Its dispatch() switch has no default, so unknown events are skipped, and meta.sources still exists (empty). Tested in AG.4 with the pre-AG.4 bundle: it answered, without sources.

                  What does one document question cost, and what's the site-wide ceiling?

                  1 embedding + 2 generate calls (+0–1 embedding for the query, +1 classifier on a close call). At 15 Flash-Lite requests per minute shared by everyone, that's about 7 questions per minute, roughly 250 a day.

                  Why was loading history moved before routing in AG.2?

                  The LLM classifier needs the last question and answer to label a follow-up like "why?" as a document question. It's still read before this turn's user message is saved, so it never contains the message being answered.

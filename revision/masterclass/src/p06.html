6.ALessons

An embedding is a fixed-length list of numbers (a vector) that an embedding model produces for a piece of text, such that texts with similar meaning get vectors that point in similar directions. Computers compare numbers well and meaning badly. Keyword search fails on “How do I get my money back?” vs a document that says “refund policy”. Embeddings put both near each other, so search works by meaning.

The model is a transformer encoder trained with contrastive learning: pairs that belong together (question/answer, title/abstract, paraphrases) are pulled close; random pairs are pushed apart. After training, each dimension doesn’t mean anything human-readable on its own; meaning lives in the overall direction.

 A map where every sentence gets coordinates. Sentences about refunds cluster in one neighbourhood, shipping in another. Searching = dropping a pin for the question and looking at the nearest houses. The real map has hundreds or thousands of dimensions instead of two. Semantic search, RAG retrieval, deduplication (near-duplicate questions), clustering support tickets, recommendations, routing (DocMind compares a message to example phrases per intent). DocMind uses gemini-embedding-001 with 3072 dimensions, stored in chunks.embedding vector(3072). Real numbers from step1-embeddings.ts: “The cat sat on the mat” vs “A kitten was resting on the rug” scored 0.7628; cat vs a stock-market sentence scored 0.5879. Unrelated text still scores well above 0, so the gap matters, not the absolute value.
  • Expecting similarity 1.0 for “same topic”. Values depend on the model; compare relative ranks.
  • Mixing vectors from two models in one index.
 Cosine similarity compares direction only (−1 to 1). Dot product grows with both direction agreement and lengths. Euclidean distance is the straight-line distance between the points.
  • cos(a, b) = (a · b) / (|a| × |b|).
  • If every vector has length 1 (normalised), then a · b = cos(a, b) and |a − b|² = 2 − 2·cos(a, b): all three give the same ranking. Many embedding APIs return normalised vectors (check the docs; some sizes need you to normalise).
  • With unnormalised vectors, dot product favours long vectors (e.g. long documents), Euclidean penalises them.
 pgvector operators: <=> cosine distance (1 − cosine similarity), <#> negative inner product (so smaller is better, for ORDER BY), <-> Euclidean (L2) distance.
  • Sorting by <=> DESC (that returns the least similar).
  • Using an index built for one operator class with a different operator: the index is silently not used.
 pgvector is a Postgres extension that adds a vector column type, distance operators, and approximate nearest-neighbour indexes (HNSW and IVFFlat).

  document_id uuid NOT NULL REFERENCES documents(id) ON DELETE CASCADE,
  content text NOT NULL,
  embedding vector(1536) NOT NULL
);

-- insert: send the vector as a string '[0.1,0.2,...]' or via your driver

-- exact search (no index): top 5 for one user, cosine
SELECT c.id, c.content, d.filename, c.embedding <=> $1 AS distance
FROM chunks c JOIN documents d ON d.id = c.document_id
WHERE d.user_id = $2 AND d.status = 'ready'
ORDER BY c.embedding <=> $1
LIMIT 5;

SET hnsw.ef_search = 100;            -- per session/transaction: more candidates = better recall, slower

-- or IVFFlat (fast build, smaller; build AFTER loading data; lists ≈ rows/1000)

SET ivfflat.probes = 10;             -- lists searched per query (default 1)

-- delete a document's vectors

HNSW (Hierarchical Navigable Small World): a multi-layer graph. Top layers have few long-range links; lower layers are dense. A search enters at the top, greedily walks toward the query, drops a layer, repeats, and keeps the best ef_search candidates at the bottom. ~O(log n) hops instead of comparing with every vector.

IVFFlat: k-means splits vectors into lists clusters at build time. A query finds the nearest cluster centroids and scans only the probes closest lists. Build it after the data exists (centroids come from the data).

Filtering pitfall: with an ANN index, Postgres takes the index’s top candidates and then applies WHERE user_id = …. If most candidates belong to other users, you get fewer than 5 rows (or none). Fixes: pgvector 0.8+ iterative index scans (SET hnsw.iterative_scan = relaxed_order), partial indexes or partitions per tenant, higher ef_search, or exact search when a user has few vectors.

 DocMind has no vector index: every search is an exact scan over the user’s chunks (fine at its size).   2. Without an index: Postgres joins chunks to documents, filters by user and status, computes <=> for each remaining row, sorts, returns 5. Exact, linear in the user’s rows.
  3. With HNSW: the planner sees ORDER BY embedding <=> $1 LIMIT 5 and uses the index to fetch candidates nearest the query, then applies the WHERE filters to them; with iterative scans enabled it keeps scanning until 5 rows pass.
  4. hnsw.ef_search sets how many candidates the graph search keeps: higher = better recall, slower.
  5. Deleting a document cascades its chunks; the index entries are cleaned up by vacuum.

6.1Embeddings

What is an embedding?A fixed-length vector of numbers that represents the meaning of a text (or image), produced by an embedding model so that similar meanings get nearby vectors. An embedding model reads a text and outputs a point in a high-dimensional space, for example 1,536 numbers. Training arranges the space so that texts used in similar contexts or with similar meaning end up close together, and unrelated texts far apart. You never interpret single numbers; you compare whole vectors with a distance or similarity function. Embeddings exist for text, images, audio and code, and multimodal models put several types in one shared space. “How do I reset my password?” and “I forgot my login credentials” land near each other; “Quarterly revenue grew 15%” lands far away. Not exactly, but research shows a lot of the text can be reconstructed from some embeddings, so treat them as sensitive data, not anonymised. “Each dimension means a specific concept like ‘sports’.” Basics. Why do we convert text into numerical vectors?So we can measure similarity of meaning with fast math (and index it), which enables semantic search, clustering and retrieval, where keyword matching misses synonyms and paraphrases. Search over text needs a notion of “close in meaning”. Words alone fail on synonyms (car/automobile), paraphrases and different languages, and succeed on accidental shared words. Mapping text to vectors turns meaning-similarity into geometry, which computers can compute quickly and index for millions of items. It also makes text usable by other numeric methods: clustering, classification, deduplication, recommendation. A support bot finds the “Refund policy” article for “can I get my money back?” although no keyword overlaps. Exact identifiers (codes, SKUs), negation and precise numbers, and very long texts squeezed into one vector. “Because computers can’t store text.” Purpose. How does an embedding model generate vectors at a high level?Tokenize the text, run it through a transformer encoder so each token gets a context-aware vector, pool those into one vector (mean or a special token), often normalise it. The model was trained contrastively so related texts land close together. The text is tokenised and passed through a transformer encoder; every token gets a context-aware vector after the attention layers. A pooling step turns the token vectors into one vector (mean of all tokens, or the vector of a special first token), sometimes followed by a projection and normalisation to length 1. The model was trained contrastively on pairs (query, relevant passage) so that pairs score high and in-batch non-pairs score low, which is what makes distances meaningful for retrieval. Step through the “How text becomes an embedding” animation in lesson 6.A. They were trained with different roles for queries and documents; the hint puts each into the right part of the space. “It averages word vectors from a dictionary.” (That was older word2vec-style; modern models are contextual.) Intuition. What does embedding dimensionality mean?The number of values in each vector (e.g. 768, 1536, 3072). More dimensions can capture finer distinctions but cost more storage, memory and compute per comparison. Dimensionality is the length of each vector, fixed by the model (some let you request a shorter output). Each extra dimension adds capacity to separate meanings, but also storage (4 bytes per float32 dimension), memory for indexes, and compute per comparison. Dimension doesn’t depend on input length: a word and a page both become, say, 1,536 numbers.1M chunks × 3072 dims × 4 bytes ≈ 12 GB of raw vectors; at 768 dims ≈ 3 GB. Only if the model was trained for it (Matryoshka-style models like many current ones); truncating other models’ vectors degrades quality badly. Re-normalise after truncating. “Dimension = number of words the model knows.” Cost awareness. Does a larger embedding dimension always mean better results?No. Quality depends on the model and on your data; a good 768-dim model can beat a weaker 3072-dim one. Many modern models support shorter outputs (Matryoshka-style) with a small quality loss and big savings. Measure on your own retrieval eval. More dimensions give the model more room to encode distinctions, but returns diminish, and quality depends far more on training data and objective than on width. Costs grow linearly: storage, memory for indexes, and compute per comparison; and pgvector indexes the vector type only up to 2,000 dimensions. Many current models are trained so that the first N dimensions are usable on their own (Matryoshka representation learning), letting you choose 256/768/1536 with small quality loss. Benchmarks often show a good 768-dim model beating a larger, older model on retrieval for a given domain. Run your own retrieval eval (recall@k on your questions) for 2–3 candidate models/dimensions and weigh quality against storage and latency. “Always pick the biggest.” Judgement. What does semantic similarity mean?Similarity in meaning, not in exact words: “cancel my subscription” and “stop my plan from renewing” are semantically similar with almost no shared words. Two texts are semantically similar if they mean roughly the same thing or are about the same topic, regardless of surface wording. Note that “similar” depends on how the model was trained: some models score a question and its answer as close (retrieval-trained), others score paraphrases as close (similarity-trained). A question and a document that contradicts it can still be “similar” because they’re about the same thing. “The meeting is cancelled” and “The meeting is not cancelled” can score very high similarity. Similar ≠ relevant or correct; reranking and the LLM’s reading of the text still matter. “Similar embeddings means identical meaning.” Basics. What is cosine similarity? The cosine of the angle between two vectors: dot product divided by the product of their lengths. 1 = same direction, 0 = unrelated (orthogonal), −1 = opposite. It ignores vector length. Cosine similarity measures the angle between vectors: 1 means same direction, 0 orthogonal, −1 opposite. Because it divides by both lengths, it ignores magnitude, which for text embeddings usually reflects things like length or frequency rather than meaning. Scores are model-specific: one model’s 0.8 is not another’s. In DocMind’s first experiment: “The cat sat on the mat” vs “A kitten was resting on the rug” = 0.7628; vs a stock-market sentence = 0.5879. 
const cosine = (a, b) => {
  let dot = 0, na = 0, nb = 0;
  for (let i = 0; i < a.length; i++) { dot += a[i] * b[i]; na += a[i] ** 2; nb += b[i] ** 2; }
  return dot / (Math.sqrt(na) * Math.sqrt(nb));
};
 Embedding spaces aren’t uniformly spread; most texts share some direction (language, style), so unrelated pairs often score well above 0. Compare relative ranks. “Cosine similarity is a probability.” Core metric. What is dot-product similarity?The sum of element-wise products. It equals cosine similarity times both lengths, so it’s cheaper and identical to cosine when vectors are normalised. The dot product sums element-wise products. Geometrically it’s |a|·|b|·cos θ, so it rewards both alignment and length. For normalised vectors (length 1) it equals cosine similarity and is cheaper (no division). Some models are trained for dot product and produce meaningful lengths; use what the model card recommends. In pgvector, <#> returns the negative inner product so ascending ORDER BY gives the best first. a = [1, 2], b = [3, 1] → 1·3 + 2·1 = 5. When vectors are normalised (same ranking as cosine, faster), or when the model encodes importance in vector length. “Dot product and cosine always rank the same.” Only for equal-length vectors. Basics. What is Euclidean distance?The straight-line distance between two points: the square root of the sum of squared differences. Smaller = more similar. Euclidean (L2) distance is the straight-line distance: √Σ(aᵢ − bᵢ)². It depends on both direction and magnitude. For unit vectors, |a − b|² = 2 − 2·cos(a, b), so it ranks identically to cosine. pgvector’s <-> operator computes it. a = [1, 2], b = [3, 1] → √((1−3)² + (2−1)²) = √5 ≈ 2.236. When the model was trained with it, or for non-normalised features where absolute position matters (some image or tabular embeddings). “Bigger Euclidean distance = more similar.” Basics. How do these similarity metrics differ?Cosine uses direction only; dot product uses direction and magnitude; Euclidean measures absolute position. For normalised vectors they produce the same ranking; otherwise use the metric the model was trained for (its docs say).

Why should the same embedding model generally be used for ingestion and query embedding?Each model has its own vector space. A query from model B compared with chunks from model A gives meaningless distances. An embedding model defines its own space; similarity is only meaningful between vectors produced by that model with the same settings (version, output dimension, task type). Queries and documents must therefore be embedded by the same model, or retrieval silently returns nonsense with no error. Ingesting with model A and embedding queries with model B is like plotting cities with one map projection and searching with another: coordinates look valid but point to the wrong places.Some models use different task types or prefixes for queries vs documents (“query:” / “passage:”, or a task_type parameter), but it’s still the same model and space. That’s fine: a cross-encoder reranker reads text, not vectors, so it doesn’t need to match the embedding model. “Same dimension means compatible.” Correctness. Can two different embedding models produce compatible vectors?Not in general, even with the same dimension. Different training gives different spaces. Only versions explicitly documented as compatible, or vectors passed through a learned alignment mapping, can be compared, and that’s rare and lossy. Each model learns its own coordinate system: even with the same dimension count, dimension 17 in model A has nothing to do with dimension 17 in model B, and the global geometry differs. Only vectors from the same model (and the same version and settings, such as output dimension and normalisation) are comparable. Alignment methods (learning a linear map between spaces from paired examples) exist but lose quality and are rarely worth it versus re-embedding. Even upgrading “model-v1” to “model-v2” from the same provider typically requires re-embedding. Store the model name/version with each vector (or per table/column) and assert it matches the query model in code. “Providers keep vectors compatible across versions.” Understanding of vector spaces. What happens if you change your embedding model?All stored vectors become incompatible with new query vectors, so you must re-embed the whole corpus (and possibly change the column dimension and rebuild indexes) before switching queries. The new model’s query vectors are in a different space from the stored chunk vectors, so similarity scores become meaningless: search returns essentially random chunks while looking fine (no errors). You must re-embed the corpus, possibly change the column dimension and rebuild indexes, and switch query embedding at the same moment as the corpus switch. Plan it as a migration: dual columns, backfill, eval, cutover, cleanup. Lesson 6.D walks through the safe sequence. Only if search queries each document with its matching model, which complicates ranking across documents; usually you dual-write and cut over once the backfill is done. “Only new documents need the new model.” Operational awareness. How would you re-embed an existing document collection?Background backfill into a new column/table: batched, rate-limited, idempotent, resumable, with progress tracking; dual-write new data; evaluate; switch reads behind a flag; keep the old vectors until confident.

6.2Vector databases

What is a vector database?A database designed to store vectors with metadata and answer nearest-neighbour queries fast, usually with ANN indexes, filtering and hybrid search: Pinecone, Qdrant, Weaviate, Milvus, or Postgres with pgvector. A vector database stores vectors with ids and metadata, builds approximate nearest-neighbour indexes, and answers “top-k most similar to this vector, with these filters” quickly at scale. Dedicated ones (Pinecone, Qdrant, Weaviate, Milvus) add features like hybrid search, sharding and replication; general databases with extensions (Postgres + pgvector, Elasticsearch/OpenSearch k-NN) add vectors next to existing data. A product search with 50M items and strict latency targets might use a dedicated vector DB; a SaaS app with 1M chunks and per-user permissions fits well in pgvector. Transactions and joins with your relational data; you must sync deletes and permission changes between systems. “Vector databases understand text.” They only store and compare vectors. Basics. Why can’t we simply store embeddings in ordinary database columns?You can store them (an array or JSON column), but you can’t search them efficiently: you’d load every vector and compute distances in the app. You need distance operators in the database and special indexes, which a vector type and ANN indexes provide. Storing is easy (an array or JSON column), searching is the problem. Without vector-aware operators and indexes, finding the nearest vectors means reading every row into the application and computing distances: O(n·d) per query plus huge data transfer. Vector types add compact storage, distance operators executed inside the database, and ANN indexes that avoid scanning everything. 1M rows × 1536 floats ≈ 6 GB transferred to the app per query without database-side search: impossible for a web request. For small, static sets (e.g. a few hundred router example phrases, like DocMind’s intent examples). “You need a vector database to store embeddings at all.” Reasoning. Can PostgreSQL store vectors?Yes, with the pgvector extension: a vector(n) type (plus halfvec, sparsevec, bit), distance operators and HNSW/IVFFlat indexes. Yes. pgvector adds types vector(n) (float32), halfvec(n) (float16, half the storage, higher index dimension limit), sparsevec and bit, distance operators, and HNSW/IVFFlat indexes. Managed Postgres providers (Neon, Supabase, RDS, Cloud SQL) support it. What is pgvector?An open-source Postgres extension for vector similarity search, so embeddings live in the same database as your app data, with SQL joins, filters and transactions. pgvector is an open-source extension that teaches Postgres vector types, distance functions (<-> L2, <#> negative inner product, <=> cosine, <+> L1), exact search by default, and ANN indexes. Because it’s inside Postgres, vector search composes with WHERE filters, JOINs, transactions, row-level security and backups. DocMind’s search joins chunks to documents for owner and status filters in the same query that orders by cosine distance. Practical up to tens of millions of vectors on a well-sized server with HNSW; beyond that, partitioning or dedicated systems are considered. “pgvector is a separate database.” Basics. What are HNSW and IVFFlat?Two approximate nearest-neighbour index types. HNSW builds a layered graph and greedily navigates it: high recall and speed, more memory, slower build, works on an empty table. IVFFlat clusters vectors into lists and searches the nearest few: faster build and smaller, but needs data first and usually lower recall at equal speed. HNSW builds a multi-layer proximity graph: each vector links to its nearest neighbours (m links), upper layers are sparse shortcuts, the bottom layer holds all vectors. Search enters at the top and greedily moves toward the query, keeping ef_search candidates. It has high recall at low latency, supports inserts without rebuilding, but uses more memory and builds slowly. IVFFlat runs k-means to create lists centroids, assigns each vector to its nearest list, and at query time scans only the probes nearest lists. It builds quickly and uses less memory, but must be built after data exists, and recall drops if data drifts from the centroids. What’s the difference between exact and approximate nearest-neighbor search?Exact compares the query with every vector: perfect recall, cost grows linearly. Approximate uses an index to check a small subset: much faster at scale, but may miss some true neighbours (recall below 100%), tunable with ef_search/probes. Exact (brute-force) k-NN compares the query with every vector: perfect recall, linear time. Approximate (ANN) methods trade a little recall for sub-linear time by searching a graph (HNSW), clusters (IVF) or compressed codes (PQ). Recall@k measures how many of the true top-k the ANN returned; you tune parameters (ef_search, probes) to hit a target like 95–99% at acceptable latency. 10M vectors: exact ≈ seconds per query; HNSW ≈ milliseconds with ~98% recall. For a sample of queries, compute exact top-k (no index, e.g. SET enable_indexscan = off or a separate exact query) and compare with the indexed results. “Approximate means the results are wrong.” Trade-off. What is a vector index?A data structure (graph or clusters) that lets the database find vectors near a query without scanning all of them. A vector index is a data structure built from the stored vectors that lets the database find near neighbours without comparing against all of them. What is top-K retrieval?Returning the K most similar items to the query (ORDER BY distance LIMIT K). K trades recall against noise and prompt size. Top-K returns the K highest-scoring items. K is a precision/recall knob: small K keeps prompts short and precise but risks missing the answer; large K improves recall but adds noise and cost. One row per chunk with: a stable id; the document foreign key; position (chunk_index, page); the text (needed for prompts and keyword search); the embedding; metadata used for filtering and citations (heading, language, token count); and the embedding model version. How would you isolate vectors belonging to different users?Every query filters by the owner taken from the auth token, through a join or a user_id/tenant_id column; never trust an id from the request body. At scale, per-tenant partitions or partial indexes keep ANN results correct; Postgres row-level security adds a safety net. Isolation must happen inside the retrieval query, because top-k is computed over whatever rows the query can see. Options: filter by an owner/tenant column through a join or denormalised column (with the id from the session), row-level security policies as a backstop, partial indexes or partitions per tenant for ANN correctness at scale, or separate collections per tenant in a vector DB. How would you delete all chunks belonging to a document?DELETE FROM chunks WHERE document_id = $1 after checking the document belongs to the caller, or rely on ON DELETE CASCADE from documents, inside a transaction with the document row. Deleting a document’s vectors must be complete (no orphans that could still be retrieved), authorised (only the owner), and consistent with ongoing processing (a running ingestion job must not re-insert after deletion). Use foreign keys with ON DELETE CASCADE or an explicit delete in the same transaction as the document row, scoped by owner; with an external vector DB, delete by a document-id metadata filter and handle failures with retries or a cleanup job.

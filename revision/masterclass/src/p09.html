9.ALessons

A workflow is a process whose steps and order are defined in code as a graph: step A, then B and C in parallel, then D if a condition holds. Each step may call an LLM, but the path is decided by your code. An agent lets the model decide the path. Many AI features are multi-step processes with a known shape: generate outline → approve → generate lessons → save. Letting an agent improvise that order adds cost and risk for no benefit. Workflows give predictable execution, per-step retries, persisted state that survives restarts, and pausing for humans.
  • Deterministic workflow: same input → same path (the LLM output inside a step may vary, the structure doesn’t).
  • Non-deterministic process: the path itself depends on model decisions (an agent).
  • Common combination: a workflow whose individual steps call an agent for an open-ended sub-task.
 A workflow is a recipe card: steps in order, “while the sauce simmers, chop the onions” (parallel), “if guests are vegetarian, skip step 4” (branch). An agent is a chef improvising with what’s in the fridge. Order fulfilment, document ingestion pipelines, report generation, onboarding flows, content generation with review, approval chains. The shapes a workflow graph can take.
ShapeMastraUse when
Sequential.then(step)a step needs the previous output
Parallel.parallel([a, b]) (output keyed by step id)independent steps; total time = slowest one
Conditional.branch([[cond, step], …]) (every true condition runs)different paths for different inputs
Loop over items.foreach(step, { concurrency: n }) (default 1 = sequential; output array keeps input order)same step for each item, with a concurrency cap
Repeat until.dountil(step, cond) / .dowhileretry until quality passes, poll until ready
Reshape data.map(async ({ inputData }) => …)adapt one step’s output to the next step’s input

If any step in a .parallel() throws, the whole parallel block fails. For partial success, catch inside the step and return { failed: true }.

 Workflow state is what’s known so far: inputs, each step’s status and output. Persistence writes it to storage after each step (a snapshot). Suspend stops a run at a step and saves it; resume continues it later, even in another process. A human approval might take hours; a server deploy restarts the process every few days; an LLM step might fail at 60%. Without persisted state you’d restart from zero or lose the run. With it, the run continues from the last completed step.
  1. run.start() executes steps; after each, the engine saves a snapshot (status + step results) to storage.
  2. A step calls suspend(payload): the snapshot is saved with status suspended and the payload; start() returns { status: 'suspended', suspended: [stepId] }. Nothing is running now.
  3. Later, any process: createRun({ runId }) + run.resume({ step, resumeData }). The engine loads the snapshot, claims it (status suspended → running, atomically), and re-runs the suspended step’s execute from the top with resumeData set.
  4. Server restart while a run is running: Mastra’s default recovery: { workflows: 'auto' } re-drives such runs from the last snapshot at boot. Suspended runs simply wait.

Rule that follows from step 3: nothing with a side effect may sit above the if (!resumeData) return suspend(...) line, or it runs twice.

 A video game save point. Quitting (crash) loses only the progress since the last save. Waiting for a friend to join (approval) is a save + pause; when they arrive you load and continue.
  • Expecting start() to mean finished. Always check result.status: success, suspended, failed, canceled (and remember bail() ends as success with the bail payload as the result).
  • Assuming run.cancel() stops a step that’s already running: it doesn’t unless the step listens to abortSignal.
 Retries re-run a failed step. Idempotency makes re-running safe. A compensating action undoes the effect of an earlier completed step when a later step fails (the saga pattern).
  • Retries happen at several layers (HTTP client, step retries: n, workflow retryConfig: { attempts, delay }, a re-run of the whole workflow). Pick one or two layers on purpose; multiplying them multiplies LLM spend.
  • A step can run more than once (retry, crash after the work but before the snapshot, recovery). So each step’s side effects must be idempotent: upserts on natural keys ((course_id, module_no, lesson_no)), “skip if already done” checks, idempotency keys on external APIs.
  • Compensation: workflows can’t roll back across systems with one transaction. If step 4 charges a card and step 5 fails permanently, run a compensating step (refund) and mark the run failed. For pure content generation, the usual “compensation” is simply: keep drafts unpublished, or delete them.
 Payments + order creation (refund on failure), booking flights + hotels (cancel the flight if the hotel fails), course generation (drafts invisible until a final publish transaction). A complete workflow: validate + dedupe → outline (LLM, structured) → suspend for approval → lessons in parallel with a concurrency cap and retries → module quizzes → publish in one transaction. Uses the chat() helper from Phase 5 for LLM calls, pg for app tables, and @mastra/pg for workflow snapshots. 
CREATE TABLE courses (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  user_id uuid NOT NULL, request_key text NOT NULL,          -- idempotency: one course per user + request
  topic text NOT NULL, status text NOT NULL DEFAULT 'draft',  -- draft | awaiting_approval | generating | published | rejected | failed
  outline jsonb, outline_approved_at timestamptz, run_id text,

  UNIQUE (user_id, request_key));
CREATE TABLE lesson_drafts (

// mastra/course.workflow.js
import { createWorkflow, createStep } from '@mastra/core/workflows';
import { z } from 'zod';
import { pool } from '../db.js';
import { chat } from '../llm.js';

const Outline = z.object({
  title: z.string().min(3),
  modules: z.array(z.object({
    title: z.string().min(3),
    lessons: z.array(z.object({ title: z.string().min(3) })).min(2).max(6),
  })).min(1).max(10),
});
const Lesson = z.object({ body: z.string().min(400) });
const Quiz = z.object({ questions: z.array(z.object({
  question: z.string(), options: z.array(z.string()).length(4), correctIndex: z.number().int().min(0).max(3),
})).length(5) });

// 1. dedupe + create the course row (idempotent upsert)
const prepare = createStep({
  id: 'prepare',
  inputSchema: z.object({ userId: z.string(), requestKey: z.string(), topic: z.string().min(3).max(200), modules: z.number().int().min(1).max(10) }),
  outputSchema: z.object({ courseId: z.string(), topic: z.string(), modules: z.number(), outline: Outline.nullable(), approved: z.boolean() }),
  execute: async ({ inputData, bail, runId }) => {
    const { rows: [c] } = await pool.query(
      `INSERT INTO courses (user_id, request_key, topic, run_id) VALUES ($1, $2, $3, $4)
       ON CONFLICT (user_id, request_key) DO UPDATE SET run_id = EXCLUDED.run_id
       RETURNING id, status, outline, outline_approved_at`,
      [inputData.userId, inputData.requestKey, inputData.topic, runId]);
    if (c.status === 'published') return bail({ outcome: 'duplicate', courseId: c.id });  // ends the run as success
    return { courseId: c.id, topic: inputData.topic, modules: inputData.modules, outline: c.outline, approved: !!c.outline_approved_at };
  },
});

// 2. outline: skip the LLM if a previous run already produced one
const outline = createStep({
  id: 'outline',
  inputSchema: prepare.outputSchema,
  outputSchema: prepare.outputSchema.extend({ outline: Outline }),
  execute: async ({ inputData }) => {
    if (inputData.outline) return { ...inputData, outline: inputData.outline };
    const { data } = await chat({ temperature: 0.4, schema: Outline, messages: [
      { role: 'system', content: 'You design concise, practical courses. No duplicate module or lesson titles.' },
      { role: 'user', content: `Course topic: ${inputData.topic}. Exactly ${inputData.modules} modules, 2-6 lessons each.` } ] });
    await pool.query("UPDATE courses SET outline = $2, status = 'awaiting_approval' WHERE id = $1", [inputData.courseId, data]);
    return { ...inputData, outline: data };
  },
});

// 3. human approval: suspend until the user answers
const approve = createStep({
  id: 'approve-outline',
  inputSchema: outline.outputSchema,
  outputSchema: outline.outputSchema,
  suspendSchema: z.object({ courseId: z.string(), outline: Outline }),
  resumeSchema: z.object({ approved: z.boolean() }),
  execute: async ({ inputData, resumeData, suspend, bail }) => {
    if (inputData.approved) return inputData;                               // approved in an earlier run
    if (!resumeData) return await suspend({ courseId: inputData.courseId, outline: inputData.outline });
    // ↑ nothing with side effects above this line: execute runs again from the top on resume
    if (!resumeData.approved) {
      await pool.query("UPDATE courses SET status = 'rejected' WHERE id = $1", [inputData.courseId]);
      return bail({ outcome: 'rejected', courseId: inputData.courseId });
    }
    await pool.query("UPDATE courses SET outline_approved_at = now(), status = 'generating' WHERE id = $1", [inputData.courseId]);
    return { ...inputData, approved: true };
  },
});

// 4. one lesson (run by foreach, 3 at a time)
const LessonItem = z.object({ courseId: z.string(), topic: z.string(), moduleNo: z.number(), moduleTitle: z.string(),
  lessonNo: z.number(), title: z.string(), siblings: z.array(z.string()) });
const writeLesson = createStep({
  id: 'write-lesson',
  retries: 2,                                                              // step-level retry for flaky LLM calls
  inputSchema: LessonItem,
  outputSchema: z.object({ moduleNo: z.number(), lessonNo: z.number() }),
  execute: async ({ inputData: l }) => {
    const done = await pool.query('SELECT 1 FROM lesson_drafts WHERE course_id = $1 AND module_no = $2 AND lesson_no = $3',
      [l.courseId, l.moduleNo, l.lessonNo]);
    if (done.rowCount) return { moduleNo: l.moduleNo, lessonNo: l.lessonNo };   // already generated: no LLM spend
    const { data } = await chat({ temperature: 0.5, maxTokens: 1500, schema: Lesson, messages: [
      { role: 'system', content: 'Write one lesson in Markdown. Stay on the lesson title. Do not repeat sibling lessons.' },
      { role: 'user', content: `Course: ${l.topic}\nModule: ${l.moduleTitle}\nLesson: ${l.title}\nOther lessons in this module: ${l.siblings.join('; ')}` } ] });
    await pool.query(
      'INSERT INTO lesson_drafts (course_id, module_no, lesson_no, title, body) VALUES ($1,$2,$3,$4,$5) ON CONFLICT DO NOTHING',
      [l.courseId, l.moduleNo, l.lessonNo, l.title, data.body]);
    return { moduleNo: l.moduleNo, lessonNo: l.lessonNo };
  },
});

// 5. one quiz per module
const writeQuiz = createStep({
  id: 'write-quiz',
  retries: 2,
  inputSchema: z.object({ courseId: z.string(), moduleNo: z.number(), moduleTitle: z.string() }),
  outputSchema: z.object({ moduleNo: z.number() }),
  execute: async ({ inputData: m }) => {
    const { rows } = await pool.query('SELECT body FROM lesson_drafts WHERE course_id = $1 AND module_no = $2 ORDER BY lesson_no', [m.courseId, m.moduleNo]);
    const { data } = await chat({ temperature: 0.3, schema: Quiz, messages: [
      { role: 'system', content: 'Write 5 multiple-choice questions answerable from the lessons only. Options must be distinct.' },
      { role: 'user', content: rows.map((r) => r.body).join('\n\n---\n\n').slice(0, 24000) } ] });
    if (data.questions.some((q) => new Set(q.options).size !== 4)) throw new Error('duplicate options');   // → retry
    await pool.query('INSERT INTO module_quizzes (course_id, module_no, questions) VALUES ($1,$2,$3) ON CONFLICT (course_id, module_no) DO UPDATE SET questions = EXCLUDED.questions',
      [m.courseId, m.moduleNo, JSON.stringify(data.questions)]);
    return { moduleNo: m.moduleNo };
  },
});

// 6. publish: only if everything exists, in one transaction
const publish = createStep({
  id: 'publish',
  inputSchema: z.object({ courseId: z.string(), expectedLessons: z.number(), expectedModules: z.number() }),
  outputSchema: z.object({ outcome: z.literal('published'), courseId: z.string() }),
  execute: async ({ inputData }) => {
    const client = await pool.connect();
    try {
      await client.query('BEGIN');
      const { rows: [n] } = await client.query(
        `SELECT (SELECT count(*) FROM lesson_drafts WHERE course_id = $1)::int AS lessons,
                (SELECT count(*) FROM module_quizzes WHERE course_id = $1)::int AS quizzes`, [inputData.courseId]);
      if (n.lessons !== inputData.expectedLessons || n.quizzes !== inputData.expectedModules) throw new Error(`incomplete: ${JSON.stringify(n)}`);
      await client.query("UPDATE courses SET status = 'published' WHERE id = $1", [inputData.courseId]);
      await client.query('COMMIT');
    } catch (e) { await client.query('ROLLBACK'); throw e; } finally { client.release(); }
    return { outcome: 'published', courseId: inputData.courseId };
  },
});

export const courseWorkflow = createWorkflow({
  id: 'course-generation',
  inputSchema: prepare.inputSchema,
  outputSchema: z.object({ outcome: z.string(), courseId: z.string() }),
})
  .then(prepare)
  .then(outline)
  .then(approve)
  .map(async ({ inputData: c }) => c.outline.modules.flatMap((m, mi) => m.lessons.map((l, li) => ({
    courseId: c.courseId, topic: c.topic, moduleNo: mi + 1, moduleTitle: m.title, lessonNo: li + 1, title: l.title,
    siblings: m.lessons.map((x) => x.title).filter((t) => t !== l.title) }))))
  .foreach(writeLesson, { concurrency: 3 })                                  // rate-limit friendly
  .map(async ({ getStepResultAsync }) => {
    const c = await getStepResultAsync(approve);
    return c.outline.modules.map((m, i) => ({ courseId: c.courseId, moduleNo: i + 1, moduleTitle: m.title }));
  })
  .foreach(writeQuiz, { concurrency: 3 })
  .map(async ({ getStepResultAsync }) => {
    const c = await getStepResultAsync(approve);
    return { courseId: c.courseId, expectedModules: c.outline.modules.length,
      expectedLessons: c.outline.modules.reduce((s, m) => s + m.lessons.length, 0) };
  })
  .then(publish)
  .commit();

9.1Workflow fundamentals

What is a workflow?A defined sequence or graph of steps, with data flowing from one step to the next, executed by an engine that tracks each step’s status and can retry, pause and resume. A workflow engine executes a defined graph of steps for each run: it passes data from step to step, records each step’s status and output, retries failed steps by policy, can pause (suspend/sleep) and continue later, and lets you inspect runs. The definition is code (or config) and the order is fixed by it; individual steps can call anything, including LLMs or agents. Order fulfilment: validate payment → reserve stock → ship → email, with retries per step and a human check for high-value orders. A queue runs independent jobs; a workflow coordinates many steps of one process with state across them (a workflow engine often uses queues underneath). “A workflow is a list of function calls in a route handler.” (No persistence, retries or resume.) Basics. What is the difference between a workflow and an agent?In a workflow, code decides the order of steps; in an agent, the model decides the next action at runtime. Workflows are predictable and easy to retry and audit; agents are flexible for open-ended tasks. The key difference is who decides the control flow. In a workflow, the developer encodes the steps, order, branches and loops; the engine executes them and persists progress. In an agent, the model chooses actions step by step from the tools available. Workflows give predictability, durability, per-step retries and easy auditing; agents give flexibility for tasks whose path can’t be known in advance. They combine well: workflows calling agents for open sub-tasks. “Generate a course” (fixed steps) → workflow. “Help me understand my documents” (open-ended, choose tools) → agent. “Generate a course, researching each topic” → workflow whose research step calls an agent. Yes, as a tool: the agent decides to start it; the workflow guarantees the process. “Workflows can’t use LLMs.” Key distinction. What is a deterministic workflow?One where the same input always follows the same path of steps. LLM outputs inside steps can vary, but the structure doesn’t. Deterministic here means the control flow is fixed by code: given the same inputs and step outputs, the same steps run in the same order. This is what makes replay, resume and debugging possible: the engine can re-run from a snapshot and know which step is next. LLM outputs inside steps are still non-deterministic, so steps must validate their outputs and be safe to re-run. Temporal-style engines require workflow code to be deterministic so they can replay history; Mastra persists step results in snapshots for a similar purpose. Yes: the branch logic is deterministic given the step’s (stored) output; on resume the stored output is reused, not regenerated. “Deterministic means the LLM gives the same answer every time.” Precision. What is a non-deterministic process?A process whose path or result can differ between runs with the same input, like an agent choosing tools, or any LLM sampling at temperature > 0. A non-deterministic process can take different paths or produce different results for the same input: an agent deciding tools, sampling at temperature > 0, timing-dependent concurrency, external data that changes. Non-determinism isn’t bad, but it must be contained: record outputs so re-runs don’t re-decide, validate results, and bound behaviour with limits. Asking an agent the same question twice may produce 2 searches one time and 3 the next. Fix what you can (temperature 0, seeds, fakes), test properties (valid schema, cites a source, under N steps) rather than exact strings, and evaluate on sets of runs. “Non-deterministic means random and useless.” Precision. What are workflow steps?Units of work with a defined input, output and execute function: validate, call an LLM, write to the DB. In Mastra: createStep({ id, inputSchema, outputSchema, execute }). A step is the smallest unit the engine tracks: it has an id, an input schema, an output schema, and an execute function; optionally suspend/resume schemas and retry settings. The engine validates input, runs execute, validates output, and stores the result in the run snapshot. Good steps are small enough to retry cheaply, large enough to be meaningful, and idempotent. createStep({ id: 'write-lesson', retries: 2, inputSchema: LessonItem, outputSchema: z.object({ moduleNo, lessonNo }), execute }). One logical action with one side effect (one LLM call + one write), so a retry repeats little and is safe. “Steps are just functions; size doesn’t matter.” Basics. What is sequential execution?Running steps one after another, each receiving the previous step’s output. Sequential steps form a chain where each consumes the previous output; total time is the sum. Use it for real dependencies (outline before lessons, validation before charging). Mastra: .then(a).then(b). prepare → outline → approve: each needs the previous result. Carry it through outputs, use .map() to combine, read an earlier step with getStepResultAsync, or use workflow state. “Sequential is always slower, so avoid it.” Basics. What is parallel execution?Running independent steps at the same time and continuing when all finish; total time is the slowest step instead of the sum. Independent steps start together and the workflow continues when all complete; total time ≈ the slowest step. In Mastra, .parallel([a, b]) outputs an object keyed by step id; .foreach(step, { concurrency: n }) runs one step per array item with a cap. If any parallel step throws, the block fails, so catch inside steps when partial success is acceptable. Generating summaries for 3 modules in parallel takes ~1 call’s time instead of 3. Provider rate limits, DB pool size, memory, and cost spikes. “Parallel steps share variables safely.” (They should communicate through outputs, not shared mutable state.) Basics. What is conditional branching?Choosing which step(s) to run based on data, e.g. a short course skips quiz generation. In Mastra, .branch() runs every step whose condition is true. Branching selects steps based on data. In Mastra’s .branch([[condition, step], …]) every condition that’s true runs its step (not just the first), and the output is keyed by step id like parallel. Simple skips can be an if inside a step that returns its input unchanged. Conditions should use stored step outputs so resumed runs follow the same path. 
createWorkflow({ id: 'triage', inputSchema: Ticket, outputSchema: z.any() })
  .then(classify)                                   // { category: 'billing' | 'bug' | 'other' }
  .branch([
    [async ({ inputData }) => inputData.category === 'billing', billingStep],

What is workflow state?Everything about a run so far: input, current status, each step’s status and output, suspend payloads. It’s what you need to continue the run. Run state = input, status (running, suspended, success, failed, canceled, waiting), each step’s status and output, suspend payloads and resume data, plus optional shared workflow state. It’s what makes inspection (“where is this run?”), resume and retry possible. Keep business data in your own tables and keep run state focused on orchestration. Snapshot for a course run: { status: 'suspended', steps: { prepare: success, outline: success, 'approve-outline': suspended { outline } } }. Prefer storing large content in your tables and passing ids, to keep snapshots small. “State lives in memory while the server runs.” Basics. What is workflow persistence?Saving workflow state to durable storage (Postgres, etc.) after steps, so a run survives restarts and can be resumed by any instance. Persistence writes run state to durable storage after steps and on suspend, usually a table keyed by workflow name + run id. Any process with access to the storage can load the run, so a different instance (after a deploy or crash) can resume it. Mastra uses its storage adapters (e.g. Postgres via @mastra/pg), with tables like mastra_workflow_snapshot. A run suspended on Monday is resumed on Wednesday by a different server instance after two deploys. The engine can’t persist; the step’s result may be lost and the step re-run later, so steps must be idempotent. “Persistence means logging.” Basics. What is suspend/resume?Pausing a run inside a step and saving its state (suspend), then continuing it later with new data such as a user’s answer (resume), possibly in a different process. Suspend stops the run at a step and saves its state with a payload explaining what it’s waiting for; nothing runs while suspended (no thread or request held). Resume loads the state, claims the run, and continues the suspended step with resume data (validated by a resume schema). In Mastra the step’s execute runs again from its first line, now with resumeData, so code above the suspend call must be safe to repeat. Step “approve-outline”: if (!resumeData) return await suspend({ outline }). Suspend waits for external input (resume); sleep waits for time (in Mastra the run status is “waiting”). “Suspend keeps a promise waiting in memory.” Basics. What is idempotency in workflows?Designing each step so running it twice has the same effect as once (skip if done, upsert by natural key), because retries, crashes and recovery can re-run steps. How do you prevent duplicate execution?Dedupe at the start (idempotency key → one run per request), claim resumes atomically (suspended → running in one conditional update), make side effects idempotent with unique constraints, and use stable job/run ids. What is a compensating action?A step that undoes the business effect of an earlier completed step when a later one fails, because you can’t roll back across systems: refund a charge, cancel a reservation, delete unpublished drafts. // a tiny saga runner: run steps, and on failure run compensations in reverse
async function runSaga(steps, ctx) {
  const done = [];
  try {
    for (const s of steps) { await s.run(ctx); done.push(s); }
  } catch (err) {
    for (const s of done.reverse()) await s.compensate?.(ctx).catch((e) => log({ evt: 'compensation_failed', step: s.id, e: e.message }));
    throw err;
  }
}

// shared token bucket: every worker awaits a token before calling the provider
class TokenBucket {
  constructor(ratePerMin) { this.capacity = ratePerMin; this.tokens = ratePerMin; this.refillMs = 60000 / ratePerMin; this.last = Date.now(); }
  async take() {
    for (;;) {
      const now = Date.now();
      this.tokens = Math.min(this.capacity, this.tokens + (now - this.last) / this.refillMs); this.last = now;
      if (this.tokens >= 1) { this.tokens -= 1; return; }
      await new Promise((r) => setTimeout(r, this.refillMs));
    }
  }
}

If RAG already retrieves relevant information, why can an LLM still hallucinate? Retrieval only puts text in the prompt; it doesn’t force the model to use it correctly. The model can miss the right sentence in a long context, combine facts wrongly, prefer its training knowledge, or fill gaps when retrieval returned something related but not the answer. Retrieval supplies evidence; it doesn’t control generation. The model still generates token by token from everything it knows, so it can ignore, misread or extend the evidence. Failure points: the retrieved text is related but not the answer; the answer is split across chunks; conflicting sources; long noisy context; the model’s prior knowledge pulling against the context; or instructions that don’t demand grounding. That’s why RAG systems add citations, not-found paths and faithfulness checks. Generation is still next-token prediction over everything in the context plus what the model learned. Nothing in the architecture prevents an unsupported token. Context says “refund window: 30 days for monthly plans”. User asks about annual plans. The model answers “30 days” (pattern-matched) though annual isn’t mentioned. Better retrieval and reranking, strict grounding rules with citations, a not-found path, low temperature, faithfulness checks. “RAG eliminates hallucination.” Understanding RAG’s limits. If increasing top-K improves retrieval recall, why might it reduce answer quality? More chunks also means more irrelevant text: the signal gets diluted, models attend less to facts in the middle of long contexts, near-duplicates crowd the window, cost and latency rise, and conflicting passages confuse the answer. Recall@k measures whether the right chunk is somewhere in the context. Answer quality depends on whether the model finds and uses it amid everything else. Large k adds near-topic but irrelevant chunks, near-duplicates, conflicting statements and more tokens: the signal-to-noise ratio drops, cost and latency rise, and facts in the middle of long contexts are used less reliably. Recall measures whether the answer is somewhere in the context; answer quality depends on whether the model finds and uses it. k = 3: right chunk missing 20% of the time. k = 20: right chunk present 98% of the time, but the model picks a similar wrong chunk’s number 10% of the time. Retrieve 20, rerank to 5: both problems shrink. Retrieve wide (top 50) for recall, rerank, and send narrow (top 5) for precision. “More context is always better.” Precision vs recall reasoning. If an agent can perform a task autonomously, why would you introduce a workflow?For predictability and durability: a workflow gives a fixed order, per-step retries, persisted state that survives restarts, human approval points, known cost, and easy auditing. An agent may skip steps, loop, or take a different path each run. Autonomy is a cost when the process is known. Workflows give guarantees agents don’t: every required step runs in order (approval before generation), state survives restarts, each step retries independently, costs are predictable, behaviour is testable, and every run is auditable. Use agents inside steps that truly need judgement.Course generation must always outline → approve → generate → publish; an agent might generate lessons before approval. Course generation: the workflow controls outline → approval → lessons; a research agent inside the “gather sources” step decides which searches to run. “Agents are always better because they’re smarter.”Architecture judgement. If you can use a larger LLM for every operation, why would you ever use a smaller model?Cost, latency and rate limits. Many tasks (classification, routing, extraction, rewriting a query) are easy enough that a small model is as accurate on your eval set at a fraction of the cost and time. Use the big model where it measurably matters. Bigger models cost more per token, are slower (higher time to first token and generation time), hit rate limits sooner, and for many tasks give no measurable improvement. Smaller models are good enough for classification, routing, extraction, rewriting and many summaries, especially with good prompts or fine-tuning. Routing tasks to the cheapest model that passes your eval saves money and latency at scale.A router classifying 1M messages a month on a large model can cost many times more than the same accuracy on a small one, and it adds latency before every answer. Run the same eval set on both and compare quality, latency and cost; check the error cases. “Smaller models are always worse.” Cost-aware engineering. If a workflow supports retries, why do you still need idempotency? Because a retry re-runs a step whose side effects may already have happened: the step can fail after writing to the DB or calling an API but before its success was recorded. Without idempotency, the retry duplicates lessons, charges or emails. Retries re-run work; idempotency makes re-running safe. A step can fail after doing its side effect (row inserted, email sent, card charged) but before the engine records success, or a crash can lose the success record. Without idempotency the retry repeats the effect. The two are complementary: retries give availability, idempotency gives correctness. Crash timeline: insert lesson 7 → process dies → snapshot still says “lesson 7 not done” → recovery re-runs → second insert. Insert lesson 7 → network blip on the snapshot write → retry → second lesson 7, unless the insert is ON CONFLICT DO NOTHING on (course, module, lesson). Unique keys + upserts, “skip if done” checks, idempotency keys on external calls. “If the engine retries, duplicates can’t happen.” Distributed-systems thinking. If you store conversation history in a database, why might you still need a summarization mechanism?Storage isn’t the limit; the prompt is. Long histories exceed the context window, cost more on every turn, and dilute attention. Summarising older turns keeps the important facts in a few hundred tokens. Storing history solves persistence, not the prompt size problem. Every turn must fit the context window and you pay for every token sent. Long conversations exceed limits, raise cost per turn, slow responses, and bury important early facts. Summaries (or extracted memories) keep the essential information in a small, stable budget while the full history stays in the database for display. A 200-message support chat: sending all of it costs ~30K tokens per turn; a 500-token summary + last 10 messages keeps context and cost bounded.DocMind sends the last 8 messages; older context is simply dropped today. Names, ids, decisions, open questions and user preferences; test that answers relying on early facts still work. “Just send everything; context windows are huge now.” Context management. If embeddings represent semantic meaning, why can keyword search sometimes produce better results?Embeddings compress meaning and blur exact tokens: product codes, error ids, names, numbers and rare jargon get mapped near “similar-looking” things. Keyword search matches the exact string, and BM25 weights rare terms highly. Embeddings capture general meaning and blur exact tokens, rare words and numbers: product codes, error ids, names, versions, legal clause numbers. Keyword search matches exact strings and weights rare terms heavily (IDF), so for such queries it’s more precise. Embedding models may also never have seen your domain’s new terms. Hybrid search uses both.“E1234” vs “E1243” are almost identical to an embedding model and completely different to a support engineer. Run an eval with exact-term questions (codes, names): compare recall@5 for vector-only, BM25-only and hybrid. “Keyword search is outdated now that we have embeddings.” Retrieval depth. If an LLM generates valid JSON, why should you still validate it?Valid syntax isn’t valid data: wrong types, missing fields, out-of-range values, duplicate options, an answer index that doesn’t exist, ids that don’t belong to the user, or injected content. The model is an untrusted client. JSON validity only guarantees syntax. The data can still have missing or extra fields, wrong types, out-of-range values, inconsistent cross-field relations, ids that don’t exist or belong to someone else, injected content, or plausible but wrong facts. Validation with a schema plus business checks is what makes model output safe to store or act on. { "correctIndex": 4, "options": ["A","B","C","D"] } is valid JSON and an invalid quiz.DocMind’s quiz checks “options all different” and correctIndex 0–3 with Zod, and shuffles because positions were skewed even when valid. It reduces shape errors, but not semantic or business-rule errors. “Valid JSON means valid data.” Defensive design. If your API has authentication, why do you still need authorization?Authentication tells you who is calling; it says nothing about whether this user may touch this object. Without authorization any logged-in user can change an id and read someone else’s data (IDOR). Authentication answers who; authorization answers what that identity may access. Every authenticated user can send any id, so without authorization checks on each resource, users can read or modify others’ data (IDOR). Authorization must be enforced server-side in every query and tool, including background jobs and vector search. Logged-in Bob changes /documents/41 to /42 and reads Alice’s file if the query is WHERE id = $1 only. For every endpoint, call it with user B’s token on user A’s resource and expect 404/403. “Logged-in users are trusted.” Classic red-flag check. If your code works locally, what could prevent it from working in production?Different environment variables and secrets, proxies (trust proxy, IPs, buffering of SSE), CORS origins, timeouts and memory limits, cold starts/sleeping instances, network and DNS differences, data volume, concurrency and race conditions, different Node or OS versions, rate limits, and shared resources (a queue prefix pointing at the wrong environment). Production differs in configuration (env vars, secrets, URLs, feature flags), infrastructure (proxies, load balancers, TLS, timeouts, buffering), scale (data volume, concurrency, race conditions), resources (memory/CPU limits, sleeping instances), dependencies (real provider limits, regions, DNS), data (unexpected inputs, legacy rows), and multiple instances (in-memory state not shared). Most “works locally” bugs come from one of these. An in-memory rate limiter works locally with one process; in production with 3 instances, each has its own counter.All real in DocMind: Render’s 3 proxy hops, BULLMQ_PREFIX copied from .env making production share the laptop’s queue, a hotspot DNS refusing the Neon hostname, 512 MB RAM driving the 10 MB upload cap. Staging that mirrors production, config validated at startup, infrastructure as code, and testing behind a real proxy. “If it works locally, it’s a production bug in the platform.” Production awareness. If you can solve a problem with a single LLM call, why would you introduce an agent?Usually you wouldn’t. Add an agent only when the steps depend on intermediate results you can’t know in advance (which query to search, whether to search again, which tool), and accept the extra latency, cost and testing burden. An agent adds latency (multiple calls), cost, non-determinism and new failure modes. It’s justified only when the steps depend on intermediate results the code can’t know in advance (which source to search, whether to search again, which tool fits). If one call (or a fixed pipeline) solves the task with good quality, it’s the better engineering choice. Summarising a given text: one call. Answering questions over a user’s varied sources where the right source and query vary: maybe an agent. Compare the simple pipeline and the agent on the same eval set: quality, latency, cost. “Agents are always better.” Restraint. If you can execute 20 LLM calls in parallel, why might you deliberately limit concurrency?Provider rate limits (requests and tokens per minute) turn bursts into 429 storms; your DB pool and memory have limits; cost spikes; and one tenant shouldn’t starve others. A cap gives steady throughput with fewer failures. Unbounded parallelism turns into 429 storms (requests/tokens-per-minute limits), more retries (making it slower overall), DB pool exhaustion, memory spikes, cost spikes, and unfairness (one user’s batch starving others). A concurrency cap matched to limits gives the highest sustained throughput and predictable behaviour. 20 parallel calls with a 10-RPM limit: half fail immediately, retries collide; with concurrency 3 and a token bucket, all succeed steadily. From provider limits and observed latency (throughput ≈ concurrency / latency), then tune while watching 429 rates. “More parallel is always faster.” Systems thinking. If a document is already embedded, what happens when its original content changes?Its chunks and vectors become stale: search returns old text and answers cite outdated facts. You must detect changes (hash/updated_at), re-extract, re-chunk and re-embed (only changed parts if possible), atomically replace the old chunks, and invalidate caches. Stale chunks and vectors keep representing the old content, so search returns outdated text and answers cite it. You need change detection (hash, updated_at, webhooks from the source), re-extraction and re-chunking, re-embedding (ideally only changed chunks), atomic replacement of the old chunks, cache invalidation, and versioning if you must show which version an answer used. A policy PDF updated from 30 to 14 days refund: until re-ingested, the bot keeps saying 30 days. Hash each chunk’s text; on re-ingest, embed only chunks whose hash isn’t already stored. “Embeddings update automatically.” Data lifecycle. If you use a vector database, why might you still need relational database queries?Ownership and permissions, joins (chunk → document → user), counts and lists (“which documents do I have?”), exact filters, transactions, status tracking, billing and history are relational problems. Similarity search answers only “what’s similar to this”. Vector search answers one question: which items are similar to this vector. Everything else in an application is relational: who owns what, permissions and sharing, document status, lists and counts, filters by date or type, joins to users and billing, transactions for consistent updates, audit and history. Many questions users ask (“which files do I have?”, “how many contracts expire this month?”) are SQL questions, not similarity questions. DocMind’s listDocuments and the 409-on-processing check are pure SQL.DocMind’s listDocuments exists because “which files do I have?” can’t be answered by chunk search. It favours keeping vectors in the relational database (pgvector) unless scale demands otherwise. “A vector DB replaces the relational DB.” Right tool for the job. If a user approves a workflow step, how do you ensure the approval cannot be reused by another user?Bind the pending approval to the run’s owner and check it against the authenticated user (from the token, not the request); claim it atomically once (conditional UPDATE … WHERE user_id AND status = 'pending'); include the exact action in what’s approved; expire it; and return 404/409 otherwise. Approvals are capabilities: whoever can submit one can trigger an action. Bind each pending approval to the run owner (and tenant), check the authenticated user (from the token, not a request field) matches, make the approval single-use with an atomic claim, scope it to the exact action shown (store the validated arguments with the pending record), expire it, and audit who approved what. Unknown or foreign approval ids return 404. 
UPDATE pending_approvals SET status = 'approved', approved_at = now()
WHERE id = $1 AND user_id = $2 AND status = 'pending' AND expires_at > now()
RETURNING action, args;   -- 0 rows → 404/409, nothing executes

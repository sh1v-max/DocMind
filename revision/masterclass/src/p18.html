Pattern for all 15: “Because X only solves part A; part B fails when … ; so we also need Y, for example …”. Name the mechanism, give a concrete failure, then the fix.
If RAG already retrieves relevant information, why can an LLM still hallucinate?Retrieval only puts text in the prompt; it doesn’t force the model to use it correctly. The model can miss the right sentence in a long context, combine facts wrongly, prefer its training knowledge, or fill gaps when retrieval returned something related but not the answer.Generation is still next-token prediction over everything in the context plus what the model learned. Nothing in the architecture prevents an unsupported token.Context says “refund window: 30 days for monthly plans”. User asks about annual plans. The model answers “30 days” (pattern-matched) though annual isn’t mentioned.Better retrieval and reranking, strict grounding rules with citations, a not-found path, low temperature, faithfulness checks.“RAG eliminates hallucination.”Understanding RAG’s limits. If increasing top-K improves retrieval recall, why might it reduce answer quality?More chunks also means more irrelevant text: the signal gets diluted, models attend less to facts in the middle of long contexts, near-duplicates crowd the window, cost and latency rise, and conflicting passages confuse the answer.Recall measures whether the answer is somewhere in the context; answer quality depends on whether the model finds and uses it.Retrieve wide (top 50) for recall, rerank, and send narrow (top 5) for precision.“More context is always better.”Precision vs recall reasoning. If an agent can perform a task autonomously, why would you introduce a workflow?For predictability and durability: a workflow gives a fixed order, per-step retries, persisted state that survives restarts, human approval points, known cost, and easy auditing. An agent may skip steps, loop, or take a different path each run.Course generation must always outline → approve → generate → publish; an agent might generate lessons before approval.“Agents are always better because they’re smarter.”Architecture judgement. If you can use a larger LLM for every operation, why would you ever use a smaller model?Cost, latency and rate limits. Many tasks (classification, routing, extraction, rewriting a query) are easy enough that a small model is as accurate on your eval set at a fraction of the cost and time. Use the big model where it measurably matters.A router classifying 1M messages a month on a large model can cost many times more than the same accuracy on a small one, and it adds latency before every answer.Cost-aware engineering. If a workflow supports retries, why do you still need idempotency?Because a retry re-runs a step whose side effects may already have happened: the step can fail after writing to the DB or calling an API but before its success was recorded. Without idempotency, the retry duplicates lessons, charges or emails.Crash timeline: insert lesson 7 → process dies → snapshot still says “lesson 7 not done” → recovery re-runs → second insert.Unique keys + upserts, “skip if done” checks, idempotency keys on external calls.Distributed-systems thinking. If you store conversation history in a database, why might you still need a summarization mechanism?Storage isn’t the limit; the prompt is. Long histories exceed the context window, cost more on every turn, and dilute attention. Summarising older turns keeps the important facts in a few hundred tokens.DocMind sends the last 8 messages; older context is simply dropped today.Context management. If embeddings represent semantic meaning, why can keyword search sometimes produce better results?Embeddings compress meaning and blur exact tokens: product codes, error ids, names, numbers and rare jargon get mapped near “similar-looking” things. Keyword search matches the exact string, and BM25 weights rare terms highly.“E1234” vs “E1243” are almost identical to an embedding model and completely different to a support engineer.Retrieval depth. If an LLM generates valid JSON, why should you still validate it?Valid syntax isn’t valid data: wrong types, missing fields, out-of-range values, duplicate options, an answer index that doesn’t exist, ids that don’t belong to the user, or injected content. The model is an untrusted client.DocMind’s quiz checks “options all different” and correctIndex 0–3 with Zod, and shuffles because positions were skewed even when valid.Defensive design. If your API has authentication, why do you still need authorization?Authentication tells you who is calling; it says nothing about whether this user may touch this object. Without authorization any logged-in user can change an id and read someone else’s data (IDOR).Classic red-flag check. If your code works locally, what could prevent it from working in production?Different environment variables and secrets, proxies (trust proxy, IPs, buffering of SSE), CORS origins, timeouts and memory limits, cold starts/sleeping instances, network and DNS differences, data volume, concurrency and race conditions, different Node or OS versions, rate limits, and shared resources (a queue prefix pointing at the wrong environment).All real in DocMind: Render’s 3 proxy hops, BULLMQ_PREFIX copied from .env making production share the laptop’s queue, a hotspot DNS refusing the Neon hostname, 512 MB RAM driving the 10 MB upload cap.Production awareness. If you can solve a problem with a single LLM call, why would you introduce an agent?Usually you wouldn’t. Add an agent only when the steps depend on intermediate results you can’t know in advance (which query to search, whether to search again, which tool), and accept the extra latency, cost and testing burden.Restraint. If you can execute 20 LLM calls in parallel, why might you deliberately limit concurrency?Provider rate limits (requests and tokens per minute) turn bursts into 429 storms; your DB pool and memory have limits; cost spikes; and one tenant shouldn’t starve others. A cap gives steady throughput with fewer failures.Systems thinking. If a document is already embedded, what happens when its original content changes?Its chunks and vectors become stale: search returns old text and answers cite outdated facts. You must detect changes (hash/updated_at), re-extract, re-chunk and re-embed (only changed parts if possible), atomically replace the old chunks, and invalidate caches.Data lifecycle. If you use a vector database, why might you still need relational database queries?Ownership and permissions, joins (chunk → document → user), counts and lists (“which documents do I have?”), exact filters, transactions, status tracking, billing and history are relational problems. Similarity search answers only “what’s similar to this”.DocMind’s listDocuments exists because “which files do I have?” can’t be answered by chunk search.Right tool for the job. If a user approves a workflow step, how do you ensure the approval cannot be reused by another user?Bind the pending approval to the run’s owner and check it against the authenticated user (from the token, not the request); claim it atomically once (conditional UPDATE … WHERE user_id AND status = 'pending'); include the exact action in what’s approved; expire it; and return 404/409 otherwise.Security depth.

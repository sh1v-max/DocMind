4.ALessons

A relational database stores data in tables (relations) of rows with typed columns. Tables connect through keys, and SQL describes what data you want, not how to fetch it. Structure plus constraints means the database itself refuses bad data (duplicate emails, orphaned rows, nulls where a value is required), and you can ask questions nobody planned for with joins and aggregates.

A schema for a document-chat + quiz app. Read every line; each constraint prevents a real bug.

CREATE EXTENSION IF NOT EXISTS vector;

CREATE TABLE users (
  id            uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  email         text UNIQUE,                         -- many NULLs allowed (guests)
  password_hash text,

  created_at    timestamptz NOT NULL DEFAULT now()
);

  status      text NOT NULL DEFAULT 'processing' CHECK (status IN ('processing','ready','failed')),
  error       text,
  created_at  timestamptz NOT NULL DEFAULT now(),

);
CREATE INDEX documents_user_created_idx ON documents (user_id, created_at DESC);

DocMind’s real schema is simpler and was created by hand-run SQL on Neon: users, documents (with status + error), chunks (vector(3072), no user_id: ownership comes through the join to documents), chat_messages (its own user_id, because an “All documents” session has document_id = 'all'). There is no sessions table: a session is a session_id shared by message rows. And no foreign keys anywhere, so cleanup relies on code order (delete the document row first, then its chunks). Both are listed as known gaps. Messages are ordered by created_at without an id tiebreak (ISSUES #3).
  • Storing a list in a comma-separated text column instead of a join table.
  • No FK, then “orphan rows” after deletes (DocMind once had 65 orphan chunks).
  • Using timestamp instead of timestamptz.
 A join combines rows from two tables on a condition. GROUP BY collapses rows into groups for aggregates. A window function computes across related rows but keeps every row.

Data used below: users (1 Alex, 2 John, 3 Mira); documents (1 Alex “AI Basics”, 2 Alex “RAG Guide”, 3 John “Node.js Guide”).

-- INNER JOIN: only matching pairs → 3 rows (Mira disappears)
SELECT u.name, d.title FROM users u JOIN documents d ON d.user_id = u.id;

-- LEFT JOIN: every user, NULLs where no match → 4 rows (Mira, NULL)
SELECT u.name, d.title FROM users u LEFT JOIN documents d ON d.user_id = u.id;

-- count per user, including zero (count(d.id) ignores NULLs; count(*) would say 1 for Mira)
SELECT u.name, count(d.id) AS docs FROM users u LEFT JOIN documents d ON d.user_id = u.id
GROUP BY u.id, u.name ORDER BY docs DESC;

-- WHERE filters rows before grouping; HAVING filters groups after
SELECT user_id, count(*) FROM documents WHERE status = 'ready' GROUP BY user_id HAVING count(*) >= 2;

-- window: latest document per user without losing the row
SELECT * FROM (
  SELECT d.*, row_number() OVER (PARTITION BY user_id ORDER BY created_at DESC) AS rn FROM documents d
) t WHERE rn = 1;

-- CTE: name a step, read top to bottom
WITH per_user AS (SELECT user_id, count(*) AS n FROM documents GROUP BY user_id)
SELECT u.name, p.n FROM per_user p JOIN users u ON u.id = p.user_id WHERE p.n = (SELECT max(n) FROM per_user);
  • LEFT JOIN then WHERE d.status = 'ready': the WHERE removes the NULL rows and silently turns it into an inner join. Put the condition in the ON.
  • Selecting columns that aren’t grouped or aggregated.
 An index is a separate data structure (by default a B-tree) that keeps column values sorted with pointers to rows, so the database can find matches without reading the whole table.

A B-tree is a shallow, balanced tree: finding a key in a million rows takes about 20 comparisons and a few page reads instead of reading every page. Composite index (user_id, created_at DESC) is sorted by user, then by date inside each user: perfect for “this user’s latest documents”, useless for “all documents from yesterday” (leftmost-prefix rule). Every INSERT/UPDATE/DELETE must also update every index, and indexes take disk and memory.

 Index foreign keys you filter or join on (Postgres does not create them automatically), columns in frequent WHERE/ORDER BY, and unique business keys. Vector columns need special indexes (HNSW/IVFFlat, Phase 6).
  • Indexing every column “just in case”.
  • A function on the column defeats the index: WHERE lower(email) = $1 needs an expression index on lower(email).
  • Expecting an index on a low-selectivity column (a boolean) to help.
 A transaction groups statements so they succeed or fail as one unit. ACID: Atomicity (all or nothing), Consistency (constraints hold), Isolation (concurrent transactions don’t see each other’s half-done work), Durability (committed = survives a crash, via the write-ahead log).

Deadlock: T1 locks row A then wants B; T2 locks B then wants A. Postgres detects the cycle (after deadlock_timeout, 1 s by default) and aborts one with an error. Prevent by locking in a consistent order and keeping transactions short.

-- lost update fixed with an atomic statement instead of read-then-write
UPDATE users SET credits = credits - 1 WHERE id = $1 AND credits > 0 RETURNING credits;
-- or lock the row you will modify
BEGIN; SELECT credits FROM users WHERE id = $1 FOR UPDATE; ... COMMIT;
 A bank transfer: debit and credit are one envelope. Either both slips are in the envelope or it isn’t sent. Publishing a generated course: insert the course row, its modules and lessons, and mark it published in one transaction, so readers never see half a course.
  • Calling an LLM inside an open transaction: a 10-second transaction holds locks and a pooled connection the whole time. Generate first, then write in a short transaction.
  • Using the pool directly (pool.query) for BEGIN/COMMIT: each call may use a different connection. Check out one client.
 A pool keeps a set of open database connections and lends them to requests, instead of opening a new connection per query. Opening a Postgres connection costs a TCP + TLS handshake + authentication + a backend process on the server (tens of milliseconds, several MB of server memory). Postgres also has a hard max_connections.
  1. pool.query() borrows an idle client, runs the query, returns it automatically.
  2. pool.connect() gives you a client for a transaction; you must release() it.
  3. When all clients are busy, new requests wait in a queue (connectionTimeoutMillis decides how long).
  4. Serverless or many app instances → use a server-side pooler (PgBouncer, Neon’s pooled endpoint) so 50 instances × 10 = 500 app connections share far fewer real ones.
 A taxi stand: cars wait at the stand and passengers take the next free one, instead of each passenger buying a car. 4.1Database fundamentals

What is a relational database?A database that stores data in tables of rows and typed columns, links tables through keys, enforces constraints, and is queried with SQL. Postgres, MySQL, SQLite. The relational model (E. F. Codd, 1970) stores facts as rows in tables; each table has a fixed set of typed columns; relationships are expressed by storing keys, not pointers; and SQL lets you combine tables with joins at query time. The database enforces integrity with constraints and gives transactions with ACID guarantees. Because queries are declarative, the planner chooses how to execute them (which index, which join algorithm). An AI app: users, documents (user_id), chunks (document_id), messages (conversation_id). “All ready documents of user 7 with their chunk counts” is one SQL query, no code loops. PostgreSQL (rich types: JSONB, arrays, extensions like pgvector), MySQL (widely hosted, simpler feature set), SQLite (embedded in one file, no server). “A relational database is any database with tables.” Constraints, joins and transactions are the point. Basics. What is a non-relational database?A database that doesn’t use the table-and-join model: document stores (MongoDB), key-value (Redis, DynamoDB), wide-column (Cassandra), graph (Neo4j), and dedicated vector stores (Pinecone, Qdrant). Non-relational (NoSQL) databases organise data by access pattern instead of normalised tables: document stores keep nested JSON per record (MongoDB), key-value stores map keys to blobs (Redis, DynamoDB), wide-column stores spread rows across many nodes (Cassandra), graph databases store nodes and edges (Neo4j), and vector databases index embeddings (Qdrant, Pinecone). They often trade joins and multi-record transactions for flexible schemas and horizontal scale. A MongoDB document for a blog post can embed its comments; reading the post is one lookup, but “all comments by user X across posts” is harder. When data is read and written as self-contained aggregates (a product with its variants), the schema varies per record, and cross-record joins are rare. “NoSQL means no schema.” The schema moves into application code. Breadth. What’s the difference between SQL and NoSQL?SQL databases have a fixed schema, joins and strong transactions; good for related data with integrity rules. NoSQL trades some of that for flexible schemas, simple access patterns and easy horizontal scaling.

The line is blurry now: Postgres has JSONB and vectors; MongoDB has multi-document transactions. Pick by access patterns and integrity needs.

 Users, documents, permissions and billing → SQL (relations, transactions). A cache of LLM responses → Redis. Event logs at huge write rates → a wide-column or log store.Postgres: users, documents, permissions and chats are relational, I need transactions, and pgvector keeps vectors next to the data they belong to. “SQL can’t scale.” Postgres handles very large workloads with indexes, read replicas and partitioning; the decision is about data shape and consistency needs. Reasoned choice. What are tables, rows and columns?A table is a set of records of one kind; a row is one record; a column is one typed attribute every row has. A table defines an entity type and its attributes (the schema): column names, types (text, integer, timestamptz, uuid, jsonb, vector) and constraints. Each row is one instance with a value (or NULL) for every column. Rows have no inherent order; ORDER BY is required for a guaranteed order. Good table design: one entity per table, one fact per column. documents: columns id (uuid), user_id (uuid), filename (text), status (text CHECK in processing/ready/failed), created_at (timestamptz). Each upload is a row. The planner may read from different indexes or parallel workers, and updates move rows physically; SQL guarantees no order unless you ask. “Rows come back in insertion order.” Basics. What is a primary key?A column (or set) that uniquely identifies each row; it’s NOT NULL and unique, and gets an index automatically. The primary key is the row’s identity: unique, never NULL, ideally never changes. Postgres creates a unique B-tree index for it automatically. Choices: natural keys (an email) change and leak meaning; surrogate keys (identity integers or UUIDs) are stable. Composite primary keys fit join tables (PRIMARY KEY (conversation_id, document_id)). id uuid PRIMARY KEY DEFAULT gen_random_uuid() lets the server or client generate ids without a round trip.Serial/identity is small and ordered; UUIDs can be generated anywhere and don’t reveal counts or allow guessing neighbours. UUIDv7 gives both uniqueness and time ordering. Using email as the primary key and then needing to let users change their email. Basics. What is a foreign key?A column that must match a primary (or unique) key in another table, so you can’t reference a row that doesn’t exist. ON DELETE CASCADE / SET NULL / RESTRICT decides what happens to children. A foreign key constraint makes the database check, on every insert/update of the child and every delete/update of the parent, that the referenced row exists. ON DELETE behaviour: CASCADE (delete children), SET NULL, RESTRICT/NO ACTION (block). It turns “orphan rows” from a bug you discover months later into an immediate error. Postgres does not automatically index the referencing column; add an index if you join or delete by it.

Sharded or very write-heavy systems sometimes enforce relationships in code; for a normal app it’s usually a mistake. “Foreign keys slow everything down, so skip them.” Integrity. What are unique constraints?A rule that no two rows share the same value (or combination) in given columns. Enforced by a unique index, so it also prevents race-condition duplicates. A UNIQUE constraint (backed by a unique index) guarantees no two rows have equal values in the listed columns. It’s the only reliable way to prevent duplicates under concurrency: two transactions inserting the same email at the same moment can’t both succeed. NULLs are distinct by default in Postgres (many NULLs allowed), unless declared NULLS NOT DISTINCT (Postgres 15+). Partial unique indexes enforce uniqueness for a subset (WHERE deleted_at IS NULL). UNIQUE (user_id, sha256) stops the same user uploading the same file twice; insert with ON CONFLICT (user_id, sha256) DO NOTHING RETURNING *.DocMind detects duplicate emails through the UNIQUE constraint (Postgres error 23505 → 409), not by checking first. Catch Postgres error code 23505 (unique_violation) and return 409 Conflict with a friendly message. Checking “does it exist?” in code before inserting. Practical integrity. What is database normalization?Organising tables so each fact is stored once, removing duplication that causes update anomalies, by splitting data into related tables. Normalisation removes redundancy by splitting data so each fact is stored in exactly one place. That prevents update anomalies (changing a user’s email in one row but not in another copy), insert anomalies (can’t store a product until it has an order) and delete anomalies (deleting the last order deletes the product’s info). The cost is more joins; the benefit is consistency. Storing owner_email on every document means changing an email requires updating many rows; storing only user_id keeps one source of truth. Usually to 3NF, then denormalise deliberately where measured read performance needs it. “Normalisation means splitting everything into as many tables as possible.” Design basics. Explain 1NF, 2NF and 3NF.1NF: atomic values, no repeating groups. 2NF: 1NF and every non-key column depends on the whole key (matters for composite keys). 3NF: 2NF and no non-key column depends on another non-key column. Put simply: 1NF: each cell holds one value and there are no repeating column groups (tag1, tag2…). 2NF: in a table with a composite key, every non-key column depends on the whole key, not part of it. 3NF: non-key columns depend only on the key, not on other non-key columns (“the key, the whole key, and nothing but the key”).1NF violation: tags = 'ai,rag'. 2NF violation: in (order_id, product_id) → product_name, the name depends only on product_id. 3NF violation: documents.owner_email (depends on user_id, not on the document). A tags table and a document_tags(document_id, tag_id) join table (or, pragmatically in Postgres, a text[] column with a GIN index if tags are just labels). Reciting definitions without an example. Design vocabulary. What is denormalization?Deliberately duplicating data to make reads faster or simpler, accepting the cost of keeping copies in sync, e.g. storing message_count on a conversation or the filename on each chunk. Denormalisation adds redundant data on purpose: counters (message_count), copies of frequently joined fields, precomputed aggregates, or materialised views. It speeds up reads and simplifies queries but adds write work and the risk of copies drifting. Keep copies correct with transactions, triggers, or periodic recomputation, and document which field is the source of truth. Storing filename on each chunk avoids a join in search results, at the cost of updating chunks if a document is renamed. A stored query result that you refresh (REFRESH MATERIALIZED VIEW); good for expensive analytics that can be slightly stale. “Denormalisation is bad design.” It’s a trade-off. Trade-offs. What is an index?An auxiliary sorted structure (usually a B-tree) that lets the database find rows by a column without scanning the table. Without an index the database reads every row (sequential scan) to find matches. An index is a separate structure, usually a B-tree, storing the indexed column values in sorted order with pointers to rows (TIDs). Other index types: Hash (equality), GIN (arrays, JSONB, full-text), GiST (geometric, ranges), BRIN (huge naturally ordered tables), and pgvector’s HNSW/IVFFlat for vectors. CREATE INDEX documents_user_idx ON documents (user_id); makes “this user’s documents” fast. Usually not: reading most of the table sequentially is cheaper than jumping through the index, so the planner chooses a seq scan. “Indexes store copies of whole rows.” (Only the indexed columns, plus INCLUDE columns if specified.) Basics. How do indexes improve query performance?The planner can jump to matching keys in O(log n) and read only those rows, and can return rows already in index order for ORDER BY and LIMIT, avoiding a sort. A B-tree index lets the planner find the first matching key in a few page reads (the tree is shallow), then walk the sorted leaves for ranges, and fetch the matching rows. It can also return rows already sorted (no Sort step for ORDER BY + LIMIT), satisfy queries entirely from the index (index-only scans), and enforce uniqueness. The planner decides using statistics about how many rows will match. Finding 20 recent documents for one user among 10 million rows: with (user_id, created_at DESC) the database reads ~20 index entries instead of 10 million rows. EXPLAIN ANALYZE: look for Index Scan / Index Only Scan / Bitmap Index Scan nodes and the actual time. “Adding an index always makes queries faster.” Mechanism. Can indexes negatively affect performance?Yes: every write updates every index, they use disk and cache memory, and too many can slow inserts badly. Unused indexes are pure cost. Each index must be updated on every insert, on updates of indexed columns, and on deletes (vacuum), so write-heavy tables slow down with many indexes. Indexes consume disk and shared memory, compete for cache, and building them on large tables takes time and can block writes unless created CONCURRENTLY. Unused or duplicate indexes are pure overhead. A chunks table with an HNSW index: bulk inserting 100,000 embeddings is much slower than without it, so large backfills often build the index after loading. pg_stat_user_indexes.idx_scan near 0 over a representative period. “Indexes only cost disk space.” Trade-offs. What is a composite index?An index on several columns, sorted by the first, then the second within it, etc. It serves queries that filter on a leftmost prefix of its columns.(user_id, created_at) serves WHERE user_id = $1 ORDER BY created_at, but not WHERE created_at > $1 alone.Practical indexing. What is a database transaction?A group of statements executed as one unit: all commit or all roll back. A transaction groups statements between BEGIN and COMMIT so the database applies all or none of them. If any statement fails or you ROLLBACK, earlier changes in the transaction are undone. Other sessions don’t see the uncommitted changes. Postgres runs every single statement in its own implicit transaction if you don’t open one. Publishing a course: insert modules, insert lessons, set course status = published; if any insert fails, nothing is published. A marker inside a transaction you can roll back to without aborting the whole transaction (SAVEPOINT s1; … ROLLBACK TO s1;). “Each query in my function is automatically in one transaction.” Not unless you use one client and BEGIN/COMMIT. Basics. Explain ACID properties.Atomicity: all or nothing. Consistency: constraints hold before and after. Isolation: concurrent transactions behave as if separate (to a chosen degree). Durability: committed data survives crashes. Atomicity: a transaction’s changes all happen or none do (implemented with the write-ahead log and rollback). Consistency: each transaction moves the database from one valid state to another, respecting constraints. Isolation: concurrent transactions don’t see each other’s intermediate states; the degree depends on the isolation level. Durability: once COMMIT returns, the change survives crashes because the WAL is flushed to disk. Transfer 100 from A to B: two UPDATEs; atomicity means you never lose 100 mid-way; durability means a power cut after COMMIT doesn’t undo it. Isolation and multi-record atomicity (often “eventual consistency” across nodes), in exchange for availability and scale. Confusing ACID’s C with “consistency” in distributed systems (CAP). Vocabulary. What is transaction isolation?How much concurrent transactions can see of each other’s effects. Levels trade correctness for concurrency: read committed (Postgres default), repeatable read, serializable. Read committed: in one transaction, two identical SELECTs can return different results if another transaction committed between them.Two requests read credits = 1, both decide it’s enough, both write 0: one purchase is free. Fix with an atomic UPDATE … WHERE credits > 0, SELECT … FOR UPDATE, or serializable + retry. “Serializable means transactions run one after another.” They run concurrently; the database aborts ones that would break serial equivalence. Concurrency depth. What is a database deadlock?Two transactions each hold a lock the other needs, so neither can proceed. Postgres detects it and aborts one; the app should retry. Prevent with consistent lock order and short transactions. Deadlocks need two or more transactions holding locks and waiting on each other in a cycle. Postgres checks for cycles after deadlock_timeout (1 s by default), aborts one transaction with SQLSTATE 40P01 and lets the other continue. Prevention: lock rows in a consistent order (e.g. by id), keep transactions short, avoid user or network waits inside transactions, and retry the aborted transaction. Two requests transfer money A→B and B→A at the same time: each locks its first account and waits for the second. Locking both rows ordered by id avoids it.

SELECT id FROM accounts WHERE id IN ($1, $2) ORDER BY id FOR UPDATE;   -- consistent lock order

What is connection pooling?Reusing a fixed set of open database connections across requests instead of opening one per query. A connection pool (pg.Pool, PgBouncer, a provider’s pooled endpoint) keeps N open connections. Requests borrow a connection, use it, and return it. When all are busy, requests wait in a queue up to a timeout. Configuration: max size (tune against the server’s max_connections divided by app instances), idle timeout, connection timeout. Server-side poolers in transaction mode let thousands of clients share few backends but break session features (prepared statements, SET, advisory locks across statements). new pg.Pool({ connectionString, max: 10, idleTimeoutMillis: 30000, connectionTimeoutMillis: 5000 }). Postgres uses a process per connection; hundreds of active connections thrash CPU and memory. Throughput usually peaks with a small pool. “Opening a new connection per query is fine.” Basics. Why should database connections be reused?Opening them is slow (TCP, TLS, auth, a server process) and the server allows only a limited number. Reuse cuts latency and protects the database. A new Postgres connection costs a TCP handshake, TLS negotiation, authentication, and a new backend process with its own memory; often 20–100 ms over the internet. Doing that per query multiplies latency and can exceed max_connections under load. Reusing connections also keeps prepared statement caches and server memory warm. Neon or Supabase across regions: a fresh connection can take longer than the query itself. Each instance may open its own connections, so use the provider’s pooled endpoint or an HTTP/WebSocket driver designed for serverless. “Connections are free to open.” Performance reasoning.

4.2PostgreSQL and SQL

Why would you choose PostgreSQL for an AI application?Reliable relational core for users, permissions and chats; JSONB for flexible metadata; pgvector for embeddings next to the data (filters and joins in one query); full-text search for hybrid retrieval; mature hosting and free tiers. One query in DocMind joins chunks to documents, filters by owner and status, and orders by vector distance: something you can’t do in one call if vectors live in a separate system.Hundreds of millions of vectors, very high QPS, or needing features like built-in hybrid ranking at scale: a dedicated vector DB, kept in sync from Postgres. “Postgres can’t do vectors, so you need Pinecone.” Technology judgement. What’s the difference between WHERE and HAVING?WHERE filters rows before grouping and can’t use aggregates. HAVING filters groups after GROUP BY and can. Logical order of a SELECT: FROM/JOIN → WHERE (row filter) → GROUP BY → aggregates computed → HAVING (group filter) → SELECT → ORDER BY → LIMIT. That’s why WHERE can’t use count(*) (groups don’t exist yet) and why filtering rows in WHERE instead of HAVING is more efficient when possible. SELECT user_id, count(*) FROM documents WHERE status = 'ready' GROUP BY user_id HAVING count(*) > 5; No, SELECT is evaluated after WHERE; repeat the expression or use a subquery/CTE. “HAVING is just WHERE for joins.” SQL basics. What’s the difference between INNER JOIN, LEFT JOIN and RIGHT JOIN?INNER keeps only matching pairs. LEFT keeps every left row, with NULLs where the right has no match. RIGHT is the mirror. (FULL keeps both sides.) A join builds rows from pairs of rows that satisfy the ON condition. INNER keeps only matches. LEFT keeps all left rows and fills right columns with NULL when nothing matches. RIGHT is LEFT with the tables swapped (rarely used). FULL keeps unmatched rows from both. The planner executes joins with nested loops, hash joins or merge joins depending on sizes and indexes. “Documents with their owner’s email”: INNER JOIN. “Every user with their document count, including zero”: LEFT JOIN.DocMind’s vector search changed from LEFT JOIN to INNER JOIN documents during auth: a chunk with no document row has no owner, so it must never be returned. A WHERE condition on a right-table column (WHERE d.status = 'ready') removes the NULL rows; move it into the ON clause. “RIGHT JOIN returns the right table only.” SQL basics. What is a subquery?A query nested inside another: in WHERE (IN (SELECT …), EXISTS), in FROM as a derived table, or as a scalar in SELECT. Subqueries can be scalar (one value), row lists for IN/EXISTS, or derived tables in FROM. Correlated subqueries reference the outer row and conceptually run per row (the planner often rewrites them into joins). EXISTS stops at the first match and handles NULLs safely; NOT IN with a subquery that can return NULL returns no rows, a classic bug.
SELECT * FROM users u WHERE NOT EXISTS (SELECT 1 FROM documents d WHERE d.user_id = u.id);
 Prefer NOT EXISTS: x NOT IN (1, NULL) is never true because comparison with NULL is unknown. “Subqueries are always slow.” SQL fluency. What are Common Table Expressions (CTEs)?Named temporary result sets defined with WITH, used to break a complex query into readable steps; WITH RECURSIVE walks hierarchies. WITH name AS (SELECT …) defines a named result usable in the following query, like a variable for a query. Benefits: readability (steps top to bottom), reuse of the same intermediate result, and WITH RECURSIVE for trees and graphs. Since Postgres 12, simple CTEs are inlined (optimised like subqueries) unless marked MATERIALIZED. Data-modifying CTEs (WITH deleted AS (DELETE … RETURNING *)) can chain writes in one statement. 
-- RRF hybrid search reads as three named steps
WITH vec AS (SELECT id, row_number() OVER (ORDER BY embedding <=> $1) r FROM chunks ORDER BY embedding <=> $1 LIMIT 40),
     kw  AS (SELECT id, row_number() OVER (ORDER BY ts_rank_cd(tsv, q) DESC) r FROM chunks, websearch_to_tsquery($2) q WHERE tsv @@ q LIMIT 40)
SELECT id, sum(1.0 / (60 + r)) AS score FROM (SELECT * FROM vec UNION ALL SELECT * FROM kw) u GROUP BY id ORDER BY score DESC LIMIT 6;
 WITH RECURSIVE t AS (SELECT * FROM comments WHERE id = $1 UNION ALL SELECT c.* FROM comments c JOIN t ON c.parent_id = t.id) SELECT * FROM t; “CTEs are temporary tables stored on disk.” Readable SQL. What are aggregate functions?Functions that reduce many rows to one value: count, sum, avg, min, max, string_agg, array_agg, json_agg. Aggregates collapse many rows into one value per group: count(*) counts rows, count(col) counts non-NULLs, sum/avg/min/max ignore NULLs, string_agg/array_agg/json_agg collect values (with ORDER BY inside to control order), and FILTER limits an aggregate to some rows: count(*) FILTER (WHERE status = 'failed'). One query for a dashboard: SELECT count(*) AS total, count(*) FILTER (WHERE status = 'ready') AS ready, avg(chunk_count) FROM documents WHERE user_id = $1; NULL (and count returns 0): use coalesce for display. “count(column) and count(*) are always the same.” Basics. What is GROUP BY?It splits rows into groups with equal values in the given columns so aggregates are computed per group. GROUP BY partitions rows by the listed expressions; each group produces one output row. Every selected column must be grouped or aggregated (Postgres allows other columns of a table when its primary key is grouped). ROLLUP/CUBE/GROUPING SETS produce subtotals. Token cost per user per day: SELECT user_id, date_trunc('day', created_at) d, sum(input_tokens + output_tokens) FROM llm_calls GROUP BY 1, 2; DISTINCT ON in Postgres, or row_number() OVER (PARTITION BY …) and filter rn = 1. Selecting a non-grouped column and expecting “any” value. Basics. What is a window function?A function computed over a set of rows related to the current row (a “window” defined by OVER (PARTITION BY … ORDER BY …)), without collapsing rows: row_number, rank, lag/lead, running sums. The OVER clause defines a window: PARTITION BY splits rows into groups, ORDER BY orders them within the group, and an optional frame (ROWS BETWEEN …) limits which rows count. The function is evaluated per row with access to its window, so rows are not collapsed. Common ones: row_number/rank/dense_rank, lag/lead (previous/next row), running sums, moving averages, ntile.
SELECT user_id, created_at, sum(tokens) OVER (PARTITION BY user_id ORDER BY created_at) AS running_tokens
FROM llm_calls;
 For ties: row_number gives 1,2,3; rank gives 1,1,3; dense_rank gives 1,1,2. “Window functions are the same as GROUP BY.” Intermediate SQL. What’s the difference between UNION and UNION ALL?UNION removes duplicate rows (extra sort/hash work). UNION ALL keeps everything and is faster. Use UNION ALL unless you need dedupe. Both append the results of two SELECTs with the same column count and compatible types. UNION then removes duplicate rows, which needs a sort or hash over all rows; UNION ALL doesn’t. Use UNION ALL when duplicates are impossible or wanted (combining vector and keyword candidates before fusing scores), UNION when you need set semantics. In RRF, a chunk found by both searches must appear twice (once per list) so its two scores add up: that needs UNION ALL. Rows present in both queries, and rows in the first but not the second. “UNION joins tables side by side.” Precision. What does EXPLAIN ANALYZE do?It runs the query and shows the actual plan: each node (Seq Scan, Index Scan, Hash Join, Sort), estimated vs actual rows, loops and timings. Big gaps between estimated and actual rows, or a Seq Scan on a large table, point to the problem.
EXPLAIN (ANALYZE, BUFFERS) SELECT * FROM documents WHERE user_id = '...' ORDER BY created_at DESC LIMIT 20;
-- Limit (actual time=0.03..0.05 rows=20)
--   -> Index Scan using documents_user_created_idx on documents (rows=20)
 A plan showing Seq Scan on chunks (rows=1000000) Filter: document_id = … with 900 ms is a missing index on chunks.document_id.It really executes the query: wrap writes in BEGIN … ROLLBACK. Reading only the estimated cost and ignoring actual rows/time, or running EXPLAIN ANALYZE on a DELETE in production without a transaction. Debugging skill. What are JSON and JSONB in PostgreSQL?JSON stores the text as is; JSONB stores a parsed binary form: faster to query, supports GIN indexes and operators (->, ->>, @>), but doesn’t keep key order or duplicate keys. Use JSONB.
SELECT * FROM messages WHERE metadata @> '{"model": "flash-lite"}';
CREATE INDEX ON messages USING gin (metadata);
 Storing per-message metadata: { "model": "flash-lite", "tokens": { "in": 812, "out": 140 }, "sources": [ … ] } in a metadata jsonb column. When you filter, join or constrain on it frequently, or need types and NOT NULL/foreign keys. Putting everything in one JSONB column to avoid schema design. Postgres features. What is the difference between DELETE, TRUNCATE and DROP?DELETE removes chosen rows (WHERE), fires triggers, is logged per row. TRUNCATE empties the whole table fast. DROP removes the table itself. In Postgres all three are transactional. DELETE removes rows matching WHERE, one by one: fires row triggers, respects foreign keys (cascades), returns RETURNING rows, and leaves dead rows for VACUUM. TRUNCATE removes all rows by swapping in empty storage: much faster, resets identity with RESTART IDENTITY, needs CASCADE when referenced by FKs, doesn’t fire row triggers. DROP removes the table definition, its indexes and data. All three are transactional in Postgres (rollback works inside BEGIN). Clearing a staging table before a nightly import: TRUNCATE. Removing one user’s data: DELETE … WHERE user_id = $1.DocMind’s old step2 learning script DROPs and step3 DELETEs the chunks table; they must never be re-run against the live database. Per-row work, WAL volume, cascades, index updates and locks; delete in batches or partition the table and drop partitions. “TRUNCATE can’t be rolled back.” (In Postgres it can.) Basics. How would you investigate a slow SQL query?Reproduce with real parameters, run EXPLAIN (ANALYZE, BUFFERS), look for sequential scans, bad row estimates, sorts and nested loops over many rows; check indexes and statistics (ANALYZE); check pg_stat_statements for the worst queries; consider rewriting or adding an index; re-measure.

Also rule out non-query causes: waiting for a lock, pool exhaustion, network distance (DocMind: Render in Oregon, Neon in Ohio, ~50–70 ms per query).

 A documents list endpoint went from 40 ms to 2 s after growth: EXPLAIN showed a seq scan + sort on 2M rows; adding (user_id, created_at DESC) brought it back to 3 ms. An extension that records execution counts and total/mean time per normalised query, the fastest way to find which queries cost the most overall. Adding random indexes before reading the plan. Method. What is a migration?A versioned script that changes the database schema (and sometimes data) from one version to the next, stored with the code and applied in order. A migration is one step in the schema’s history: an “up” change (and sometimes a “down” to revert) with an id or timestamp. A migration tool records which steps ran in a table in the database, applies pending ones in order, and refuses to run twice. Data migrations (backfills) are kept separate from schema changes and run in batches. 0004_add_documents_status.sql: ALTER TABLE documents ADD COLUMN status text NOT NULL DEFAULT 'ready'; Commonly yes, as a release step before the new code starts; destructive or long ones are reviewed and run deliberately. “A migration is a backup.” Basics. Why should database schema changes be managed through migrations?They’re reviewable, repeatable on every environment, ordered, tracked (no double application) and tied to the code that needs them. Manual changes drift between environments and get forgotten. Without migrations, environments drift: local, staging and production end up with different columns, and nobody knows which SQL was run where. Migrations make schema changes code-reviewed, versioned with the code that needs them, repeatable for new developers and test databases, and safe to deploy in order (expand → migrate → contract). DocMind hand-ran SQL in the Neon editor and kept it as comments in schema.ts; it works for one person but is listed as debt. Add the new column, write to both, backfill, switch reads, stop writing the old one, drop it later. “I’ll just remember what I changed.” Engineering discipline.

4.3Drizzle ORM

What is an ORM?Object-Relational Mapper: a library that maps tables to code objects and builds queries for you, so you work with typed functions instead of raw SQL strings. An ORM maps tables to objects and rows to instances, generates SQL from method calls, and often manages relations, migrations and types. Spectrum: query builders (Knex, Kysely, Drizzle’s core API) stay close to SQL; full ORMs (Prisma, TypeORM, Sequelize) add more abstraction (relation loading, lifecycle hooks). Benefits: type safety, less boilerplate, safer parameterisation. Costs: leaky abstractions, hidden N+1 queries, harder tuning. Drizzle: db.select().from(documents).where(eq(documents.userId, id)) produces select … from "documents" where "documents"."user_id" = $1. Loading a list (1 query) then each item’s relation in a loop (N queries). Fix with a join or a batched IN query. “With an ORM you don’t need to know SQL.” Basics. Why use Drizzle instead of writing raw SQL everywhere?Type safety from the schema (wrong column names fail at compile time), parameterization by default, composable query pieces, and a schema file that drives migrations, while staying close to SQL and thin at runtime. Drizzle keeps you close to SQL (you can predict the query), types every column from your schema file (a typo or wrong type fails at compile time), always parameterises values, lets you compose conditions as values (and(eq(...), ...)), drives migrations from the same schema, and has almost no runtime overhead or code generation step. It still offers a sql template for anything it doesn’t model. DocMind’s cosineDistance(chunks.embedding, vec) is a typed helper producing embedding <=> $1, used inside an ordinary select with a join and where clause. Prisma has a separate schema language, generated client and powerful relation API but more abstraction; Drizzle is TypeScript-native, SQL-shaped and lighter. “Drizzle is faster than SQL.” It generates SQL. Tool reasoning. How does Drizzle interact with PostgreSQL?You give it a driver (node-postgres pool, postgres.js, Neon serverless). Its query builder produces a SQL string plus parameters, sends them through the driver, and maps rows back to typed objects. No query engine or extra process in between. You pass Drizzle a driver connection (e.g. a node-postgres Pool). Each builder call composes an AST; awaiting it renders SQL text plus a params array, sends it through the driver, receives rows, and maps column names to your schema’s property names (snake_case to camelCase) and types (timestamps to Date, numeric to string unless mapped). Transactions borrow one connection from the pool for their duration. .toSQL() on a query shows exactly what will be sent: useful for debugging. No, the driver does; Drizzle uses whatever client you give it. “Drizzle stores data itself.” Understanding of layers. What is Drizzle Kit?Drizzle’s CLI: generate SQL migrations from schema changes, apply them, push schema directly, introspect an existing DB into a schema file, and Drizzle Studio for browsing data. drizzle-kit reads drizzle.config (schema path, output folder, dialect, credentials). generate diffs the schema against the last snapshot and writes SQL migration files; migrate applies them; push syncs the DB directly; pull introspects an existing DB into a schema file (useful for baselining); studio opens a data browser. Baseline for DocMind: drizzle-kit pull or generate an initial migration and mark it as applied, so the next generate only contains the new change. Numbered SQL files plus a meta folder with JSON snapshots and a journal that tracks order. “drizzle-kit runs at request time.” Tooling. What’s the difference between push and migrations?push diffs schema vs the live database and applies changes immediately with no files: quick for prototyping. generate + migrate writes versioned SQL files you review, commit and apply the same way everywhere: right for production. push compares your schema with the live database and runs whatever DDL makes them match, interactively, without leaving a record: great for local prototyping, dangerous for shared or production databases (accidental drops, no review, no reproducibility). generate + migrate produce committed SQL files that are reviewed, applied in order everywhere, and tracked in a migrations table. Prototype locally with push; once others or production use the DB, switch to migrations. Only carefully: push on a DB managed by migrations makes the migration history lie about the real schema. “push is just a faster migrate.” Process maturity. What happens when you change a schema and generate a migration?Drizzle Kit compares the new schema with its last snapshot, writes the SQL needed (CREATE/ALTER/DROP), saves a new snapshot, and records it in its journal. migrate then runs unapplied files and records them in a migrations table in the DB. Rename filename to name in schema.js → generate asks “rename or drop+create?” → choose rename → SQL: ALTER TABLE "documents" RENAME COLUMN "filename" TO "name";An ambiguous rename becomes drop + add (Kit asks interactively; read the SQL); a NOT NULL column on a populated table fails (next question). Editing an already-applied migration file instead of writing a new one. Process detail. How do you define relationships in Drizzle?Foreign keys with .references(() => users.id, { onDelete }) in the table definition (real DB constraints), and relations() declarations (one/many) for the relational query API’s with: loading. They are separate: relations alone create no constraint. Two separate things: foreign keys declared on columns (.references(() => users.id, { onDelete: 'cascade' })) create real database constraints; relations() declarations tell Drizzle’s relational query API how tables connect (one/many) so it can load nested data with with. You usually want both: constraints for integrity, relations for convenient loading. db.query.users.findFirst({ where: eq(users.id, id), with: { documents: { where: eq(documents.status, 'ready') } } }). A join table with two references, and relations from each side to the join table. “Declaring relations() creates foreign keys.” Tool knowledge. How do you perform joins?With the SQL-like builder: db.select({...}).from(a).innerJoin(b, eq(b.aId, a.id)) (also leftJoin, rightJoin, fullJoin), or the relational API db.query.a.findMany({ with: { b: true } }). Joins in the core API mirror SQL: innerJoin, leftJoin, rightJoin, fullJoin with an ON condition built from operators. Selected columns can be shaped into nested objects. For left joins, the joined table’s fields become nullable in the result type, which forces you to handle missing rows. 
const rows = await db
  .select({ id: documents.id, filename: documents.filename, owner: users.email, chunks: count(chunks.id) })
  .from(documents)
  .innerJoin(users, eq(users.id, documents.userId))
  .leftJoin(chunks, eq(chunks.documentId, documents.id))
  .where(eq(documents.userId, userId))
  .groupBy(documents.id, users.email);
 Call .toSQL() on the query or enable Drizzle’s logger. Loading each relation in a loop (N+1). Practical use. How would you handle database transactions using Drizzle?await db.transaction(async (tx) => { ... }): use tx for every statement inside; throwing (or tx.rollback()) rolls back; returning commits. Keep slow work like LLM calls outside. db.transaction(async (tx) => { … }) checks out one connection, sends BEGIN, runs your callback with tx (a Drizzle instance bound to that connection), COMMITs if it resolves, ROLLBACKs if it throws (or you call tx.rollback()), and releases the connection. Nested tx.transaction() creates savepoints. Isolation level can be set via options. Ingestion’s “delete old chunks, insert new ones, mark ready” as one transaction so a crash never leaves a document half-indexed. That statement runs on another connection outside the transaction: it won’t roll back and can deadlock against the transaction’s own locks. Calling external APIs inside the transaction. Applied transactions. What problems can occur when adding a NOT NULL column to an existing populated table?Existing rows have no value, so the ALTER fails, unless you give a default. Also, the running old code doesn’t write the new column, so inserts fail after the migration. Do it in steps: add nullable (or with a default), deploy code that writes it, backfill in batches, then add NOT NULL. ALTER TABLE users ADD COLUMN plan text NOT NULL; on a table with rows fails: “column contains null values”. ADD COLUMN plan text NOT NULL DEFAULT 'free' succeeds instantly in Postgres 11+ (the default is stored in the catalog, not written to every row).DocMind added documents.status as NOT NULL DEFAULT 'ready': old rows became ready, and the then-deployed code (which never wrote status) kept working. user_id was added nullable for the same reason. Add it nullable, deploy code that writes it, backfill in batches with UPDATE … WHERE id BETWEEN, then SET NOT NULL (consider adding a CHECK constraint NOT VALID first and validating it to avoid long locks). “Just add it and update all rows in the same migration on a huge table.” That can lock the table for a long time. Production-safe schema changes. When would you choose raw SQL over ORM methods?For features the ORM doesn’t model well (window functions, recursive CTEs, vector operators, complex upserts, bulk operations), for performance-critical hand-tuned queries, and for migrations. Still parameterize (Drizzle’s sql template does). Hybrid search with RRF (CTEs, window functions, UNION ALL, vector operators) is far clearer in raw SQL through Drizzle’s sql template than in builder calls. Use the sql template (values become parameters), type the result explicitly, and test it. “Raw SQL is always unsafe.” Unsafe is string concatenation, not SQL itself. Pragmatism.

4.4SQL practice ladder

Tables: users(id, name), documents(id, user_id, title, status, created_at), chunks(id, document_id, tokens), llm_calls(id, user_id, input_tokens, output_tokens, created_at). Write each query, then reveal.
  1. Ready documents of user 7, newest first.
  2. Number of chunks and total tokens per document, including documents with 0 chunks.
  3. Users whose total tokens this month exceed 100,000.
  4. Each user’s single most expensive day.
  5. Documents stuck in processing for over 10 minutes.
  6. For each user, the gap between consecutive uploads.
 
-- 1
SELECT id, title, created_at FROM documents WHERE user_id = 7 AND status = 'ready' ORDER BY created_at DESC;
-- 2
SELECT d.id, d.title, count(c.id) AS chunks, coalesce(sum(c.tokens), 0) AS tokens
FROM documents d LEFT JOIN chunks c ON c.document_id = d.id GROUP BY d.id, d.title;
-- 3
SELECT user_id, sum(input_tokens + output_tokens) AS total FROM llm_calls
WHERE created_at >= date_trunc('month', now()) GROUP BY user_id HAVING sum(input_tokens + output_tokens) > 100000;
-- 4
WITH daily AS (
  SELECT user_id, date_trunc('day', created_at) AS day, sum(input_tokens + output_tokens) AS t
  FROM llm_calls GROUP BY 1, 2)
SELECT DISTINCT ON (user_id) user_id, day, t FROM daily ORDER BY user_id, t DESC;
-- 5
SELECT id, title FROM documents WHERE status = 'processing' AND created_at < now() - interval '10 minutes';
-- 6
SELECT user_id, created_at, created_at - lag(created_at) OVER (PARTITION BY user_id ORDER BY created_at) AS gap
FROM documents;
 2 needs LEFT JOIN + count(c.id) (not count(*)) to show zeros. 4 uses Postgres’s DISTINCT ON (row_number() works too). 5 is how you find jobs that died without marking failure.

@Q 9.2
S: The key difference is who decides the control flow. In a workflow, the developer encodes the steps, order, branches and loops; the engine executes them and persists progress. In an agent, the model chooses actions step by step from the tools available. Workflows give predictability, durability, per-step retries and easy auditing; agents give flexibility for tasks whose path can’t be known in advance. They combine well: workflows calling agents for open sub-tasks.
@Q 9.12
S: Suspension lets a run wait for something that may take minutes to days without consuming resources: human decisions (approval, choice, correction), external events (webhooks, payment confirmation, another system finishing), or dependencies (a document still processing). Because state is persisted, the wait survives deploys and crashes, and resuming can happen in any process.
@Q 9.13
N: “The run is lost” (with persistence it isn’t) or “it continues from the exact line where it crashed”.
@Q 9.16
S: In workflows, steps can execute more than once: retries after failures, recovery after crashes (a step may have finished its side effect but not saved its result), duplicate resumes, or re-runs of failed workflows. Idempotency means designing each step’s effects so running it again changes nothing: check-before-act using stored state, unique constraints with upserts, idempotency keys for external APIs, and deterministic ids for created records.
@Q 9.19
S: In a distributed process, earlier steps may have committed real effects in other systems (payments, emails, bookings) that a database rollback can’t undo. A compensating action is the business-level undo for a completed step, run (usually in reverse order) when a later step fails permanently. This is the saga pattern. Compensations should be idempotent and themselves retried; some effects can’t be undone (an email sent), so you design order and approvals to minimise them.
@Q 9.20
S: Choose a workflow when you can draw the process as a flowchart before running it: known steps and order, needs to survive restarts, requires human approval points, needs per-step retries and audit trails, or must have predictable cost and latency. Choose an agent only for the parts where the next step depends on judgement over intermediate results.
@Q 9.27
S: A custom tool needs: an id (stable, unique), a description written for the model (what, when, when not), an input schema with field descriptions, an optional output schema, and an execute function that takes validated input plus context, reads scope from the request context, enforces authorization, handles errors as data where useful, and returns small, structured results. Add requireApproval for side effects.
@Q 9.28
S: A step is defined with createStep: id, inputSchema, outputSchema, and an async execute that receives inputData plus helpers and returns data matching outputSchema. Optional: suspendSchema/resumeSchema for pausing, retries for transient failures, and a description. Steps should do one thing, be idempotent, and keep large data in your database rather than in outputs.
@Q 9.29
S: By default each step’s output becomes the next step’s input. For anything else: .map() reshapes data between steps (and can read earlier steps with getStepResultAsync or the initial input with getInitData); after .parallel() or .branch() the output is an object keyed by step id; .foreach() outputs an array in input order; and workflow state (stateSchema + setState) holds values shared across steps.
@Q 9.31
S: Plan error handling per failure type: transient (retries with delay at step or workflow level), invalid model output (retry once or twice, then fail), expected business outcomes (return a status, or bail() to end early with a result), optional parallel work (catch inside the step and return a failed marker), and unrecoverable errors (let the step throw so the run fails). After start/resume, inspect result.status and update your own records; alert on failure rates.
@Q 9.32
S: Implementation in three requests. Start: the route creates a run with the user as resource, starts it; steps run until the approval step calls suspend(payload); the snapshot is saved; start() returns status suspended; the API returns 202 with what the user must review. Approve: an authenticated endpoint checks the run belongs to the user and claims the waiting state atomically, then calls resume with the step id and validated resume data. Continue: the suspended step’s execute runs again from the top with resumeData, takes the approve/reject path, and the run proceeds to the end.
Q: How does the UI learn the result?
A: By polling a status endpoint backed by your own tables (or an SSE event), not by waiting on the resume request.
@Q 9.33
S: Persist two kinds of state. Orchestration state (run snapshots: step statuses, outputs, suspend payloads) goes into the framework’s storage, configured once on the Mastra instance (PostgresStore or the workflows-only WorkflowsPG). Business state (courses, lessons, statuses users see) goes into your own tables, linked to the run by run id and owner. That keeps your app’s queries independent of framework internals.
@Q 9.34
S: Human approval = suspend + an authenticated decision endpoint + resume. Design details: show exactly what will happen (the outline, the email draft, the amount); bind the approval to the user and the specific pending action; claim it once atomically; validate the decision with a resume schema; handle reject paths (bail or regenerate with feedback); expire stale requests; record an audit trail.
@Q 9.35
S: The failing step throws; if it has retries, the engine waits and re-executes it; if it still fails, the step and run are marked failed with the error and the snapshot keeps completed steps’ results. Your code then reports a failure, and a retry (re-run with the same business key) resumes useful progress thanks to idempotent steps. For latency-sensitive steps, catch the error inside the step and use a fallback provider; for non-critical steps, mark them failed and continue.
@Q 9.36
S: A framework gives tested persistence, resume claims, recovery, retries, typed steps, tracing and a model router: weeks of work you don’t write or maintain. The costs: learning its concepts, abstractions that hide behaviour (you must know details like resume re-running a step from the top), dependency upgrades in a fast-moving project, extra tables and memory, and debugging through library code. Hand-rolled orchestration is fine for small, stable flows and gives full control; frameworks pay off as soon as you need durability and human-in-the-loop.

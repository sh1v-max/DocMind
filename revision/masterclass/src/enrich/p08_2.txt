@Q 8.2
Q: Can a single call still use a tool?
A: Yes: one call that returns a function call, executed once, then one more call to answer, is a minimal agent loop of two steps; the difference is whether the model chooses the action.
@Q 8.7
S: The two are separate responsibilities. The model’s job ends at producing a well-formed request (name + arguments). The backend owns everything that touches the real world: looking up the tool, validating arguments, checking permissions and approvals, running the code with timeouts, handling errors, shaping the result and returning it. This split is what makes agents safe enough for production.
Q: Why does the distinction matter in interviews?
A: Confusing them suggests you think the model has access to your systems, which leads to unsafe designs; it’s one of the listed red flags.
@Q 8.18
S: Avoid agents when the steps are known (use a workflow or plain code), when a single call or a fixed RAG pipeline answers well, when latency and cost must be predictable (high-volume endpoints), when actions are high-stakes and must be deterministic and auditable, or when you can’t evaluate the agent’s behaviour well. Start simple and add agency only where measured quality requires decisions the code can’t make.
@Q 8.29
S: Log every tool call as a structured event tied to the request and run: who (user, tenant), what (tool, validated arguments, redacted where sensitive), when and how long, outcome (ok/error type), and result size; log each model step with usage and finish reason. Better still, emit trace spans (OpenTelemetry) so a whole agent run appears as one tree. These logs power debugging, audits of sensitive actions, cost analysis and eval datasets.

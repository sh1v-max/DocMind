@Q 9.1
S: A workflow engine executes a defined graph of steps for each run: it passes data from step to step, records each step’s status and output, retries failed steps by policy, can pause (suspend/sleep) and continue later, and lets you inspect runs. The definition is code (or config) and the order is fixed by it; individual steps can call anything, including LLMs or agents.
E: Order fulfilment: validate payment → reserve stock → ship → email, with retries per step and a human check for high-value orders.
Q: How is it different from a job queue?
A: A queue runs independent jobs; a workflow coordinates many steps of one process with state across them (a workflow engine often uses queues underneath).
N: “A workflow is a list of function calls in a route handler.” (No persistence, retries or resume.)
@Q 9.2
E: “Generate a course” (fixed steps) → workflow. “Help me understand my documents” (open-ended, choose tools) → agent. “Generate a course, researching each topic” → workflow whose research step calls an agent.
Q: Can an agent call a workflow?
A: Yes, as a tool: the agent decides to start it; the workflow guarantees the process.
N: “Workflows can’t use LLMs.”
@Q 9.3
S: Deterministic here means the control flow is fixed by code: given the same inputs and step outputs, the same steps run in the same order. This is what makes replay, resume and debugging possible: the engine can re-run from a snapshot and know which step is next. LLM outputs inside steps are still non-deterministic, so steps must validate their outputs and be safe to re-run.
E: Temporal-style engines require workflow code to be deterministic so they can replay history; Mastra persists step results in snapshots for a similar purpose.
Q: Can a deterministic workflow branch on an LLM classification?
A: Yes: the branch logic is deterministic given the step’s (stored) output; on resume the stored output is reused, not regenerated.
N: “Deterministic means the LLM gives the same answer every time.”
@Q 9.4
S: A non-deterministic process can take different paths or produce different results for the same input: an agent deciding tools, sampling at temperature &gt; 0, timing-dependent concurrency, external data that changes. Non-determinism isn’t bad, but it must be contained: record outputs so re-runs don’t re-decide, validate results, and bound behaviour with limits.
E: Asking an agent the same question twice may produce 2 searches one time and 3 the next.
Q: How do you test something non-deterministic?
A: Fix what you can (temperature 0, seeds, fakes), test properties (valid schema, cites a source, under N steps) rather than exact strings, and evaluate on sets of runs.
N: “Non-deterministic means random and useless.”
@Q 9.5
S: A step is the smallest unit the engine tracks: it has an id, an input schema, an output schema, and an execute function; optionally suspend/resume schemas and retry settings. The engine validates input, runs execute, validates output, and stores the result in the run snapshot. Good steps are small enough to retry cheaply, large enough to be meaningful, and idempotent.
E: <code>createStep({ id: 'write-lesson', retries: 2, inputSchema: LessonItem, outputSchema: z.object({ moduleNo, lessonNo }), execute })</code>.
Q: How big should a step be?
A: One logical action with one side effect (one LLM call + one write), so a retry repeats little and is safe.
N: “Steps are just functions; size doesn’t matter.”
@Q 9.6
S: Sequential steps form a chain where each consumes the previous output; total time is the sum. Use it for real dependencies (outline before lessons, validation before charging). Mastra: <code>.then(a).then(b)</code>.
E: prepare → outline → approve: each needs the previous result.
Q: How do you pass the original input to a later step?
A: Carry it through outputs, use <code>.map()</code> to combine, read an earlier step with <code>getStepResultAsync</code>, or use workflow state.
N: “Sequential is always slower, so avoid it.”
@Q 9.7
S: Independent steps start together and the workflow continues when all complete; total time ≈ the slowest step. In Mastra, <code>.parallel([a, b])</code> outputs an object keyed by step id; <code>.foreach(step, { concurrency: n })</code> runs one step per array item with a cap. If any parallel step throws, the block fails, so catch inside steps when partial success is acceptable.
E: Generating summaries for 3 modules in parallel takes ~1 call’s time instead of 3.
Q: What limits how parallel you should go?
A: Provider rate limits, DB pool size, memory, and cost spikes.
N: “Parallel steps share variables safely.” (They should communicate through outputs, not shared mutable state.)
@Q 9.8
S: Branching selects steps based on data. In Mastra’s <code>.branch([[condition, step], …])</code> every condition that’s true runs its step (not just the first), and the output is keyed by step id like parallel. Simple skips can be an <code>if</code> inside a step that returns its input unchanged. Conditions should use stored step outputs so resumed runs follow the same path.

createWorkflow({ id: 'triage', inputSchema: Ticket, outputSchema: z.any() })

  .branch([
    [async ({ inputData }) => inputData.category === 'billing', billingStep],
    [async ({ inputData }) => inputData.category === 'bug', createIssueStep],

Q: What if no condition is true?
A: No branch step runs; design a default condition or handle it after the branch.
N: “.branch runs only the first matching branch.”
@Q 9.9
S: Run state = input, status (running, suspended, success, failed, canceled, waiting), each step’s status and output, suspend payloads and resume data, plus optional shared workflow state. It’s what makes inspection (“where is this run?”), resume and retry possible. Keep business data in your own tables and keep run state focused on orchestration.
E: Snapshot for a course run: <code>{ status: 'suspended', steps: { prepare: success, outline: success, 'approve-outline': suspended { outline } } }</code>.
Q: Should large data (lesson bodies) go into run state?
A: Prefer storing large content in your tables and passing ids, to keep snapshots small.
N: “State lives in memory while the server runs.”
@Q 9.10
S: Persistence writes run state to durable storage after steps and on suspend, usually a table keyed by workflow name + run id. Any process with access to the storage can load the run, so a different instance (after a deploy or crash) can resume it. Mastra uses its storage adapters (e.g. Postgres via <code>@mastra/pg</code>), with tables like <code>mastra_workflow_snapshot</code>.
E: A run suspended on Monday is resumed on Wednesday by a different server instance after two deploys.
Q: What happens if the database is down during a step?
A: The engine can’t persist; the step’s result may be lost and the step re-run later, so steps must be idempotent.
N: “Persistence means logging.”
@Q 9.11
S: Suspend stops the run at a step and saves its state with a payload explaining what it’s waiting for; nothing runs while suspended (no thread or request held). Resume loads the state, claims the run, and continues the suspended step with resume data (validated by a resume schema). In Mastra the step’s execute runs again from its first line, now with resumeData, so code above the suspend call must be safe to repeat.
E: Step “approve-outline”: <code>if (!resumeData) return await suspend({ outline })</code>.
Q: Suspend vs sleep?
A: Suspend waits for external input (resume); sleep waits for time (in Mastra the run status is “waiting”).
N: “Suspend keeps a promise waiting in memory.”
@Q 9.12
E: Waiting for a manager’s approval on an expense, a user choosing an option, a payment provider’s webhook, a document finishing processing, or a scheduled date.
Q: Why not keep the HTTP request open until the user answers?
A: Requests time out, connections drop, deploys restart processes; the wait might be hours or days.

@Q 9.13
S: The process dies mid-step: in-memory progress is lost, but the last snapshot records which steps completed. On restart (or when a recovery job runs), the engine finds runs still marked running and re-executes from the first incomplete step. Whatever the interrupted step did before the crash (partial DB writes, API calls) happens again on re-run, so idempotent side effects are essential.

Q: Does Mastra resume automatically?
A: By default (<code>recovery: { workflows: 'auto' }</code>) it re-drives running runs at boot; it can be turned off globally or per workflow.
@Q 9.14
S: Two cases. Suspended runs: your code calls resume with the run id, the suspended step id and resume data, after checking the user may resume it. Crashed running runs: the engine’s recovery or your own job restarts them from the last snapshot. Q: What if two resume calls race?
A: Mastra claims the run atomically (suspended → running); the loser gets WORKFLOW_RESUME_ALREADY_CLAIMED; add your own app-level claim to return a clean 409.
N: “Resume restarts the whole workflow.”
@Q 9.15
S: Human-in-the-loop (HITL) inserts a person at decision points: approve/reject, edit generated content, choose between options, or handle cases the system flags as uncertain. A: Before irreversible or expensive actions and where quality matters more than speed (publishing, sending, deleting, paying).

@Q 9.16

@Q 9.17
S: Duplicate execution has several sources: the client submitting twice, two resumes, recovery re-running a step, retries, and two workers picking the same job. @Q 9.18
S: Classify failures: transient (timeouts, 429, 5xx) → retry with backoff; invalid LLM output → retry once or twice; permanent (bad input, missing data) → don’t retry, fail with a reason. // a tiny saga runner: run steps, and on failure run compensations in reverse
async function runSaga(steps, ctx) {
  const done = [];
  try {
    for (const s of steps) { await s.run(ctx); done.push(s); }
  } catch (err) {
    for (const s of done.reverse()) await s.compensate?.(ctx).catch((e) => log({ evt: 'compensation_failed', step: s.id, e: e.message }));
    throw err;
  }
}

// shared token bucket: every worker awaits a token before calling the provider
class TokenBucket {
  constructor(ratePerMin) { this.capacity = ratePerMin; this.tokens = ratePerMin; this.refillMs = 60000 / ratePerMin; this.last = Date.now(); }
  async take() {
    for (;;) {
      const now = Date.now();
      this.tokens = Math.min(this.capacity, this.tokens + (now - this.last) / this.refillMs); this.last = now;
      if (this.tokens >= 1) { this.tokens -= 1; return; }
      await new Promise((r) => setTimeout(r, this.refillMs));
    }
  }
}
const llmBucket = new TokenBucket(60);   // e.g. 60 requests per minute (per process; use Redis for many processes)

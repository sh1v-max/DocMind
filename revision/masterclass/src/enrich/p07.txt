@Q 7.2
S: Two problems pushed RAG into the mainstream: models don’t know private or recent information, and retraining them for every document change is slow and expensive. The 2020 RAG paper combined a retriever with a generator so knowledge could live in an updatable index; with modern instruction-following LLMs the pattern became the default way to build “chat with your data”. It also adds traceability: you can show which sources an answer used.
E: A legal team adds 200 new contracts on Monday; with RAG they’re searchable after ingestion, with no model retraining.
Q: Would a bigger context window make RAG unnecessary?
A: Not for large or many-user corpora: you still can’t send everything per request, and cost/latency/attention problems grow with context. Long context and RAG are complementary.
N: “RAG was introduced to make models faster.”
@Q 7.3
S: RAG solves knowledge access: grounding answers in specific, current, permissioned data. It reduces hallucinations by giving the model evidence, enables citations, keeps knowledge updatable (re-index instead of retrain), and enforces access control at retrieval time (each user only retrieves what they may see). It doesn’t teach the model new skills or styles; that’s what fine-tuning or prompting is for.
E: A per-customer support bot: same model for everyone, different retrieved documents per customer.
Q: Which problem does RAG not solve?
A: Reasoning errors, poor writing style, tasks needing the whole corpus at once (global counts, full summaries) and bad source data.
N: “RAG makes the model smarter.”

E: Step through the “Complete RAG” animation in lesson 7.A: 15 steps from upload to evaluation.

A: Extraction and chunking quality plus a small eval set; most downstream problems start there.

@Q 7.5
S: Ingestion converts raw files into indexed, searchable units with metadata, and tracks the lifecycle: accepted → processing → ready/failed, re-ingest on change, delete on removal. It includes validation (type, size, duplicate detection), storage of the original, extraction, cleaning, chunking, embedding, indexing, and status/progress reporting. It runs asynchronously and must be idempotent because jobs are retried.
E: Upload a 40-page PDF → 202 → worker extracts 40 pages → 95 chunks → 1 batched embedding call per 64 chunks → rows inserted in one transaction → status ready.
Q: What should happen when a document is re-uploaded with changes?
A: Detect by hash, re-run ingestion that replaces the old chunks atomically, and invalidate caches.
N: “Ingestion is just uploading the file.”
@Q 7.6

@Q 7.10

@Q 7.16
S: Chunking defines the retrievable units of your corpus. A: No: parent-child retrieval embeds small chunks and sends larger parents.

@Q 7.17
S: Fixed-size chunking cuts every N units (characters, words or tokens), often with overlap. It’s fast, deterministic, gives uniform chunk sizes (predictable prompt size) and is a good baseline. Its weakness: boundaries ignore meaning, so sentences, tables and key facts get split.
E: 512-token chunks with 64-token overlap is a common starting point.
Q: Characters, words or tokens?
A: Tokens match model limits and costs best; words are a fine approximation; characters split words.
N: “Fixed-size chunking is always bad.” It’s a reasonable baseline.
@Q 7.18
S: Recursive splitting tries separators from most to least meaningful: blank lines (paragraphs), newlines, sentence ends, spaces, and finally characters. A piece that fits is kept whole; only oversized pieces are split further with the next separator. Then small pieces are merged up to the size limit. Result: chunks rarely break mid-sentence and respect paragraphs when possible.
E: Run <code>recursiveSplit()</code> in the chunking lesson mentally on a 3-paragraph text with a 1,200-character limit: paragraphs stay together unless one is too long.
Q: Does it understand meaning?
A: No, it only respects formatting boundaries; semantic chunking uses embeddings for meaning.
N: Confusing it with semantic chunking.
@Q 7.19
S: Semantic chunking embeds each sentence (or small window), computes similarity between consecutive ones, and places boundaries where similarity drops sharply (a topic shift), often with min/max size limits. Chunks then align with topics instead of arbitrary lengths.
E: An article that moves from “pricing” to “security” gets a boundary exactly at the shift even if paragraphs are uneven.
N: “Semantic chunking always beats other methods.”
@Q 7.20

@Q 7.32

@Q 7.33

@Q 7.35
H: For each query term t in document d: score += IDF(t) × tf·(k1+1) / (tf + k1·(1 − b + b·|d|/avgdl)). tf = how often t occurs in d; IDF(t) ≈ log(1 + (N − n_t + 0.5)/(n_t + 0.5)) where n_t = documents containing t; k1 ≈ 1.2 controls saturation; b ≈ 0.75 controls length normalisation.
E: In 10,000 support articles, “the” appears everywhere (IDF ≈ 0, adds nothing); “E1234” appears in 3 (high IDF): a chunk mentioning E1234 twice beats one mentioning “timeout” ten times.
Q: Is Postgres ts_rank BM25?
A: No, it’s a different ranking without corpus-wide IDF; extensions like pg_search (ParadeDB) or engines like Elasticsearch provide BM25.
N: “BM25 is a neural model.”
@Q 7.36
S: Steps: (1) run both retrievers with identical permission filters, retrieving more than you need (e.g. 40 each); (2) fuse: RRF by rank (robust, no tuning) or normalised weighted scores (tunable, e.g. 0.7 vector + 0.3 keyword); (3) deduplicate; (4) optionally rerank the fused top 30–50; (5) keep top-k. Tune k values and weights on an eval set.

@Q 7.37
H: score(d) = Σ over retrievers 1 / (k + rank_r(d)), with k ≈ 60 and ranks starting at 1; documents missing from a list get nothing from it. Example with k = 60: rank 1 in both lists → 2/61 ≈ 0.0328; rank 1 in one list only → 1/61 ≈ 0.0164; rank 3 and rank 5 → 1/63 + 1/65 ≈ 0.0313.
E: Move the k slider in the RRF lab: small k favours top-ranked items strongly; large k flattens the differences.

@Q 7.38
S: Reranking is a second-stage model that scores (query, candidate) pairs more precisely than the first-stage retriever and reorders them. @Q 7.40
S: A cross-encoder concatenates query and passage into one input ([CLS] query [SEP] passage), runs a transformer over both together so every query token can attend to every passage token, and outputs a single relevance score. @Q 7.41

C js:
async function multiQueryRetrieve(userId, question) {
  const { data } = await chat({ temperature: 0.3, schema: z.object({ queries: z.array(z.string()).min(1).max(4) }), messages: [
    { role: 'system', content: 'Write up to 4 search queries that together cover the question. One per sub-question or phrasing.' },
    { role: 'user', content: question } ] });
  const lists = await Promise.all([question, ...data.queries].map((q) => retrieve({ userId, query: q, k: 20 })));
  const scores = new Map();
  for (const list of lists) list.forEach((hit, i) => scores.set(hit.id, { hit, s: (scores.get(hit.id)?.s ?? 0) + 1 / (60 + i + 1) }));
  return [...scores.values()].sort((a, b) => b.s - a.s).slice(0, 6).map((x) => x.hit);
}

// diversity with MMR: avoid five near-identical chunks for an ambiguous query
function mmr(queryVec, candidates, k = 5, lambda = 0.7) {
  const picked = [];
  while (picked.length < k && candidates.length) {
    let best, bestScore = -Infinity;
    for (const c of candidates) {
      const rel = cosine(queryVec, c.embedding);
      const red = picked.length ? Math.max(...picked.map((p) => cosine(c.embedding, p.embedding))) : 0;
      const score = lambda * rel - (1 - lambda) * red;          // relevant but not redundant
      if (score > bestScore) { bestScore = score; best = c; }
    }
    picked.push(best); candidates = candidates.filter((c) => c !== best);
  }
  return picked;
}

@Q 7.51
S: Recall@k = (relevant items retrieved in the top k) / (total relevant items). For RAG it’s the ceiling on answer quality: information not retrieved can’t be used (unless the model knows it, which is what we don’t want to rely on).
E: 2 relevant chunks exist, 1 is in the top 5 → recall@5 = 0.5.
Q: How do you raise recall?
A: Hybrid search, query rewriting/multi-query, better chunking, larger candidate sets with reranking.
N: “Recall is the share of results that are relevant.” That’s precision.
@Q 7.52
S: Reciprocal rank for one query = 1 / position of the first relevant result (0 if none in the list). MRR averages it over all queries. It focuses on how quickly the first good result appears, which suits cases where one relevant chunk is enough.
E: First relevant at rank 1, 2, and not found for three queries → (1 + 0.5 + 0) / 3 = 0.5.
Q: When is MRR misleading?
A: When answers need several chunks: MRR ignores everything after the first hit.
N: “MRR measures the average rank.”
@Q 7.53
S: DCG sums each result’s relevance gain divided by log2(position + 1), so lower positions count less; NDCG divides by the best possible DCG for that query (ideal ordering), giving 0–1 comparable across queries. It supports graded relevance (0, 1, 2, 3 for not/partly/very relevant).
E: The worked example in lesson 7.D: relevant at positions 2 and 4 → NDCG@5 = 0.65 (verified by running the code).
Q: Why the logarithm?
A: It models users (and models) paying less attention further down, without making position 10 worthless.
N: “NDCG is only for web search.”
@Q 7.54
H: Typical computation: (1) split the answer into atomic claims with an LLM; (2) for each claim, ask a judge model (or NLI model) whether the provided context supports it; (3) faithfulness = supported claims / total claims.

@Q 7.55
S: Answer relevancy checks whether the response addresses the user’s actual question, regardless of correctness: an answer about monthly refunds to a question about annual refunds is irrelevant even if faithful. @Q 7.56
S: Context precision (as in RAGAS-style metrics) asks: of the retrieved chunks, how many are actually useful for answering, and are the useful ones ranked near the top? It’s a rank-aware precision of the context, typically judged by an LLM against the question and reference answer.

@Q 7.57

@Q 7.58
S: Retrieval quality measures the search component (did we fetch the right evidence: recall, precision, MRR, NDCG, context precision/recall). const Verdicts = z.object({ claims: z.array(z.object({ claim: z.string(), supported: z.boolean(), sourceId: z.number().nullable() })) });
async function checkFaithfulness(answer, sources) {
  const { data } = await chat({ temperature: 0, schema: Verdicts, messages: [
    { role: 'system', content: 'Split the answer into factual claims. For each, say if the sources support it and which source id. Be strict.' },
    { role: 'user', content: `Sources:\n${sources.map((s, i) => `[${i + 1}] ${s.content}`).join('\n')}\n\nAnswer:\n${answer}` } ] });
  const supported = data.claims.filter((c) => c.supported).length;
  return { score: data.claims.length ? supported / data.claims.length : 1, unsupported: data.claims.filter((c) => !c.supported) };
}

// neighbour expansion: fetch chunk_index ± 1 for each hit and merge per document in order
async function withNeighbours(hits) {
  const keys = hits.flatMap((h) => [h.chunk_index - 1, h.chunk_index, h.chunk_index + 1].map((i) => [h.document_id, i]));
  const { rows } = await pool.query(
    `SELECT document_id, chunk_index, content FROM chunks
     WHERE (document_id, chunk_index) IN (SELECT * FROM unnest($1::uuid[], $2::int[]))
     ORDER BY document_id, chunk_index`, [keys.map((k) => k[0]), keys.map((k) => k[1])]);
  return rows;
}

// fan out page-range jobs; each is idempotent by (documentId, from)
const RANGE = 50;
for (let from = 1; from <= pageCount; from += RANGE) {
  await queue.add('ingest-range', { documentId, from, to: Math.min(from + RANGE - 1, pageCount) },
    { jobId: `${documentId}:${from}`, attempts: 3, backoff: { type: 'exponential', delay: 5000 } });
}
await pool.query('UPDATE documents SET pages_total = $2, pages_done = 0 WHERE id = $1', [documentId, pageCount]);

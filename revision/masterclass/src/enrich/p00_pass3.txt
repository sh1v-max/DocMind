@Q 7.59
S: An eval dataset is a fixed, versioned list of inputs with what “correct” looks like: the question, the ids of chunks that answer it (for retrieval metrics), a reference answer (for correctness/faithfulness judges), and a type tag (lookup, multi-chunk, follow-up with history, exact-term, unanswerable) so you can see which kinds of questions regress. Sources: real user questions (anonymised), questions written by people who know the documents, and LLM-generated questions per chunk that a human reviews. It grows every time production shows a failure.
@Q 7.60
S: Hallucination detection compares what the answer claims with what the system gave the model. Methods: claim-level verification by an LLM judge or NLI model against the retrieved context (faithfulness), citation checks (every claim cites a source that actually contains it), consistency checks (sample several answers; disagreement suggests guessing), and comparison with reference answers on the eval set. In production, run it on samples or on high-risk answers, and use user reports as a signal.
@Q 7.61
S: Unanswerable questions are inevitable, and the worst outcome is a confident invented answer. Design the not-found path explicitly: detect it (no chunk above a relevance threshold, or the model’s explicit not-found marker), respond with a fixed honest message and next steps, never fall back silently to general knowledge, and measure it with unanswerable items in the eval set.

@Q 13.18
S: Failure handling covers three cases. Transient: BullMQ retries 3 times with exponential backoff (5 s, 10 s). Permanent: after the last attempt (checked with getState() === 'failed', since a stalled job can fail before attempts run out), the failed handler deletes partial chunks and sets status failed with a short reason. Infrastructure: if Redis is down at upload, the row is removed and the user gets 503; a crashed worker’s job is picked up again by stalled-job recovery (measured: ~10 minutes with the tuned settings).

@Q 13.21

@Q 15.9
S: MCP (Model Context Protocol), introduced by Anthropic in late 2024 and now widely adopted, is an open protocol for connecting AI applications to external capabilities. An MCP server exposes tools, resources and prompts; an MCP client inside a host app discovers and uses them over JSON-RPC 2.0 (stdio or Streamable HTTP). The model then sees those tools like any other function-calling tools.
@Q 15.11
S: Roles: the host is the AI application (an IDE, a chat app, your agent backend); it creates one MCP client per server connection; each server is a separate program exposing capabilities. Clients and servers negotiate capabilities at initialisation; servers can also ask clients for things (sampling a model completion, eliciting user input, listing roots) if the client supports them.
@Q 15.12
S: Tools are model-controlled actions with input schemas (the model decides to call them, the host executes via the server). Resources are application-controlled context: readable data identified by URIs (files, records, schemas) that the host can attach to the conversation. Prompts are user-controlled templates (often exposed as slash commands) with arguments.
@Q 15.15
S: Different levels of delegation. MCP connects an agent to capabilities it controls: it decides when to call a tool and interprets the result. A2A connects an agent to another autonomous agent: it delegates a goal, and the remote agent decides how to achieve it with its own tools, possibly over a long-running task with status updates.
Q: Can they be used together?
A: Yes: an agent can use MCP tools internally while being reachable by other agents over A2A.
@Q 15.17
S: The agent backend emits an ordered stream of typed events for each run (over SSE or similar); the frontend subscribes and renders: text as it streams, tool calls as status or cards, state changes as UI updates; user actions (messages, approvals, form inputs) are sent back to the backend. Because event types are standard, generic UI components can render any compliant agent.
@Q 15.18
S: Each protocol covers one boundary: AG-UI between the user’s interface and your agent, MCP between your agent and the tools/data it uses, A2A between your agent and other agents. A system can use any subset; most apps today use only MCP (or plain function calling) plus a custom UI stream.
@Q 15.21

Risks are false hits (similar wording, different meaning), stale answers after documents change, and cross-user leaks, so scope keys must include tenant and data version, thresholds must be high, and entries must expire.

@Q 15.26

@Q 15.27

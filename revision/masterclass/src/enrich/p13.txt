@Q 13.1
S: The user problem: finding answers inside long PDFs is slow, and generic chatbots don’t know your files and make things up. DocMind indexes your PDFs, answers questions only from them with sources, remembers the conversation, and can quiz you on a document. The engineering goal was to build each part of an AI backend for real: ingestion, vector search, RAG, streaming, structured output, queues, auth and an agent loop, all on free tiers and deployed.

@Q 13.3

@Q 13.4
S: All data calls go through one helper that adds the Bearer token and handles 401s (re-bootstrap a guest or show sign-in). Chat uses POST /chat-stream with a JSON body and reads the SSE stream with fetch + a manual parser (TextDecoder with stream: true, split on blank lines), because EventSource can’t send headers or POST. Unknown SSE event types are ignored, so new backend events don’t break old frontends.
Q: How does the frontend know a document is ready?
A: It polls GET /documents every 2 s (10 s after a minute) while anything is processing; uploadFile() resolves only when the document is ready.

@Q 13.6
S: The embedding model maps text to 3072-number vectors where similar meaning means a small cosine distance. DocMind uses it in three places: chunk vectors at ingestion, the user message (embedded once and reused for routing and, when the agent’s first search uses the message as-is, for that search), and example phrases per intent for the router. The same model for all three is required for the distances to mean anything.
Q: What happens if the embedding API is down?
A: Uploads stay processing and the job retries (then fails with a reason); chat fails at the embed step with an error message.
N: “It generates the answers.”
@Q 13.7
S: Only metadata is persisted for documents (filename, size, text length, chunk count, owner, status, error, created_at); the original PDF bytes are parsed in memory during upload and then discarded. Chunks hold the text and vectors. That kept the free-tier stack simple, at the cost of re-upload for re-processing and no original-page view.
Q: How would you add originals?
A: Upload to object storage (presigned URL), store the key on the document row, and let the worker read from storage.
N: Claiming PDFs are stored in Postgres.
@Q 13.8
S: Chunks are rows in <code>chunks</code>: id, document_id, content, embedding vector(3072). They’re created in document order by a 500-word splitter. Ownership and readiness are on the document, so every search joins documents and filters by user and status; deleting a document deletes its chunks (code order: row first, then chunks, since there are no foreign keys).
Q: What’s missing that you’d add?

@Q 13.11
S: Order matters: auth first (who), cap before multer (don’t read a file you’ll reject), parse and chunk in the request (fast, needs the bytes), save the row as processing (so the UI can show it and chat can 409), enqueue with jobId = documentId (no double queueing; 503 and row removed if Redis fails), respond 202. @Q 13.12

@Q 13.14
S: <code>chunkText(text, 500)</code> splits on whitespace into words and slices groups of 500, joining with spaces. It ignores paragraphs, headings and sentence boundaries and has no overlap, so a fact near a boundary can be split. It was a deliberate simplest-first baseline (the code comment says strategy trade-offs are a later topic).
Q: What exact change would you make first?
A: Paragraph- and sentence-aware packing to ~400 words with ~60 words of overlap, then compare recall on the 9-question set and new boundary questions.

@Q 13.15
S: The worker receives chunk texts (not the PDF) in the job, deletes any existing chunks for the document, calls the Gemini embedding endpoint with the API key in a header, and inserts chunks with their vectors; on success it marks the document ready. Retries come from BullMQ’s attempts (3, exponential 5 s → 10 s). Embedding calls count against the provider’s per-minute limits, which is the main scaling constraint.
Q: Why put chunk texts in the job and not the PDF?
A: Smaller job payloads in Redis (free-tier command and memory limits) and the expensive parsing already happened in the request.

@Q 13.16
S: The pgvector extension provides the vector(3072) type. Drizzle writes the vector column like any other value; queries use Drizzle’s cosineDistance helper, which renders <code>embedding &lt;=&gt; '[…]'</code>, mapped to a number. Without an index, Postgres computes the distance for each candidate row after the owner/status join filter, which is fine at DocMind’s scale.
Q: Why no index yet?
A: Data is small, and pgvector indexes cap vector at 2,000 dimensions; adding one needs halfvec or shorter embeddings, plus care with post-filtering by user.

@Q 13.22
S: Routing happens once per message in prepareChat, after embedding and loading history. The router returns an intent, how it was decided (vector or LLM) and the margin. Each intent maps to a code path: smalltalk builds a short prompt with no search; document_question runs the agent loop with tools; quiz_request returns a fixed offer with an action button.

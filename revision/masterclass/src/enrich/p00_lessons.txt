@L Arrays, copies, destructuring
W: <ol><li><code>filter</code> walks the 3 chunks and keeps 2 with distance &lt; 0.4 → new array; the original is unchanged.</li><li><code>map</code> turns those 2 objects into 2 strings.</li><li><code>reduce</code> starts with <code>{}</code>; chunk 1 sets a = 480; chunk 2 sets b = 120; chunk 3 adds 500 to a → <code>{ a: 980, b: 120 }</code>.</li><li><code>{ doc, ...rest } = chunks[0]</code> creates a variable doc and a new object rest with the other two keys.</li><li><code>{ ...orig }</code> creates a new outer object, but <code>shallow.user</code> is the same object as <code>orig.user</code>, so changing its name changes both; <code>structuredClone</code> copies the nested object too.</li></ol>
@L Authentication: JWT
W: <ol><li>Login succeeds → server creates a refresh token (random 32 bytes), stores sha256(token) with an expiry, sets it as an httpOnly cookie scoped to /auth/refresh, and returns a 15-minute access JWT.</li><li>Client calls APIs with the access token until one returns 401 (expired).</li><li>Client calls /auth/refresh; the browser sends the cookie automatically.</li><li>Server hashes the cookie value and runs <code>DELETE … WHERE token_hash = $1 AND expires_at &gt; now() RETURNING user_id</code>: one row means valid and now consumed.</li><li>Server stores a new refresh token (rotation), sets the new cookie, returns a new access token; the client retries the original request.</li><li>If an old refresh token is replayed, the DELETE finds nothing → 401; with reuse detection you’d also revoke the user’s other tokens.</li></ol>
@L The relational model
W: <ol><li>A user signs up → one users row (email unique; a second signup with the same email fails with 23505 → 409).</li><li>Upload → documents row with user_id FK; UNIQUE (user_id, sha256) rejects a duplicate file.</li><li>Ingestion inserts chunks with document_id; UNIQUE (document_id, chunk_index) makes re-runs safe.</li><li>Deleting the user cascades to documents → chunks, conversations → messages in one statement.</li><li>“Messages of conversation X in order” uses the (conversation_id, id) index: no sort, no scan.</li></ol>
@L Streaming LLM output
W: <ol><li>Client POSTs; the server registers <code>res.on('close')</code> to abort the provider call if the user leaves.</li><li>Headers sent: <code>text/event-stream</code>, no cache, no proxy buffering. From now on the status is 200 and errors must be events.</li><li>The provider stream arrives in arbitrary byte chunks; TextDecoder with <code>stream: true</code> keeps multi-byte characters intact; <code>\r\n</code> is normalised; events are cut at blank lines; the partial tail stays in the buffer.</li><li>Each <code>data:</code> JSON is parsed; the text delta is appended to <code>full</code> and forwarded as <code>data: {"text": …}</code>.</li><li><code>[DONE]</code> or end of stream → the full answer is saved (exactly what was streamed) → <code>event: done</code> → <code>res.end()</code>.</li><li>If the provider fails mid-stream → <code>event: error</code> unless the abort came from the client leaving.</li></ol>
@L pgvector in practice
W: <ol><li>The query vector arrives as a string <code>'[0.01, …]'</code> and is cast to vector.</li><li>Without an index: Postgres joins chunks to documents, filters by user and status, computes <code>&lt;=&gt;</code> for each remaining row, sorts, returns 5. Exact, linear in the user’s rows.</li><li>With HNSW: the planner sees <code>ORDER BY embedding &lt;=&gt; $1 LIMIT 5</code> and uses the index to fetch candidates nearest the query, then applies the WHERE filters to them; with iterative scans enabled it keeps scanning until 5 rows pass.</li><li><code>hnsw.ef_search</code> sets how many candidates the graph search keeps: higher = better recall, slower.</li><li>Deleting a document cascades its chunks; the index entries are cleaned up by vacuum.</li></ol>
@L Changing the embedding model safely
W: <ol><li>Day 1: <code>ALTER TABLE chunks ADD COLUMN embedding_v2 vector(768)</code> (nullable, instant).</li><li>Deploy: new uploads write both columns.</li><li>Backfill job: batches of 100 rows WHERE embedding_v2 IS NULL, rate-limited, resumable.</li><li>When the count of NULLs reaches 0: build the HNSW index on embedding_v2.</li><li>Run the retrieval eval with v2 queries against v2 vectors; compare recall@k with v1.</li><li>Flip a flag: queries embed with v2 and search embedding_v2. Keep v1 for a week for rollback.</li><li>Drop embedding_v1 and stop dual writes.</li></ol>
@L Chunking strategies
W: <ol><li><code>recursiveSplit(text, 1200)</code>: the whole text is too long, so split on blank lines into paragraphs.</li><li>Paragraphs are appended to a buffer while the buffer stays ≤ 1,200 characters; when the next one doesn’t fit, the buffer becomes a chunk.</li><li>A single paragraph longer than 1,200 is split again with the next separator (newlines, then sentences, then words).</li><li>Separators are kept on each piece, so sentences keep their full stops (a bug in the first version of this function dropped them; fixed after running it).</li></ol>
@L Reranking
W: <ol><li><code>retrieve()</code> returns 40 candidates from hybrid search.</li><li><code>rerank()</code> sends the query and the 40 texts in one request; the reranker scores each pair.</li><li>Results come back as indexes with relevance scores, sorted; we keep the top 5 and map them back to the original chunk objects (filename, ids).</li><li>The 5 go into context construction. Latency added: one network round trip plus model time for 40 short pairs.</li></ol>
@L Query transformation
W: <ol><li>Parent-child: children (2–3 sentences each) are searched; the SQL groups hits by parent and keeps the best distance per parent; the top 4 parents (whole sections) are returned.</li><li>Neighbour expansion: for a hit at chunk_index 12, also fetch 11 and 13 of the same document, then merge them in order so the model reads continuous text.</li><li>Both add context without making the embedded units larger.</li></ol>
@L Measuring RAG
W: <ol><li>For q17 the system retrieves [c5, c2, c9, c7, c1]; labels say {c2, c7}.</li><li>top-5 contains 2 relevant → precision 0.4; both relevant found → recall 1.0.</li><li>First relevant at position 2 → reciprocal rank 0.5.</li><li>DCG = 1/log2(3) + 1/log2(5) = 1.062; ideal DCG (both at the top) = 1 + 1/log2(3) = 1.631; NDCG = 0.651 (the code above prints exactly this when run).</li><li>Averaging over all questions gives the dataset scores you track release to release.</li></ol>
@L The tool-calling protocol
W: <ol><li>Request 1 carries the user message and the tool list.</li><li>Response 1 has no text, one tool call with id call_1 and arguments as a JSON string.</li><li>Your code parses the string, validates, runs listDocuments for the session user.</li><li>Request 2 resends the whole conversation: user message, the assistant turn with the tool call (unchanged), and a tool message with tool_call_id call_1 and the JSON result.</li><li>Response 2 is plain text: the loop ends. Two model calls, one tool execution.</li></ol>
@L The same agent in Mastra
W: <ol><li>The route creates a RequestContext and sets userId from req.user.id.</li><li><code>docAgent.generate(message, { maxSteps: 4, requestContext })</code>: Mastra sends instructions + tools (converted from Zod) to the model.</li><li>When the model calls search-documents, Mastra validates the input against inputSchema and calls execute(input, context).</li><li>execute reads userId from context.requestContext and runs the owner-scoped retrieval; Mastra validates the output and sends it back to the model.</li><li>The loop ends with text or at maxSteps; the result contains text, tool calls/results and usage. For delete-document (requireApproval) a streaming call pauses with a tool-call-approval chunk until <code>approveToolCall({ runId })</code>.</li></ol>
@L Walkthrough: quiz generator
W: <ol><li>POST /quizzes { documentId, count: 20 } with an Idempotency-Key → quiz row (status generating) → job.</li><li>The job samples 20 source chunks across sections and generates in 4 batches of 5 (concurrency 2).</li><li>Each batch: structured output → Zod → distinct options → judge verifies keys → embedding dedupe → insert rows with positions.</li><li>A failed batch retries once; still failing → quiz partial with a “generate remaining” action.</li><li>All 20 valid → options shuffled in code → status ready → the UI shows the quiz.</li></ol>
@L DocMind architecture
W: <ol><li>Upload: guest JWT → cap check (5) → multer 10 MB → pdf-parse → 500-word chunks → documents row processing → BullMQ job (jobId = documentId) → 202 in ~2 s.</li><li>Worker: delete old chunks → Gemini embeddings → insert → status ready (~5 s for a small PDF).</li><li>Chat: POST /chat-stream → ready check → embed message → last 8 messages → router → agent → searchDocuments (owner-scoped top 3) → Gemini streams → SSE meta/status/sources/text/done → saved.</li></ol>

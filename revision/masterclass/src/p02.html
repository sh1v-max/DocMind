2.ALessons

Every value in JavaScript has a type. There are 7 primitive types (string, number, bigint, boolean, undefined, null, symbol) and one non-primitive: object (arrays, functions, dates, maps are all objects). Types decide what operations mean. "5" + 1 and 5 + 1 do different things. JavaScript was designed to “keep going” instead of throwing, so it converts types automatically (coercion). That convenience causes many bugs.

Primitives are stored by value: copying a primitive copies the value. Objects are stored by reference: a variable holds a pointer to the object on the heap; copying the variable copies the pointer.

let a = 1; let b = a; b = 2;        // a is still 1
const o1 = { n: 1 }; const o2 = o1; o2.n = 2;  // o1.n is now 2: same object

Coercion rules you must know:

  • + with a string → string concatenation: "5" + 1 === "51".
  • Other math operators convert to number: "5" - 1 === 4, "abc" * 2 is NaN.
  • == converts before comparing; === doesn’t.
  • Falsy values: false, 0, -0, 0n, "", null, undefined, NaN. Everything else is truthy, including "0", [] and {}.
typeof null            // "object"  (a historic bug, kept for compatibility)
typeof function(){}    // "function"
typeof []              // "object" → use Array.isArray([])
0.1 + 0.2 === 0.3      // false: numbers are 64-bit floating point
Number.isNaN(NaN)      // true; NaN !== NaN
 Primitives are like writing a number on a sticky note and handing over a copy. Objects are like handing over the address of a house: two people with the same address walk into the same house. Query params and form fields always arrive as strings. req.query.page is "2", so req.query.page + 1 is "21". That’s why you parse with Zod (z.coerce.number().int().min(1)).
  • Using == and being surprised by 0 == "" (true).
  • Checking arrays with typeof.
  • Comparing money as floats. Use integer cents.
 Scope is where a variable can be seen. Hoisting is the engine registering declarations before running the code. A closure is a function together with the variables it captured from where it was created. Closures are how JavaScript keeps private state (counters, caches, configured functions) without classes, and how every callback remembers its context. Hoisting explains why some code works before the line that declares it and some throws.

Before running a scope, the engine creates bindings for its declarations:

  • var x → created and set to undefined (function-scoped).
  • let/const/class → created but uninitialised until the declaration line runs. Touching them before is a ReferenceError. That window is the temporal dead zone.
  • Function declarations → created with the whole function, callable before the line.

Lexical scope: a function sees variables based on where it is written, not where it is called. When a function is created it keeps a reference to its surrounding scope. If it outlives that scope (returned, passed as a callback), the variables stay alive: that is the closure.

function makeCounter() {
  let count = 0;                 // lives on after makeCounter returns
  return () => ++count;          // closure over `count`
}
const next = makeCounter();
next(); next();                  // 1, 2  — nobody else can touch `count`

// The classic loop bug
for (var i = 0; i < 3; i++) setTimeout(() => console.log(i));  // 3 3 3 (one shared i)
for (let j = 0; j < 3; j++) setTimeout(() => console.log(j));  // 0 1 2 (new j per iteration)
 A closure is a backpack. A function packs the variables it needs from the room where it was made and carries them wherever it goes. Express middleware factories are closures: rateLimit({ max: 20 }) returns a middleware function that remembers max. Memoisation caches, once-only init functions and React hooks all rely on closures.
  • Thinking let isn’t hoisted. It is; it just isn’t initialised (TDZ).
  • Memory leaks from closures holding large objects in long-lived callbacks.

 A Promise is an object representing a value that will be available later (or an error). async/await is syntax for writing promise code that reads top to bottom. Network calls, database queries and file reads take milliseconds to seconds. Blocking the single JavaScript thread while waiting would freeze the whole server. Callbacks solved this but nested badly (“callback hell”) and made error handling inconsistent. Promises give one composable object with one error channel.

A promise is pending, then settles once to fulfilled (with a value) or rejected (with a reason). .then/.catch register reactions; when the promise settles, the reactions are queued as microtasks.

await p inside an async function: the function pauses, returns control to the caller (the async function itself already returned a pending promise), and when p settles, the rest of the function is scheduled as a microtask. It does not block the thread.

// sequential: total ≈ a + b
const user = await getUser(id);
const docs = await getDocs(id);

// concurrent: total ≈ max(a, b)
const [user2, docs2] = await Promise.all([getUser(id), getDocs(id)]);

// errors: one try/catch covers every await
async function load(id) {
  try {
    const doc = await db.getDocument(id);
    if (!doc) throw new NotFoundError(id);
    return doc;
  } catch (err) {
    logger.error({ err, id }, 'load failed');
    throw err;                     // rethrow so the caller knows
  }
}

 The event loop is the mechanism that lets one JavaScript thread handle many waiting operations: run code until the stack is empty, then take the next queued callback. JavaScript runs your code on one thread. I/O (network, disk, timers) is done by the runtime (browser Web APIs, or libuv in Node). The event loop is how the results come back to your code without blocking.
  1. Call stack: the functions currently running. Synchronous code runs to completion; nothing interrupts it.
  2. Runtime facilities: timers, sockets, file reads are handed off. libuv uses the OS (epoll/kqueue/IOCP) for network I/O and a thread pool (default 4 threads) for file system, DNS lookup, crypto and zlib.
  3. Queues: when an operation completes, its callback is queued.
  4. Microtasks (promise reactions, queueMicrotask) run as soon as the stack empties, all of them, before anything else. In Node, the process.nextTick queue runs even before promise microtasks.
  5. Node’s loop phases, each with its own queue: timers (setTimeout/setInterval) → pending callbacks → idle/prepare → poll (wait for and run I/O callbacks) → check (setImmediate) → close callbacks. Between every callback, Node drains nextTick then microtasks.
 A chef (the one thread) cooks one dish at a time. Ovens and fryers (libuv, the OS) run in the background and ring a bell when done. Orders behind the counter are the queues. Some notes are marked urgent (microtasks): the chef handles every urgent note before taking the next normal order. A CPU-heavy loop (parsing a 50 MB JSON, hashing with a high cost synchronously, a long regex) blocks the stack, so no other request’s callback can run: the whole server stalls. Fix: worker threads, a job queue, or streaming parsers.
  • “setTimeout(fn, 0) runs immediately.” It runs after the current code and all microtasks, in a later timers phase.
  • “Node is multi-threaded so CPU work is fine.” Your JavaScript runs on one thread unless you use worker_threads.
  • A recursive process.nextTick or microtask loop starves I/O forever.

2.1Core JavaScript

What are the different data types in JavaScript? Seven primitives: string, number, bigint, boolean, undefined, null and symbol. Everything else is an object, including arrays, functions, dates and maps.

Primitives are immutable values. Objects are mutable collections of properties accessed by reference. typeof returns "object" for null (historic bug) and "function" for functions.

 A request body parsed by express.json() gives you strings, numbers, booleans, null, arrays and objects (JSON has no undefined, bigint, symbol or Date). A Postgres bigint column comes back from pg as a string by default, exactly because a JS number can’t hold every 64-bit integer. Number is a 64-bit float and is exact only up to 2^53 − 1 (Number.MAX_SAFE_INTEGER). Large ids (e.g. some database bigint columns, Twitter-style ids) need bigint or strings. “Array is a separate type.” It’s an object. Basic language knowledge. What’s the difference between primitive and reference types? Primitives are copied by value. Objects are accessed by reference: assigning or passing an object copies the reference, so both variables point to the same object. Every variable holds a value. For primitives the value is the data itself, so assignment copies the data and the two variables are independent. For objects the value is a reference (an address on the heap), so assignment copies the address and both variables point at the same object. Equality follows the same rule: {a:1} === {a:1} is false because two different objects have two different addresses, while two equal strings are ===. This is why mutating an object passed into a function is visible to the caller, and why React and immutable patterns create a new object instead of editing the old one. 
function rename(u) { u.name = 'X'; }
const user = { name: 'A' }; rename(user);  // user.name === 'X'
function reassign(u) { u = { name: 'Y' }; } reassign(user); // user unchanged: only the local copy of the reference changed
 No, it’s pass-by-value where the value of an object variable is a reference (sometimes called “call by sharing”). That’s why mutating works but reassigning doesn’t. “Objects are copied when you pass them to a function.” Or “JavaScript is pass-by-reference” (you can’t reassign the caller’s variable). Understanding of mutation bugs. What’s the difference between var, let and const? var is function-scoped and initialised to undefined when hoisted. let and const are block-scoped and in the temporal dead zone until declared. const can’t be reassigned, but a const object can still be mutated. var belongs to the nearest function (or the global scope) and ignores blocks, so a var inside an if or loop leaks out. let and const belong to the nearest block {}, can’t be redeclared in the same scope, and sit in the temporal dead zone until their line runs. const forbids reassigning the binding, not changing the object it points to. Modern code uses const by default and let when the value must change; var mainly appears in old code and in classic interview traps like the loop-closure bug. 
if (true) { var a = 1; let b = 2; }

Scope understanding. What is hoisting? Before a scope runs, the engine registers its declarations. var becomes undefined, function declarations are fully available, and let/const/class exist but are uninitialised until their line. When the engine enters a scope it first creates bindings for all declarations in it (the “creation phase”), then runs the code. Function declarations get their full function value immediately; var gets undefined; let/const/class get an uninitialised binding (TDZ). That is why you can call a function declared lower in the file, why reading a var early gives undefined instead of an error, and why a function expression stored in a var throws “is not a function” when called early. 
sayHi();                 // works: function declaration hoisted
function sayHi() {}
console.log(x);          // undefined
var x = 5;

 Yes. ES module import declarations are processed before any code in the module runs, so imported bindings are available everywhere in the file (they’re live, read-only bindings). “Hoisting physically moves code to the top.” Nothing moves; declarations are processed first. Mental model of execution. What is the temporal dead zone? The time between entering a scope and reaching a let/const/class declaration. The binding exists but accessing it throws a ReferenceError. The TDZ exists because let/const are hoisted (the scope knows the name) but not initialised. Any read or write before the declaration line throws a ReferenceError. It also applies to default parameters referring to later parameters and to typeof (normally safe on undeclared names, but typeof x in x’s TDZ throws).

  // TDZ for `limit` starts here

  const limit = 10;     // TDZ ends

 To catch bugs early: reading a variable before it has a meaningful value is almost always a mistake, and const must never be seen without its value. “let and const are not hoisted.” They are; they’re just not initialised. Precise vocabulary. What’s the difference between == and ===? === compares value and type with no conversion. == converts types first using coercion rules. Use === except for the idiom x == null, which checks null or undefined. === (strict equality) returns true only if both values have the same type and value (objects: same reference; NaN is never equal to itself). == (loose equality) first converts types with a set of rules: null and undefined equal each other and nothing else; a number vs a string converts the string to a number; booleans convert to numbers first (true == 1); objects convert to primitives. These rules produce non-transitive surprises, so linters forbid == except x == null.

'' == '0'          // false (not transitive!)

 There’s no built-in deep equality: compare fields you care about, use a library (e.g. Node’s util.isDeepStrictEqual), or compare stable serialisations for simple data. “== compares value, === compares type.” Both compare values; === just doesn’t convert first. Avoiding coercion bugs. What is type coercion? Automatic conversion of a value from one type to another, for example to string with + or to number with -, or to boolean in an if. Explicit conversion is Number(x), String(x), Boolean(x). Coercion happens implicitly in three places: string concatenation (+ with any string converts the other side to a string), numeric operators (- * / %, unary +, comparisons) convert to numbers, and boolean contexts (if, &&, ||, !) convert to true/false. Objects are converted via valueOf/toString (or Symbol.toPrimitive). Explicit coercion (Number(), String(), Boolean(), parseInt(x, 10)) is clearer and is what you use at API boundaries. What’s the difference between null and undefined? undefined means “no value was assigned” (missing property, missing argument, function with no return). null is an intentional “empty” value that a programmer sets.

Precision with absent values. What are closures? A closure is a function plus the variables from the scope where it was created. The function keeps access to them even after that outer function has returned. When a function is created, it stores a hidden link to the scope it was created in (its lexical environment). When it later runs, variable lookups follow that link outward. If the function survives longer than its outer function call (returned, stored, passed as a callback), the captured variables stay alive in memory because something still references them. Each call of the outer function creates a fresh scope, so each closure gets its own private variables. That’s how factories, memoisation, middleware configuration and module-private state work. 
function createRateLimiter(max) {
  const hits = new Map();                      // private state
  return function allow(ip) {
    const n = (hits.get(ip) ?? 0) + 1;
    hits.set(ip, n);
    return n <= max;                           // remembers `max` and `hits`
  };
}
const allow = createRateLimiter(3);
 Captured variables stay in memory as long as the function is reachable. A long-lived closure capturing a big object (a whole request, a large array) is a common memory leak. “A closure is a function inside a function.” That’s nesting; the key is captured variables outliving their scope. Core JS understanding, used everywhere in Node. What is lexical scope? Variable visibility is decided by where code is written. An inner function can see outer variables; the lookup goes outward through the nesting at write time, not through the call stack. Scope is resolved by position in the source code. The engine builds a chain of scopes from the innermost block outwards to the module/global scope, and looks up a name by walking that chain. Because it’s decided at write time, you can reason about which variable a name refers to by reading the code, and closures are possible. (The opposite, dynamic scope, would resolve names from whoever called the function; JavaScript doesn’t do that, except for this, which is call-time.)

Explain the difference between function declarations and function expressions. A declaration (function f() {}) is hoisted with its body, so it can be called before its line. An expression (const f = function () {} or an arrow) is a value assigned to a variable and only exists after that line runs.

Expressions can be anonymous, passed as arguments, and created conditionally. Named function expressions (const f = function fact(n) {...}) help stack traces and recursion.

 Callbacks and handlers are usually expressions: app.get('/', async (req, res) => {...}). Utility functions at the bottom of a file are often declarations so the main logic can stay at the top. Either; teams pick one style. Declarations for named top-level functions (hoisted, good stack traces), arrows/expressions for callbacks and when you need lexical this. “Function expressions are hoisted like declarations.” Hoisting applied. What are arrow functions? A shorter function syntax with no own this, arguments, super or prototype, and they can’t be used with new. They take this from the surrounding scope. Arrow functions are always expressions. What’s the difference between call(), apply() and bind()? All three set this. call runs the function now with arguments listed; apply runs it now with arguments as an array; bind returns a new function with this (and optionally arguments) fixed, to call later. All three let you choose this explicitly. call and apply invoke the function immediately and differ only in how arguments are passed (list vs array). bind doesn’t call; it returns a new function permanently bound to the given this and any leading arguments (partial application); calling bind again on the result can’t change this. With spread syntax, fn.apply(ctx, args) is equivalent to fn.call(ctx, ...args).

When a property isn’t found on the object, JavaScript looks it up on the prototype, then that one’s prototype, up to Object.prototype. Classes are syntax on top of this. Every object has an internal [[Prototype]] link (read with Object.getPrototypeOf). What are higher-order functions? Functions that take functions as arguments or return functions. map, filter, reduce, setTimeout, Express’s app.use and middleware factories are all examples. Explain map(), filter() and reduce(). map transforms each element into a new array of the same length; filter keeps elements that pass a test; reduce folds the array into one value (a sum, an object, a map). None of them mutate the original array. map(fn) calls fn(element, index, array) for each element and collects the return values; filter(fn) keeps elements for which fn returns truthy; reduce(fn, initial) carries an accumulator through the array: each call receives the previous return value and the current element. Using map just to loop for side effects (use forEach/for…of), or forgetting reduce’s initial value. Fluency with everyday code. What’s the difference between shallow copy and deep copy? A shallow copy creates a new top-level object but nested objects are shared. A deep copy copies every level. Spread and Object.assign are shallow; structuredClone is deep. A shallow copy duplicates only the top-level container: its properties that are primitives are copied, but properties that are objects still point to the same nested objects. Spread, Object.assign, Array.from, arr.slice() are shallow. What are spread and rest operators? Same ... syntax, opposite jobs. Spread expands an array or object into elements or properties. Rest collects remaining elements or properties into one array or object. 2.2Asynchronous JavaScript

What is synchronous versus asynchronous execution? Synchronous code runs line by line and each line finishes before the next. Asynchronous code starts an operation, continues with other work, and handles the result later through a callback or promise.

In a server, one request waiting 2 seconds for an LLM shouldn’t stop 100 other requests. Async I/O lets the single thread serve them all while waiting.

No. Async means not waiting; the JS still runs on one thread. The waiting happens elsewhere (the OS, the database, the network). “async code runs on another thread.” Fundamental Node model. What are callbacks? Functions passed to another function to be called later, for example when I/O finishes. Node’s classic style is error-first: (err, result) => {}. A callback is just a function value handed to code that will call it at some point: immediately (array methods, synchronous callbacks) or later (timers, I/O, events). Node’s convention for async callbacks is error-first: the first argument is an error or null, results follow. The callback pattern’s problems are inversion of control (you trust the callee to call once, not twice, not never), error handling scattered across levels, and deep nesting.

History of async in Node. What is callback hell? Deeply nested callbacks where each async step depends on the previous one. It’s hard to read, error handling is repeated at every level, and it’s easy to forget a branch. Explain the different states of a Promise. Pending (not settled yet), fulfilled (has a value), rejected (has a reason). What’s the difference between concurrency and parallelism? Concurrency is dealing with many tasks at once by interleaving them (one thread switching while tasks wait). 2.3Event loop and Node.js runtime

What is the JavaScript event loop? The loop that takes completed async callbacks from queues and runs them on the single JS thread whenever the call stack is empty, always draining microtasks before the next macrotask.

Step through the widget in the lesson above. Order of priority: current synchronous code → nextTick queue (Node) → promise microtasks → the next macrotask (timer, I/O callback, setImmediate…) → microtasks again → …

 A request handler awaits a DB query; while it waits, the loop runs a timer callback, another request’s handler and a BullMQ worker callback; when the query result arrives, the loop resumes the first handler. The delay between when a callback should run and when it actually runs, caused by long synchronous work. Measure with perf_hooks.monitorEventLoopDelay() and alert when p99 lag grows. “The event loop is a thread.” It’s a loop running on the main thread. Core Node knowledge; often probed with an output-prediction question. What are the call stack, callback queue and microtask queue? The call stack holds currently running functions. The callback (task/macrotask) queue holds callbacks from timers and I/O waiting to run. The microtask queue holds promise reactions and queueMicrotask callbacks, which run as soon as the stack empties, before any macrotask. The call stack is a LIFO stack of execution frames: calling a function pushes a frame, returning pops it. Only when it is empty can queued callbacks run. The task (callback/macrotask) queue holds callbacks from timers, I/O and events; the loop takes one at a time. The microtask queue holds promise reactions and queueMicrotask callbacks; after every task (and in Node after every callback), the engine drains the entire microtask queue, including microtasks added while draining. setTimeout(A); Promise.resolve().then(B); C(); → C runs on the stack, then B (microtask), then A (task). Too many nested frames (usually infinite recursion): “Maximum call stack size exceeded”. “Promises go into the same queue as setTimeout.” Vocabulary. What’s the difference between microtasks and macrotasks? Microtasks (promise callbacks, queueMicrotask, and in Node process.nextTick in its own higher-priority queue) run all together right after the current task. Macrotasks (setTimeout, setInterval, I/O callbacks, setImmediate) run one at a time per loop step, with all microtasks drained between them. The distinction is priority and batching. One macrotask runs, then all microtasks, then rendering (browsers) or the next phase/callback (Node), then the next macrotask. So microtasks can starve macrotasks, and a promise callback always beats a 0 ms timer scheduled at the same time. In Node the order within the microtask stage is: the nextTick queue, then the promise queue, repeated until both are empty. 
setTimeout(() => console.log('macro'));
Promise.resolve().then(() => console.log('micro'));
// micro, macro
 The queue never empties, so timers and I/O never run: the server freezes even though nothing is “blocking” in the usual sense. “Microtasks are smaller tasks.” The name is about scheduling, not size. Ordering knowledge. What is the Node.js event loop? libuv’s loop with six phases: timers, pending callbacks, idle/prepare, poll, check, close callbacks. Each phase has a queue; between every callback Node drains nextTick and promise microtasks.
  • timers: expired setTimeout/setInterval callbacks.
  • pending callbacks: some deferred system errors (e.g. TCP errors).
  • idle/prepare: internal.
  • poll: wait for new I/O and run its callbacks; if nothing is pending, it may block here until a timer is due.
  • check: setImmediate callbacks.
  • close: e.g. socket.on('close').
 An HTTP server: incoming connection data is detected in the poll phase, your handler runs, its DB callbacks also come back in later poll phases; a setImmediate used to yield after a CPU chunk runs in the check phase. When the loop has nothing left to do: no pending timers, no open handles (sockets, servers, intervals) and no pending I/O. unref() on a timer lets the process exit even if it’s pending. “Node’s loop is the same as the browser’s.” Same idea, different phases and queues (nextTick, setImmediate). Node-specific depth. What is libuv? The C library under Node that provides the event loop, async networking via the OS (epoll, kqueue, IOCP), a thread pool (default 4 threads) for file system, DNS lookup, some crypto and zlib, plus timers and child processes. Node’s JavaScript engine (V8) has no I/O. libuv provides a cross-platform abstraction: it uses each OS’s readiness/completion mechanism (epoll on Linux, kqueue on macOS, IOCP on Windows) for sockets, so thousands of connections need no threads; it runs the event loop with its phases; and it has a thread pool for operations the OS can’t do asynchronously in a portable way: file system calls, dns.lookup, and CPU-heavy built-ins like crypto.pbkdf2, scrypt and zlib compression. 10 concurrent bcrypt.hash calls on the default pool: 4 run at once, 6 queue. Under load that looks like slow logins while CPU is not maxed. Many concurrent file reads, bcrypt hashes or zlib jobs queue behind 4 threads. You can raise UV_THREADPOOL_SIZE (set before startup). Network sockets don’t use the pool. “libuv runs your JavaScript in its thread pool.” Understanding beneath the API. What’s the difference between setTimeout() and setImmediate()? setTimeout runs in the timers phase after at least the delay; setImmediate runs in the check phase right after poll. Inside an I/O callback, setImmediate always runs first. In the main module their order is not guaranteed.

See the “setImmediate vs setTimeout in I/O” example in the widget.

 In a request handler that reads a file and then wants to “defer” work until after the current I/O phase, setImmediate is the predictable choice. setImmediate between chunks, so I/O callbacks get a chance to run (nextTick or promises would starve them). “setTimeout(fn, 0) and setImmediate are identical.” Detailed Node knowledge. What is process.nextTick()? Node’s way to schedule a callback to run right after the current operation, before promise microtasks and before the event loop continues. It’s used inside Node’s APIs to make callbacks consistently async. process.nextTick(fn) queues fn in a Node-specific queue that is processed after the current operation completes, before promise microtasks and before the event loop continues to any phase. Node’s own APIs use it to emit events asynchronously but before any I/O (so listeners attached right after creating an object still receive events). Because it runs before I/O, recursive nextTick calls starve the event loop entirely. In ES modules the module body runs inside a promise job, so promise callbacks queued in the main module run before nextTick callbacks (verified: CJS prints A E D C B, ESM prints A E C D B). Node’s stream implementation uses nextTick to emit 'error' after the constructor returns, so stream.on('error', ...) attached on the next line still catches it. Almost never in app code. nextTick for “after this function returns but before anything else” (e.g. emit an event after the caller attached listeners). setImmediate for “yield to I/O first”; it’s the safer default. “nextTick runs on the next loop iteration.” It runs before the loop moves on at all; setImmediate is the one that waits. Node depth. Does Node.js execute JavaScript in multiple threads? Your JavaScript runs on one main thread. Node itself uses extra threads (libuv thread pool, V8’s garbage collector and compiler). You get JS parallelism only with worker_threads, child processes, or running several processes (cluster, PM2, containers). The process has several threads (V8 helpers for garbage collection and compilation, libuv’s pool, possibly worker threads), but each JavaScript context runs on exactly one thread at a time, so your request handlers never run in parallel with each other in one process. To use multiple cores you run multiple processes (the cluster module, PM2, several containers behind a load balancer) or worker threads for specific CPU-bound tasks. Shared state then has to live outside (Redis, the database). A Render or Kubernetes deployment with 3 instances = 3 independent Node processes; an in-memory rate limiter then counts per instance, not globally (DocMind’s limiter has this limitation). Forks several Node processes sharing one server port; the primary distributes connections. Each worker has its own memory. “Node is multi-threaded because of libuv, so handlers run in parallel.” Accurate model. What is the worker thread module? node:worker_threads runs JavaScript in separate threads, each with its own V8 instance and event loop, communicating via messages (and optionally SharedArrayBuffer). Use it for CPU-heavy work so the main thread keeps serving requests. Each worker thread has its own V8 isolate, heap and event loop, so they don’t share JS objects; they communicate by postMessage (data is structured-cloned) or by transferring ArrayBuffers or sharing SharedArrayBuffer memory. Creating a worker costs tens of milliseconds and memory, so use a pool (e.g. Piscina) for repeated jobs. Use them for CPU-bound work (parsing large files, image processing, local embedding models); don’t use them for I/O, which is already async.

What is the difference between CPU-bound and I/O-bound operations? CPU-bound work is limited by computation (hashing, image resizing, big JSON parsing). Why can a CPU-intensive operation block a Node.js server? Because all requests share one JS thread. While a callback is computing, the stack is never empty, so the event loop can’t run any other callback: every other request waits, timeouts fire, health checks fail. Node runs all your JavaScript callbacks on one thread. That’s why CPU-heavy work goes to worker threads, a separate service, or a queue.

• Answer all 15 behavioural questions with real stories, structured but not rehearsed-sounding.
  • Talk about AI-assisted coding honestly: how you use it, how you verify it.
  • Phase 1 (introduction and the gap answer). Have 4–5 real stories ready; most questions can reuse them.
  • Sample answers use real events from DocMind’s logs. Only tell a story you actually remember living through; adjust details to your memory.
 Behavioural questions ask for past behaviour as a predictor of future behaviour. Use STAR: Situation (one sentence), Task (your responsibility), Action (what you did, the longest part), Result (outcome + what you learned).
  • Not rehearsed: memorise the story’s facts, not sentences. Start differently each time. Include one specific detail (an error message, a number) that only someone who was there would know.
  • Length: 60–90 seconds, then stop and let them ask.
  • Independent learning: you don’t have team stories, so use solo ones honestly and add “in a team I would…” where relevant.
  • Employment gap: the formula in Phase 1 (fact → choice → evidence → what changed → now).
  • “We did…” when it was you, or “I did…” when it was a team.
  • Stories with no result or no lesson.
  • Blaming tools, teammates, or the market.

17.1Questions

Tell me about a time you couldn’t solve a technical problem.Pick one where you got stuck, changed approach, and either solved it later or worked around it honestly. The interviewer checks how you behave when stuck: do you persist methodically, ask for help at the right time, change approach, and learn? A good story has a real block, the specific steps you tried, the moment you changed strategy (measuring, reading source, asking someone), and the outcome, even if the outcome was a workaround.Strong: “My rate limiter on Render kept putting requests from one user into different counters. I tried trust proxy 1, then 2, and both were wrong. I was guessing, so I stopped and found a way to measure: the RateLimit-Policy header contains a hash of the key, so I compared it with a hash of my real IP. That showed Render has Cloudflare plus its own proxies in front, and 3 was right. Lesson: when I’m guessing twice in a row, I need a measurement.”
Weak: “I never get stuck, I always find it on Stack Overflow.” After a time box (e.g. an hour or two of focused attempts) with my notes ready: what I tried, what I observed, what I suspect. A story with no specifics, or one where someone else solved it and you can’t explain how. Persistence, method, honesty. How do you approach debugging?Reproduce, read the actual error and logs, find which component fails by timing or bisecting, form one hypothesis at a time and test it, fix the root cause, then add a test or a log so it can’t come back silently. Describe a repeatable method, not luck: reproduce reliably; read the full error and logs; narrow down the component (binary search, timing, removing parts); form one hypothesis; test it with a measurement; fix the root cause; add a regression test or log; write down what you learned.“My streamed answers sometimes showed nothing. I logged the raw bytes and saw Gemini ends lines with \r\n and a \r\n could be split across two reads, so I normalised line endings on the whole buffer instead of per chunk.” Structured logs with request ids, the debugger and breakpoints, network inspection, EXPLAIN ANALYZE for queries, and small scripts to reproduce issues in isolation. “I add console.log everywhere until it works.” Method (Phase 12). What do you do when documentation is insufficient?Read the library’s source and types, write a tiny experiment script to observe the behaviour, search issues, and write down what I found for the next person. Show self-sufficiency with judgement: read the source code and type definitions, search issues and changelogs, write a minimal experiment to observe behaviour, check what version you’re actually using, and ask maintainers or the community with a minimal reproduction; then document what you found for the team.“Before planning workflows I read Mastra’s package source and its bundled docs to confirm the recovery setting and that bail() ends a run as success. For Gemini’s function calling I wrote a probe script with 17 real calls and found the model ignored mode NONE, which changed my design.” Check the date and version they target, and verify against the installed version’s docs or source. “I just guess until it works.” Self-sufficiency. How do you decide whether to use AI assistance or solve something independently?I use AI to speed up things I understand and to explain things I don’t yet, but I make sure I can explain and defend every line that ships. For core logic I’m learning, I build it step by step and test it myself first.

Show judgement: boilerplate, docs, test scaffolding → assist freely. Security, data isolation, concurrency → design it yourself, review line by line, test adversarially.

 Core security logic like ownership scoping in queries: I designed and tested it myself, then used AI only to review it. “I never use AI” (unbelievable) or “AI writes most of my code” without the verification part.Modern work habits + ownership. Have you ever used AI-generated code that caused a problem?Yes. Tell one concrete case, how you caught it, and what you changed in your process. Interviewers want honesty and evidence that you learned to verify. A good answer names a real problem, how you caught it (review, test, runtime error), the fix, and the process change you made (reading diffs, tests, checking APIs against docs).“A generated script edited a TypeScript file through a shell heredoc, and the shell turned a written \n into a real line break inside a string. It compiled weirdly and I caught it in review. Since then, edits containing escape sequences go through the editor, not shell scripts, and I read diffs before committing.” Review every diff line by line, run the type checker and tests, and test edge and failure paths before committing. “AI code never caused me problems.” Honesty and learning. How do you verify code generated by AI?Read every line and make sure I can explain it; run the type checker and tests; test edge cases and failure paths deliberately (bad input, network off, another user’s id); check library APIs against the docs for the version I use; review the diff before committing. Treat generated code like a pull request from an unknown contributor: understand every line, check it against the requirements, run it, test failure paths, check library APIs for your version, look for security issues (injection, auth checks, secrets), and keep changes small enough to review. Generated Express code using req.query = …: that fails in Express 5 (read-only); reading the docs for your version catches it. APIs you’ve never seen, missing error handling, confident comments about behaviour you can’t verify, and code that “works” only on the happy path. “If it compiles, it’s fine.” Ownership. How do you approach code reviews?As the author: small PRs with a clear description and how I tested it. As a reviewer: correctness and security first, then readability, kind and specific comments with reasons, and questions rather than orders. As an author: small focused PRs, a description of what and why, how it was tested, screenshots or logs, and responsiveness to comments without defensiveness. As a reviewer: understand the goal first, check correctness, security and edge cases, then design and readability; comment kindly and specifically with reasons, separate blocking issues from suggestions, and approve when it’s good enough. “This query filters by document id only; could another user read it? Suggest adding AND user_id = $2.”My auth work went through a PR (#3) with a written plan and a per-step results log. Explain your reasoning briefly; if it remains a preference, follow the reviewer or team convention. “I just approve if tests pass.” Collaboration. How would you respond if a senior developer disagreed with your implementation?Ask them to explain their concern, restate it to be sure I understood, share my reasoning briefly with any data I have, and if it’s still a judgement call, go with their decision and learn from it. If it’s a correctness or security issue, I’d say so clearly with evidence. Show you separate ego from code: listen and restate their concern, share your reasoning and evidence (benchmarks, constraints), look for the underlying goal you both share, and defer to their experience on judgement calls while still raising correctness or security concerns clearly. Afterwards, learn from the outcome. “They preferred a queue over doing it inline; I explained my latency concern, we measured, and the queue was the better choice for retries.” Bring evidence (a test, a benchmark, docs); if it’s still disputed, escalate respectfully or try it in a small experiment. “I’d just do it my way.” or “I’d never disagree with a senior.” Humility + spine. What would you do if you were assigned a task involving an unfamiliar technology?Read the official docs’ core concepts, build the smallest working version in a scratch project, then apply it to the task in small steps, and ask early if I’m blocked for more than a set time. Show a learning plan: read the official getting-started and core concepts, build a tiny prototype, read existing code in the team that uses it, pair with someone who knows it, then deliver the task in small steps, asking questions early and noting what you learned for others.“I learned MySQL and Ruby on Rails basics in one session before a walk-in interview; for BullMQ I wrote a learning script that measured an idle worker’s Redis commands before using it in DocMind.” Usually days for a library, longer for a new language; I prefer to show progress early with small pieces. “I’d avoid unfamiliar tasks.” Learning speed. How do you prioritize multiple tasks?By impact and urgency, unblock others first, and check priorities with my lead when unsure. I break work into small deliverable pieces so something useful ships even if plans change. Prioritise by impact and urgency (and by who’s blocked), confirm priorities with the lead when they conflict, break tasks into small deliverables, timebox, and communicate trade-offs (“if I do X today, Y moves to Thursday”). A production bug affecting users beats a feature; a reviewer blocked on my PR gets my response before I start new work. Batch them where possible, protect focus blocks, and make interruptions visible to the lead if they affect commitments. “I do whatever comes first.” Planning. What do you do when you cannot meet a deadline?Tell the person as soon as I know, with what’s done, what’s left, a new estimate and options (cut scope, get help, move the date). Never on the last day. The interviewer checks transparency and ownership: raise the risk early, explain why (scope, unknowns), offer options (reduce scope, extra help, new date), and agree on a plan; never surprise people on the due date. “Two days before, I saw the integration would take longer; I told my lead, we shipped the core path on time and the admin screen two days later.” Break work into smaller pieces, add buffer for unknowns, compare estimates with actuals. “I’d work all night and not tell anyone.” Communication. Are you comfortable receiving critical feedback?Yes, it’s the fastest way to improve, and it’s the thing I’ve missed working alone. Give an example of feedback you acted on. Show you seek feedback and act on it: thank, ask clarifying questions, separate the feedback from your identity, apply it, and follow up to check you improved.Use a real one you remember, for example feedback after an interview that went badly: what they said, what you changed (e.g. practising explaining projects out loud), and what improved. Specifically: “Was my PR description clear enough?”, “What would you have done differently in this design?” “Yes, I’m fine with feedback” with no example. Coachability. How do you ensure your code is maintainable?Clear layers (routes, services, repositories), small functions with honest names, types and validation at boundaries, comments that explain why, tests for the important paths, and docs that stay in sync with the code. Maintainable code is easy for someone else (or you in six months) to understand and change safely: clear names and structure, small functions with one job, consistent layering, types and validation at boundaries, tests for important behaviour, comments explaining why, no clever tricks without reason, and docs/runbooks for non-obvious operations. DocMind’s rule that only repositories touch SQL, and that every repository function requires userId, makes a whole class of bugs easy to spot. A new person can make a change confidently; tests catch regressions; reviews are fast. “Comment every line.” Craft. What does writing production-quality code mean to you?Code that’s correct for edge cases, secure by default, observable (logs, metrics), handles failures (timeouts, retries, clear errors), is tested, and that someone else can understand and change safely. Production quality means correct under real conditions, not just the happy path: input validation, error handling with useful messages, timeouts and retries for dependencies, security (auth, authorization, secrets), observability (logs, metrics), tests, performance that meets requirements, backwards-compatible changes and migrations, and documentation for operators. The difference between “calls the LLM” and “calls the LLM with timeout, retries, validation, usage logging and a fallback”. Some polish and scale work, but never authorization, secrets handling or data-loss risks. “Code with no bugs.” Standards. What would you expect from your first engineering team?Code reviews that teach me, clear expectations, someone I can ask when stuck, and ownership of real features with support. In return I’d bring effort, honesty about what I don’t know, and fast learning. The interviewer checks expectations and fit. Ask for things that help a junior grow: code review, mentorship, clear expectations, real ownership, and a culture where asking questions is normal; and say what you’ll bring. Avoid negativity; say you value learning, feedback and ownership, and you’d raise problems early. Only asking about salary and remote days. Fit.

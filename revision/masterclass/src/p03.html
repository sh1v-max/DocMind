3.ANode.js under the hood

Node.js is a runtime that runs JavaScript outside the browser. It combines the V8 engine (compiles and runs JS) with libuv (event loop, async I/O, thread pool) and a standard library (http, fs, crypto, streams). Classic servers used one thread per connection. Threads cost memory and context switches, and most of their time is spent waiting on I/O. Node’s bet: one thread runs your code, the OS waits on sockets for you, and callbacks fire when data is ready. That makes I/O-heavy servers (APIs, chat, proxies, LLM gateways that mostly wait) cheap to run.
  1. Your code calls db.query(). Node sends bytes on a socket and registers interest in the reply with the OS (epoll/kqueue/IOCP). It returns immediately with a pending promise.
  2. The thread runs other callbacks (other requests).
  3. The reply arrives; in the poll phase libuv sees the socket is readable and queues the callback; the promise resolves; your await continues as a microtask.
  4. File system calls, DNS lookups, crypto (pbkdf2, scrypt) and zlib run on libuv’s thread pool (default 4 threads) because many OSes don’t offer good async file APIs.
 A restaurant with one very fast waiter and a kitchen full of cooks. The waiter never stands at the stove; they take orders and deliver plates when the bell rings. An LLM chat endpoint spends ~99% of its time waiting for the provider. One Node process can hold hundreds of such requests open, as long as none of them does heavy CPU work on the main thread.
  • “Node is single-threaded.” JS execution is; the process isn’t.
  • Using sync APIs (fs.readFileSync, bcrypt.hashSync) inside request handlers.
 A Buffer is a fixed-size chunk of raw bytes. A stream is data that arrives or leaves piece by piece, so you can process it without holding all of it in memory. Reading a 2 GB file with readFile needs 2 GB of RAM (Render free has 512 MB). A stream reads ~64 KB at a time. Streams also let you start sending a response before it’s finished, which is exactly how LLM token streaming works.
  • Readable (fs.createReadStream, an HTTP request body), Writable (fs.createWriteStream, an HTTP response), Duplex (both, e.g. a TCP socket), Transform (a duplex that changes data, e.g. gzip).
  • Backpressure: when the writer is slower than the reader, write() returns false; a correct pipeline pauses reading until the drain event. stream.pipeline() does this and handles errors and cleanup.

3.BExpress and the mini application

Express is a thin layer over Node’s http module: it gives you routing and a middleware pipeline. Every request walks through middleware functions in registration order until one sends a response.

A middleware is (req, res, next) => {}. It can read/modify req and res, end the request (res.json()), call next() to continue, or call next(err) to jump to error handlers. Error handlers have four parameters (err, req, res, next). In Express 5, a rejected promise from an async handler is forwarded to next(err) automatically.

 An airport: check-in (parse), security (auth), passport control (validation), gate (handler). Fail at security and you never reach the gate; you’re sent to the help desk (error handler).

  • Calling next() after sending a response: “Cannot set headers after they are sent”.
  • Putting requireAuth before cors(): the browser’s preflight has no token and fails.

      const claim = await client.query(
        'INSERT INTO idempotency_keys (user_id, key) VALUES ($1, $2) ON CONFLICT DO NOTHING RETURNING key', [userId, key]);
      if (claim.rowCount === 0) {
        await client.query('ROLLBACK');

 Authentication proves who you are. A JWT is a signed token carrying claims (like the user id) that the server can verify without a database lookup. bcrypt is a slow, salted password hash. HTTP is stateless: every request must prove identity again. Sending the password every time is dangerous; a short-lived signed token is safer. Passwords must be hashed so a stolen database doesn’t reveal them.

A JWT is base64url(header).base64url(payload).base64url(signature). With HS256, signature = HMAC-SHA256(header.payload, secret). Anyone can read the payload; only the secret holder can produce a valid signature.

Access + refresh token pattern:

  • Access token: short-lived (5–15 min), sent as Authorization: Bearer.
  • Refresh token: long-lived (days), random opaque string stored hashed in a refresh_tokens table, sent in an httpOnly; Secure; SameSite=Strict cookie to one path (/auth/refresh).
  • On refresh: look it up, check not revoked/expired, rotate (delete old, issue new), return a new access token. If a revoked token is used again, treat it as theft and revoke the whole family.
  • Logout = delete the refresh token row. Access tokens die on their own within minutes.
import crypto from 'node:crypto';
const sha256 = (s) => crypto.createHash('sha256').update(s).digest('hex');

app.post('/auth/refresh', async (req, res) => {
  const raw = req.cookies?.rt;                      // needs cookie-parser
  if (!raw) throw new HttpError(401, 'No session');
  const { rows } = await pool.query(
    'DELETE FROM refresh_tokens WHERE token_hash = $1 AND expires_at > now() RETURNING user_id', [sha256(raw)]);
  if (!rows[0]) throw new HttpError(401, 'Session expired');   // deleted = used once (rotation)
  const next = crypto.randomBytes(32).toString('base64url');
  await pool.query("INSERT INTO refresh_tokens (user_id, token_hash, expires_at) VALUES ($1, $2, now() + interval '7 days')",
    [rows[0].user_id, sha256(next)]);
  res.cookie('rt', next, { httpOnly: true, secure: true, sameSite: 'strict', path: '/auth/refresh', maxAge: 7 * 864e5 });
  res.json({ token: jwt.sign({}, JWT_SECRET, { subject: rows[0].user_id, expiresIn: '15m' }) });
});

3.1Node.js

What is Node.js? A JavaScript runtime built on Chrome’s V8 engine and libuv. It runs JS on servers with an event-driven, non-blocking I/O model, plus a standard library for HTTP, files, crypto and streams. A runtime is the environment that executes code and provides APIs. Node takes V8 (Chrome’s JS engine: parses, compiles with JIT, garbage-collects) and adds what servers need: libuv for the event loop and async I/O, C++ bindings for networking, files, crypto and compression, and a module system. Your code calls fs or http; those call into C++; slow work is handed to the OS or libuv’s thread pool; results come back as callbacks. Running node server.js starts one process: V8 runs the file, app.listen asks libuv to watch a socket, and the process stays alive because that handle is open. V8 first interprets bytecode (Ignition), watches which functions are hot and what types they see, then compiles those to optimised machine code (TurboFan); if assumptions break (types change), it deoptimises. “Node is a framework” or “a language”. It’s a runtime; Express is the framework. Basics. Why is Node.js suitable for backend development? It handles many concurrent I/O-bound connections efficiently on one thread, shares a language and JSON with the frontend, has a huge package ecosystem, and is natural for streaming (SSE, WebSockets). Most backend time is waiting: on databases, other APIs, LLM providers. Node’s non-blocking model holds thousands of waiting requests with little memory, while thread-per-request servers spend memory and context switches on idle threads. Other reasons: one language across frontend and backend (shared types and validation like Zod), JSON-native, a huge npm ecosystem, good streaming primitives (SSE, WebSockets), fast startup for serverless. An LLM gateway that forwards requests and streams tokens back is the ideal Node workload: almost no CPU per request, lots of waiting, long-lived streaming responses. CPU-heavy work (video encoding, ML inference, big number crunching) unless offloaded to workers or other services. “Node is faster than Java/Go.” It isn’t generally faster; it’s efficient for I/O-bound concurrency. Trade-off awareness. What is non-blocking I/O? Starting an I/O operation and continuing with other work instead of waiting. The result is delivered later through a callback or promise, so one thread can serve many requests that are all waiting on I/O. Blocking I/O makes the calling thread sleep until data arrives. Non-blocking I/O asks the OS to start the operation and returns immediately; the OS notifies the program when data is ready (readiness via epoll/kqueue, or completion via IOCP). libuv collects these notifications in the poll phase and runs your callbacks. Because the thread never sleeps on one socket, it can serve many. While request A waits 3 s for an LLM, requests B to Z are parsed, queried and answered. From your code’s view yes, but internally it runs on libuv’s thread pool because portable async file APIs are limited; network I/O uses the OS’s async mechanisms directly. “Non-blocking means multi-threaded.” Core concept. What is the difference between Node.js and browser JavaScript? Same language and engine family, different environments. The browser has the DOM, window, fetch, localStorage and a security sandbox. Node has fs, process, Buffer, http, child processes, require/ESM loading from disk, and no DOM.

Event loops also differ: Node has libuv phases, process.nextTick and setImmediate. Modern Node also has fetch, Web Streams, AbortController and Web Crypto built in.

 window, document, localStorage exist only in browsers; process.env, fs, Buffer, __dirname (CommonJS) only in Node. That’s why server-only code (API keys) can’t be imported into frontend bundles safely. Browser code runs on the user’s machine and is fully visible and modifiable; Node code runs on your server and can hold secrets and talk to private databases. “Node uses a different JavaScript language.” Environment awareness. What are Node.js streams? Objects that read or write data in chunks over time instead of all at once, which keeps memory constant and lets processing start immediately. They handle backpressure so a fast producer doesn’t flood a slow consumer. A stream emits data in chunks (Buffers or strings, or objects in object mode). Readable streams have two modes: flowing (data events) and paused (read() / async iteration). Writable streams accept chunks via write() and signal backpressure by returning false when their internal buffer passes highWaterMark. Pipes connect them and handle pausing/resuming automatically. Modern code uses for await (const chunk of readable) and stream/promises.pipeline. Streaming an S3 download to the HTTP response; parsing a large CSV line by line; forwarding LLM tokens as SSE. The consumer telling the producer to slow down so data doesn’t pile up in memory. “Streams are only for files.” Sockets, HTTP requests/responses, zlib, crypto and process.stdout are all streams. Memory-aware design. What are readable, writable and duplex streams? Readable produces data (file read, request body). Writable consumes it (file write, response). Duplex does both independently (TCP socket). A Transform is a duplex whose output is computed from its input (gzip, CSV parser). Readable: a source you read from (fs.createReadStream, an incoming HTTP request, process.stdin). Writable: a destination (fs.createWriteStream, an HTTP response, process.stdout). Duplex: two independent channels in one object, like a TCP socket where reading and writing are unrelated. Transform: a duplex where the output is derived from the input (zlib.createGzip, a CSV parser). You can implement your own by extending the classes or with new Transform({ transform(chunk, enc, cb) {...} }). Upload pipeline: request (readable) → a transform that computes SHA-256 as bytes pass → S3 upload stream (writable).

3.2Express.js

What is Express.js? A minimal web framework for Node that adds routing, a middleware pipeline and helpers on top of the http module. Express wraps Node’s http server. It adds: a router that matches method + path (with params like /docs/:id), a middleware chain, request/response helpers (req.params, req.query, res.json, res.status), error-handling middleware, and sub-routers for structuring apps. It’s deliberately unopinionated: you choose validation, ORM and structure. Express 5 adds native promise support (rejected async handlers go to the error handler) and stricter path syntax. const app = express(); app.use(express.json()); app.get('/health', (req, res) => res.json({ ok: true })); app.listen(3000); Fastify: faster routing and built-in schema validation/serialisation; NestJS: an opinionated framework with dependency injection for large teams. “Express is a server.” It runs on Node’s http server. Basics. How does an Express request-response lifecycle work? Node parses the HTTP request into req; Express runs matching middleware and routes in registration order; each calls next() or ends the response; errors skip to error-handling middleware; the response is sent once.

What happens when you call next()? Express runs the next matching middleware or route. next(err) skips to the next error handler. next('route') skips the remaining handlers of the current route. Why does Express have a particular middleware execution order? Web security basics. What is preflight handling? Before a “non-simple” cross-origin request (e.g. with an Authorization header, JSON content type, or PUT/DELETE), the browser sends an OPTIONS request asking which methods and headers are allowed. How would you implement pagination? Offset/limit for small or admin lists; cursor (keyset) pagination for large or live lists: order by a unique, stable key and ask for rows after the last one seen. 3.3Authentication and security

What is authentication? Verifying who someone is: password, token, OAuth login, API key. Authentication answers “who is making this request?” with evidence: something you know (password), have (a device, a key) or are (biometrics), or a token issued after one of those. In APIs the evidence per request is usually a session cookie, a JWT, an API key, or an OAuth access token. Multi-factor authentication combines two kinds. Logging in with email + password, then sending the JWT on every request. Delegated authorisation: letting an app act on your behalf at another service (e.g. read your Google Drive) without sharing your password. “Login with Google” uses OpenID Connect on top of it. Confusing it with authorization. Basics. What is authorization? Deciding what an authenticated identity may do or access: this user may read their own documents but not yours; admins may delete. Authorization runs after authentication, on every access: does this identity have permission for this action on this resource? Models: ownership checks (user_id on the row), roles (RBAC: admin, member), attributes (ABAC: department, plan), or ACL entries (shared documents). It must be enforced on the server at the data layer; hiding a button in the UI is not authorization. Logging in proves you’re Asha (authentication). Being allowed to open document 42 depends on whether it’s Asha’s (authorization). What is JWT? JSON Web Token: a compact, signed token with JSON claims (like the user id and expiry). The server can verify it with a key, without storing sessions. Where should tokens be stored? Trade-off. An httpOnly, Secure, SameSite cookie can’t be read by JavaScript (protects against XSS theft) but needs CSRF protection and works best on the same site. localStorage or memory is simple for cross-site APIs but readable by any XSS. Hashing is one-way: you can’t get the input back, only compare. Encryption is two-way: with the key you can decrypt. Passwords are hashed; data you need to read again (API keys of your users, tokens to third parties) is encrypted. Hashing maps input to a fixed-size digest with no key and no way back; you verify by hashing again and comparing. Encryption uses a key to transform data so it can be decrypted with the (same or paired) key. What is REST? An architectural style for HTTP APIs: resources identified by URLs, manipulated with standard methods, stateless requests, standard status codes and representations like JSON. REST models an API as resources (nouns) with URLs, manipulated through a uniform interface of HTTP methods with standard semantics (safe, idempotent), stateless requests (each carries its own auth and context), representations (JSON) and status codes; responses can be cacheable. In practice “RESTful” means predictable URLs, correct methods and status codes, and consistent error and pagination formats. GET /documents, POST /documents, GET /documents/:id, PATCH /documents/:id, DELETE /documents/:id, GET /documents/:id/chunks. As creating a resource (POST /quizzes → 202 with a quiz id) or a sub-resource action (POST /documents/:id/quiz); either is fine if consistent. Verbs in URLs for everything (/getDocuments), or 200 with an error in the body. Basics. What are HTTP methods? GET reads, POST creates or triggers actions, PUT replaces, PATCH partially updates, DELETE removes; HEAD and OPTIONS are metadata. GET, HEAD, PUT and DELETE are idempotent; POST and PATCH aren’t guaranteed to be. Safe methods (GET, HEAD, OPTIONS) must not change state, so they can be cached, prefetched and retried freely. Idempotent methods (GET, HEAD, PUT, DELETE, OPTIONS) give the same end state when repeated, so clients and proxies may retry them after a timeout. POST (create/act) and PATCH (partial change) are not guaranteed idempotent, so retries need idempotency keys. A proxy retrying a timed-out DELETE /documents/5 is harmless; retrying POST /payments without a key double-charges. Yes: idempotency is about server state (still deleted), not identical responses. “POST is for sending data, GET for reading” with no idea of safety/idempotency. Basics. Explain HTTP status codes: 200, 201, 400, 401, 403, 404, 409, 429 and 500. 200 OK; 201 Created; 400 bad input; 401 not authenticated; 403 authenticated but not allowed; 404 not found; 409 conflict with current state; 429 too many requests; 500 server bug. 2xx success: 200 OK (with body), 201 Created (new resource; often a Location header), 202 Accepted (queued), 204 No Content. 4xx client errors: 400 malformed/invalid input, 401 missing/invalid credentials, 403 authenticated but not allowed, 404 not found (or hidden), 409 conflicts with current state (duplicate, wrong status), 422 semantically invalid (some APIs use it for validation), 429 rate limited (with Retry-After). 5xx server errors: 500 bug, 502 bad upstream response, 503 temporarily unavailable, 504 upstream timeout.

What is idempotency? An operation is idempotent if doing it once or many times leaves the system in the same state. DELETE /docs/1 twice → still deleted. POST /payments twice → two payments, unless you add an idempotency key. Formally f(f(x)) = f(x). In APIs: repeating the same request leaves the server in the same state as doing it once, although responses may differ. It matters because networks fail ambiguously: a client that timed out doesn’t know whether the server acted, and the only safe retry is an idempotent one. Techniques: natural idempotency (PUT, DELETE, “set status = ready”), idempotency keys for creates, unique constraints, and upserts. “Mark document ready” is idempotent; “append a chunk” isn’t, unless the chunk has a unique (document_id, chunk_index). It should be; a GET that changes state (e.g. /logout or /delete?id=) breaks caches, prefetchers and crawlers. “Idempotent means it returns the same response.” Reliability concept. Why is idempotency important in payment APIs and AI workflows? Retries are unavoidable (timeouts, crashes, double clicks). In payments a duplicate charges twice; in AI workflows a duplicate spends tokens again and saves duplicate modules or lessons. Idempotency makes retries safe. Payments: the cost of a duplicate is direct money loss and trust; providers like Stripe accept an Idempotency-Key header and replay the original result. AI workflows: steps are slow, retried often (429s, crashes, recovery) and cost tokens; a duplicated step creates duplicate content, double charges for tokens, and can send duplicate emails or webhooks. Idempotency turns “at-least-once” execution, which queues and workflow engines give you, into “effectively once”. A course workflow re-runs lesson 7 after a crash; ON CONFLICT (course_id, module_no, lesson_no) DO NOTHING plus a “skip if exists” check means no duplicate lesson and no second LLM call. Practically impossible across a network; systems deliver at-least-once and make processing idempotent. “Retries are rare, so it doesn’t matter.” Applied reliability. What is API versioning? Keeping old clients working while the API changes, via a version in the path (/v1), a header, or by only making additive changes. Breaking changes go to a new version with a deprecation period. What is a message queue? A buffer between producers and consumers: producers add messages/jobs, workers take them and process them at their own pace, with acknowledgements and retries. Reliability design. What is exponential backoff? Waiting longer after each failure: e.g. 0.5 s, 1 s, 2 s, 4 s, usually capped and with random jitter, so a struggling service gets room to recover and clients don’t retry in sync. After failure n, wait about base × 2^n (with a cap), usually randomised (jitter). The growth gives a struggling dependency time to recover instead of being hammered; the cap bounds worst-case delay; jitter prevents synchronized retry waves when many clients failed at the same moment. It’s used in TCP, cloud SDKs and job queues (BullMQ’s exponential backoff). base 500 ms → 500, 1000, 2000, 4000 ms (capped at 8000); with full jitter each wait is random between 0 and that value. Each delay is random between base and 3 × previous delay (capped): spreads retries well and avoids long fixed waits. “Backoff means waiting the same time between retries” (that’s fixed delay).

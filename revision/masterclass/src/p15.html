  • MCP (Model Context Protocol), started by Anthropic: an MCP server exposes tools (functions the model can call), resources (readable data like files or records, addressed by URI) and prompts (reusable templates). Problem solved: any frontend can render any agent backend’s progress, tool calls and shared state.

Together: the UI talks AG-UI to your agent; your agent uses MCP servers for tools and data, and A2A to delegate to other agents.

  • Prompt chaining: split a task into several LLM calls where each output feeds the next (outline → sections → polish). Easier to validate and debug than one giant prompt.
  • Context compression: shrink what you send: summarise old history, trim tool results, extract only relevant sentences from chunks, deduplicate; keep a token budget.
  • Semantic caching: embed the incoming prompt; if a previous prompt is similar above a strict threshold (and same user scope/document version), return the cached answer. Risky for personalised or time-sensitive answers; exact caches and provider prompt caching are safer first steps.
  • Guardrails: checks before and after the model: input (length, PII, abuse, injection heuristics, topic scope) and output (schema, toxicity, grounding, no secrets, no HTML).
  • Model routing: choose a model per request by task or difficulty (small model for classification/rewrites, large for hard generation). DocMind’s intent router is routing of a different kind (paths, not models).
  • Fallback routing: an ordered list of models/providers tried on failure (with circuit breakers).
  • Evaluation frameworks: datasets + metrics + runners (e.g. RAGAS-style metrics, promptfoo, framework evals) to compare versions before shipping.
  • Observability: logs (events), metrics (numbers over time), traces (one request’s path as nested spans), plus AI-specific data: prompts, model, tokens, cost, tool calls, latency per step. OpenTelemetry with GenAI attributes, or LLM-tracing tools (Langfuse, LangSmith, Mastra’s tracing).

What is LangChain?A popular open-source library for building LLM applications from components: models, prompts, document loaders, text splitters, retrievers, tools and agents, with many integrations. LangChain offers abstractions and integrations for every stage of an LLM app: chat model wrappers for many providers, prompt templates, output parsers, document loaders and text splitters, embedding and vector store integrations, retrievers, tools and agents, and a composition syntax (LCEL) to pipe components. It’s popular for prototyping RAG quickly; critics point to deep abstractions that can make debugging and customisation harder. A RAG prototype: PDF loader → RecursiveCharacterTextSplitter → embeddings → vector store retriever → prompt → chat model, in a few dozen lines. Possibly for its integrations; many teams keep core logic in their own code and use only selected pieces. “LangChain is a model.” Awareness. What is LangGraph?A library from the LangChain team for orchestrating agents and workflows as graphs: nodes do work, edges (including conditional and cyclic ones) decide what runs next, a shared state flows through, and checkpointers persist it for resume and human-in-the-loop interrupts. LangGraph models an application as a state machine graph: a typed state object, nodes (functions or agents) that read and update the state, and edges (including conditional and cyclic edges) that decide the next node. A checkpointer persists state after each step, enabling resume, time travel, and human-in-the-loop via interrupts. It’s used for complex agents (loops with tool calls, multi-agent supervisors) where control flow must be explicit. An agent graph: “call_model” → conditional edge (tool calls? → “tools” → back to “call_model” : END). Both pause execution at a point, persist state, and resume later with human input. “LangGraph is a graph database.” Awareness. How does LangChain differ from LangGraph?LangChain gives the building blocks and simple linear chains; LangGraph gives control flow and state for complex, cyclic, long-running agent processes with persistence. They’re often used together. LangChain is a toolkit of components and simple chains; LangGraph is a runtime for stateful graphs with cycles, branching, persistence (checkpointers), interrupts for human input and multi-agent patterns. Use LangChain pieces for loaders, splitters and model wrappers; use LangGraph when the control flow itself needs to be explicit and durable. LangChain: “retrieve then answer” chain. LangGraph: “route → maybe search (loop) → maybe ask human → answer” with persisted state. No; LangGraph can be used with any model client, and LangChain components can be used without LangGraph. “LangGraph replaces LangChain entirely.” Distinction. How does Mastra compare with these frameworks?Mastra is TypeScript-first and bundles agents, tools, workflows with suspend/resume and Postgres storage, memory, RAG helpers, evals and tracing in one framework. LangGraph is closer to Mastra’s workflows; LangChain to its building blocks. For a Node backend, Mastra fits naturally. Comparison points: language (Mastra is TypeScript-first; LangChain/LangGraph have Python and JS), scope (Mastra bundles agents, tools, workflows, memory, RAG helpers, evals and tracing; LangChain is components, LangGraph is orchestration), durability (Mastra workflows and LangGraph both persist state and support human-in-the-loop), and ecosystem maturity (LangChain’s integrations are broad; Mastra is newer and moves fast). In Node/TypeScript: Mastra workflows ≈ LangGraph’s graphs with persistence; Mastra agents/tools ≈ LangChain’s agents and tools; both have tracing and evals. Mastra for TypeScript-native workflows and agents, unless the team already uses LangGraph. “They’re completely different categories.” Comparison. What is an orchestration framework?Software that coordinates multi-step LLM work: calling models and tools in order or in loops, passing state, retrying, pausing and resuming, and tracing what happened. Orchestration frameworks coordinate the moving parts of LLM applications: they define steps or graphs, pass state between them, call models and tools, handle loops and branching, persist progress, retry failures, pause for humans, and record traces. Examples: Mastra, LangGraph, LlamaIndex workflows, Temporal or Inngest used with LLM steps. A support pipeline: classify → retrieve → draft → check policy → (human review) → send, run by the framework with retries and traces. Not by itself; queues execute independent jobs. Orchestration adds multi-step state and control flow on top. “Orchestration means Kubernetes.” Definition. When would you implement orchestration yourself?When the flow is small and stable, when you need precise control over a provider’s protocol, when the framework would add more concepts than code it saves, or when learning. Move to a framework once you need durable state, recovery and approvals. Hand-roll orchestration when the flow is small and stable (one tool loop, a queue job), you need exact control over a provider’s protocol or performance, the framework’s abstractions would cost more to learn than the code they replace, or you want to understand the mechanics. Re-implementing tricky parts badly: resume claims, recovery after crashes, retries without idempotency. “Always use a framework” or “never use one”. Judgement. What is a multi-agent system?Several agents with different roles, tools or prompts cooperating on a task, coordinated by a supervisor agent, a workflow, or peer-to-peer messages. Multi-agent systems split work among specialised agents (researcher, writer, critic; or per-domain agents) coordinated by a supervisor agent that delegates (agents as tools), by a workflow, or by peer messaging. Benefits: smaller focused prompts and tool sets, parallelism, separation of permissions. Costs: more calls, coordination failures, harder debugging. Mastra supports supervisor agents with sub-agents exposed as tools; LangGraph and A2A support other patterns. When tasks need clearly different tool sets or permissions, or when a single agent’s prompt becomes too large to manage; measure that it helps. “More agents = better results.” Awareness. What are the challenges of multi-agent communication?Lost or distorted context between agents, error propagation, loops between agents, cost and latency multiplying, unclear responsibility, harder debugging and evaluation, and security boundaries between agents’ permissions. Mitigations: structured messages between agents, clear contracts, step and budget limits, tracing across agents, and least-privilege tools per agent. A researcher agent summarises sources loosely; the writer agent treats the summary as fact and adds a wrong figure; no one checks. A single trace across all agents with each message and tool call, so you can see where the information went wrong. “Agents communicate perfectly in natural language.” Realism.

15.2MCP, A2A and AG-UI

What is MCP?The Model Context Protocol: an open standard for connecting AI applications to tools and data sources through MCP servers, so any MCP client can use any server. MCP (Model Context Protocol), introduced by Anthropic in late 2024 and now widely adopted, is an open protocol for connecting AI applications to external capabilities. An MCP server exposes tools, resources and prompts; an MCP client inside a host app discovers and uses them over JSON-RPC 2.0 (stdio or Streamable HTTP). The model then sees those tools like any other function-calling tools. An IDE assistant connects to a GitHub MCP server (tools: search issues, create PR), a Postgres MCP server (resource: schema; tool: run read-only query) and a docs MCP server, without custom code for each. 
// a minimal MCP server (TypeScript SDK 1.32, stdio transport)
import { McpServer } from '@modelcontextprotocol/sdk/server/mcp.js';
import { StdioServerTransport } from '@modelcontextprotocol/sdk/server/stdio.js';
import { z } from 'zod';
const server = new McpServer({ name: 'docmind-search', version: '1.0.0' });
server.registerTool('search_documents', {
  title: 'Search documents',
  description: "Search the configured user's documents for passages relevant to a query.",
  inputSchema: { query: z.string().min(1).max(500) },              // a Zod raw shape
}, async ({ query }) => {
  const hits = await retrieve({ userId: process.env.DOCMIND_USER_ID, query, k: 5 });
  return { content: [{ type: 'text', text: hits.map((h) => `${h.filename}: ${h.content}`).join('\n---\n') }] };
});
await server.connect(new StdioServerTransport());
 The host application’s model, through its MCP client; the server only exposes and executes. “MCP is a model.” Awareness. What problem does MCP solve?The N×M integration problem: without it, every AI app writes its own connector for every system. With it, a system exposes one MCP server and every compatible app can use it. Before MCP, each AI app (IDE assistant, desktop chat, agent framework) needed custom integrations for each system (GitHub, Slack, databases, internal APIs): N apps × M systems connectors. MCP standardises discovery and invocation, so a system exposes one server and any compliant client can list and call its tools, read its resources and use its prompts. It also standardises transport, capability negotiation and some security patterns (OAuth for remote servers). A company exposes its internal ticket system as an MCP server once; developers use it from their IDE assistant, chat app and custom agents. Servers can expose powerful tools; tool descriptions and results can contain prompt injection; you must authenticate servers, scope permissions, and review third-party servers like any dependency. “It makes models smarter.” Purpose. What are MCP clients and servers?A server exposes capabilities (tools, resources, prompts) over JSON-RPC via stdio or HTTP. A client lives in a host application, connects to servers, discovers their capabilities and invokes them on behalf of the model. Roles: the host is the AI application (an IDE, a chat app, your agent backend); it creates one MCP client per server connection; each server is a separate program exposing capabilities. Clients and servers negotiate capabilities at initialisation; servers can also ask clients for things (sampling a model completion, eliciting user input, listing roots) if the client supports them. Claude Desktop or an IDE (host) runs an MCP client per server; a local stdio server reads files; a remote Streamable HTTP server talks to a SaaS API with OAuth. stdio for local processes, and Streamable HTTP for remote servers (with optional SSE streaming). “The client is the LLM.” Architecture. What are MCP resources, tools and prompts?Tools: functions the model can call (with input schemas). Resources: data the app can read, addressed by URI (files, records). Prompts: reusable prompt templates the user or app can select. Tools are model-controlled actions with input schemas (the model decides to call them, the host executes via the server). Resources are application-controlled context: readable data identified by URIs (files, records, schemas) that the host can attach to the conversation. Prompts are user-controlled templates (often exposed as slash commands) with arguments. Tool: create_issue({ title, body }). Resource: file:///repo/README.md or postgres://schema. Prompt: “review-pull-request” template with a PR number argument. Tools (they act); resources are read-only by design; prompts are templates. “They’re all the same as tools.” Vocabulary. What is A2A?The Agent2Agent protocol: an open standard for agents to discover each other (agent cards), send tasks, exchange messages and receive results and status updates, across frameworks and vendors. A2A defines how independent agents interoperate: each publishes an agent card (name, description, skills, endpoint, auth requirements) for discovery; a client agent sends messages that create tasks; the remote agent processes them (possibly long-running), sends status updates and streams results, and returns artifacts (outputs). It runs over HTTP with JSON-RPC and SSE, and is framework-neutral. A travel agent delegates “book a hotel in Pune for 12–14 Nov” to a hotel-booking agent from another company, receives status updates and a booking artifact. Tasks have states and can stream updates or notify via push, instead of blocking one request. “A2A is how agents call tools.” Awareness. What problem does A2A solve?Interoperability between independently built agents: delegating work to another team’s or vendor’s agent without knowing its internals, including long-running tasks. Organisations build agents with different frameworks and vendors; without a standard, connecting them means custom APIs for each pair. A2A gives a common way to discover capabilities, delegate tasks, exchange messages and results, and handle long-running work and auth, while each agent keeps its internals private. A procurement agent working with a supplier’s quoting agent. Authenticating agents, authorising what they may request, and treating their outputs as untrusted input. “It lets agents share memory.” Purpose. How is A2A different from MCP?MCP connects an agent to tools and data (the agent stays in charge). A2A connects agents to other agents as peers (the remote agent decides how to do the task). Different levels of delegation. MCP connects an agent to capabilities it controls: it decides when to call a tool and interprets the result. A2A connects an agent to another autonomous agent: it delegates a goal, and the remote agent decides how to achieve it with its own tools, possibly over a long-running task with status updates. MCP: your agent calls a “search_documents” tool on a server and decides what to do with the result. A2A: your agent asks another agent “research competitors and send a report”, and that agent chooses its own tools and steps. Yes: an agent can use MCP tools internally while being reachable by other agents over A2A. “They’re competitors doing the same thing.” Distinction. What is AG-UI?The Agent–User Interaction protocol: a standard event stream between an agent backend and a frontend (text deltas, tool calls, state updates, run lifecycle). AG-UI standardises the stream between an agent backend and a frontend: typed events for run lifecycle, text message start/content/end, tool call start/arguments/end and results, state snapshots and deltas, custom events, and errors. The frontend can render progress, show tool calls, sync shared state, and send user input back, independent of which agent framework is behind it. A chat UI showing “Searching documents…” while a tool call runs, then streaming the answer, works the same against a Mastra, LangGraph or custom backend that speaks AG-UI. It has a small custom version (meta, status, sources, action, text, done, error events over SSE). “AG-UI is a UI component library.” Awareness. How does AG-UI connect an agent backend to a user interface?The frontend starts a run; the backend streams typed events (run started, text message content, tool call start/args/end, state snapshot/delta, run finished or error) over SSE or similar; the UI renders them and can send user input back. The agent backend emits an ordered stream of typed events for each run (over SSE or similar); the frontend subscribes and renders: text as it streams, tool calls as status or cards, state changes as UI updates; user actions (messages, approvals, form inputs) are sent back to the backend. Because event types are standard, generic UI components can render any compliant agent. Event sequence for one turn: RUN_STARTED → TEXT_MESSAGE_START → TOOL_CALL_START(searchDocuments) → TOOL_CALL_ARGS → TOOL_CALL_END → TEXT_MESSAGE_CONTENT×n → TEXT_MESSAGE_END → RUN_FINISHED. So UI components and agent backends can be mixed and matched without bespoke protocols. “It replaces HTTP.” Mechanism. How do MCP, A2A and AG-UI fit into an AI application architecture?User ↔ AG-UI ↔ your agent; your agent ↔ MCP ↔ tools and data; your agent ↔ A2A ↔ other agents. Three layers, three protocols. Each protocol covers one boundary: AG-UI between the user’s interface and your agent, MCP between your agent and the tools/data it uses, A2A between your agent and other agents. A system can use any subset; most apps today use only MCP (or plain function calling) plus a custom UI stream. A support assistant: the web widget speaks AG-UI to the assistant backend; the backend uses MCP servers for the ticketing system and knowledge base; for refunds it delegates to the billing team’s agent over A2A. MCP: building or using MCP servers for tools is the most common today. Mixing up which connection each protocol covers. Big picture.

15.3AI performance and reliability

What is prompt chaining?Breaking a task into several LLM calls in sequence, each with a focused prompt, where one call’s output feeds the next. Prompt chaining breaks a complex task into sequential, focused LLM calls: each prompt does one job, its output is validated and passed to the next. Benefits: simpler prompts, easier debugging (inspect each stage), validation between steps, the option to use different models per step. Costs: more calls and latency. Extract key facts (JSON) → draft summary from facts → check summary against facts → polish tone. The sequence is fixed by code; an agent decides the steps itself. “Chaining means passing the whole conversation to each call.” Definition. What is context compression?Reducing the tokens sent while keeping what matters: summarising history, trimming tool results, extracting relevant sentences from retrieved chunks, deduplicating. Context compression reduces tokens while preserving needed information: summarise older history, extract only relevant sentences from retrieved chunks (an LLM or extractive model), drop duplicates, shorten tool results, or use provider prompt caching for repeated prefixes. It lowers cost and latency and can improve accuracy by removing noise, but over-compression can drop the fact you needed. 6 chunks × 500 tokens → extract 2–3 relevant sentences each → 600 tokens of context. Compare answer correctness/faithfulness on the eval set with and without it. “Compression means gzip.” Definition. What is semantic caching?Reusing a stored answer when a new request is semantically similar (embedding similarity above a threshold) to a previous one, scoped by user/tenant and data version. Semantic caching looks up previous answers by meaning: embed the incoming question, search cached questions by vector similarity within the same scope, and return the stored answer above a strict threshold. It saves LLM cost and latency for repeated FAQ-style questions. Risks are false hits (similar wording, different meaning), stale answers after documents change, and cross-user leaks, so scope keys must include tenant and data version, thresholds must be high, and entries must expire. 
async function cachedAnswer(scopeKey, question, generate) {
  const qvec = await embed(question);
  const { rows } = await pool.query(
    `SELECT answer, 1 - (embedding <=> $2::vector) AS sim FROM answer_cache
     WHERE scope_key = $1 AND expires_at > now() ORDER BY embedding <=> $2::vector LIMIT 1`, [scopeKey, toVec(qvec)]);
  if (rows[0]?.sim >= 0.97) return { answer: rows[0].answer, cached: true };   // strict threshold
  const answer = await generate(question);
  await pool.query(`INSERT INTO answer_cache (scope_key, question, embedding, answer, expires_at)
                    VALUES ($1, $2, $3::vector, $4, now() + interval '1 day')`, [scopeKey, question, toVec(qvec), answer]);
  return { answer, cached: false };
}
// scopeKey = tenant + document set version, so changed documents never return stale answers
False hits: “refund for monthly plan” vs “refund for annual plan” may be very similar but need different answers. Use high thresholds, scope keys, TTLs, and only for non-personal FAQs. Using a semantic cache without scoping by user/tenant and document version. Trade-offs. What is an LLM guardrail?A check around model input or output that blocks, rewrites or flags content: schema validation, PII filters, topic restrictions, injection detection, grounding checks. Guardrails are policy checks wrapped around model calls. Input guardrails: length limits, PII detection/redaction, abuse and jailbreak classifiers, topic allow-lists. Output guardrails: schema validation, toxicity/safety filters, grounding/faithfulness checks, secret and PII leakage checks, link and HTML sanitisation, business rules (no prices not in the catalogue). They can block, rewrite, ask for clarification, or escalate. A support bot blocks answers that promise refunds above policy, and escalates instead. Use deterministic checks first (cheap, reliable), and model-based classifiers for fuzzy policies. “Guardrails are the system prompt.” Definition. What is model routing?Choosing which model handles a request based on task type, difficulty, cost or latency targets. Model routing picks a model per request based on task type, estimated difficulty, required capabilities (vision, long context, tools), latency target or user tier. It can be rule-based (task → model), classifier-based (a small model rates difficulty), or cascade (try cheap model, escalate if confidence or validation fails). Classification and query rewriting → small model; complex multi-document answers → large model. Eval quality and cost per route; check that cheap-routed requests don’t lose meaningful quality. Confusing it with intent routing (which path to take). Definition. What is fallback routing?Sending a request to a backup model or provider when the primary fails or times out. Fallback routing defines alternatives when the chosen model fails: same provider’s other model, another provider, or a degraded non-LLM response, triggered by errors, timeouts or circuit breakers. It keeps features available during outages; outputs must be validated the same way and logged with the model that served them. See generateWithFallback in Phase 5 Q33. Vectors from another model are incompatible with the stored index. Retrying the same failing model forever. Definition. What is an LLM evaluation framework?Tooling to run a fixed dataset through a model or pipeline and score outputs with metrics (exact match, judge scores, faithfulness, latency, cost), so versions can be compared and regressions caught. An eval framework runs a versioned dataset through your system and scores outputs with metrics: deterministic (exact match, JSON validity, latency, cost), reference-based (similarity to expected answers), and model-graded (LLM judges for faithfulness, relevance, rubric quality). It compares versions (prompt, model, retrieval settings), catches regressions in CI, and tracks trends. Examples include RAGAS-style metrics, promptfoo, DeepEval, and framework-built-in scorers (Mastra has scorers). A PR changes the system prompt; CI runs 80 questions and blocks the merge because faithfulness dropped from 0.94 to 0.88. Realistic, diverse, including edge cases and unanswerable questions, versioned, and growing from production failures. “Evals are unit tests with exact string matching.” Definition. What is observability in AI applications?Being able to see what happened inside each request: logs, metrics and traces plus prompts, model versions, tokens, cost, tool calls and per-step latency, so you can debug quality and cost, not only errors. Observability is the ability to answer “what happened in this request and why?” from telemetry. For AI apps that means the classic three (logs, metrics, traces) plus AI-specific context on each model call: prompt/prompt version, model, parameters, tokens, cost, latency, finish reason, tool calls and results, retrieval scores, and links to eval and user feedback, with sensitive data redacted. A trace for one chat request: auth 3 ms → rewrite (flash-lite, 220 in / 15 out tokens, 640 ms) → retrieve 48 ms → generate (1,800 in / 210 out, 2.4 s, finish stop) → save 12 ms; tagged with user, prompt version and model. Tokens and cost per request/user, model and prompt version, finish reasons, tool-call counts and errors, retrieval scores, eval scores, user feedback. “Logging errors is enough.” Definition. What is the difference between logging and tracing?Logs are individual events (“tool failed”). Traces connect all the work for one request across components into a tree of timed spans with a shared id, showing order and where time went. Logs are discrete events with context (good for details and errors). Metrics are numeric time series (good for alerting and trends). Traces are trees of timed spans sharing a trace id across services and steps (good for seeing where time goes and how components interact in one request). For an agent run, the trace shows the sequence of model steps and tool calls with timing; logs explain individual events. Log: “searchDocuments failed: timeout”. Trace: request r_1 → agent step 2 → searchDocuments span 5,002 ms (timeout) → model step 3 span 1.1 s; you see where and in what order. 
import { trace } from '@opentelemetry/api';
const tracer = trace.getTracer('docmind');
async function tracedTool(name, args, fn) {

How would you monitor an agent’s execution?A trace per run with a span per model call (model, tokens, latency, finish reason) and per tool call (name, args summary, duration, outcome); counters for steps per run, loop-limit hits, tool error rate; sampled transcripts for review. How would you track token consumption across multiple agents?Record usage on every model call tagged with run id, agent name, user and feature; roll up per run and per user; propagate a run/trace id through agents so totals add up; budget per run. How would you measure end-to-end latency?From request received to last byte sent (and time to first token for streams), as p50/p95/p99, broken down by stage spans (auth, retrieval, each model call, tools, DB writes); also measured from the client for real user experience. Also measure from the client (real user monitoring), since network and rendering add time.

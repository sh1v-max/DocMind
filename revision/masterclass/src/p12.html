12.AThe method

A fixed sequence you follow for every incident, so you don’t guess-and-patch under pressure.
  1. Reproduce the issue (or find a request that shows it). Note exact input, user, time, environment.
  2. Collect evidence: logs by request id, error messages and cause chains, metrics (latency, error rate, saturation), recent deploys/config changes, traces.
  3. Identify the failing component: client, API, DB, queue, worker, LLM provider, network. Narrow by timing each stage.
  4. Form hypotheses ranked by likelihood × ease of checking.
  5. Test hypotheses one at a time with a measurement, not a feeling. Change one thing.
  6. Fix the root cause, not the symptom (raising a timeout is rarely the fix).
  7. Add a regression test (and an alert if it could recur silently).
  8. Monitor the result after deploy; write down what happened.

Real examples from DocMind’s logs: a stream that showed nothing (Gemini’s \r\n line endings split across reads → normalise on the whole buffer); the rate limiter keying on proxies (measured the RateLimit-Policy partition key against sha256(client IP) for hop counts 1, 2, 3); production sharing the laptop’s queue (found because there were 0 keys under the docmind: prefix); a DNS resolver refusing the Neon hostname on a hotspot (not a code bug).
  • Changing several things at once.
  • “Works on my machine” without comparing environments.
  • Declaring victory without a test or a metric.

12.BDiagnose these snippets first

async function transfer(from, to, amount) {
  const client = await pool.connect();
  await client.query('BEGIN');
  await client.query('UPDATE accounts SET balance = balance - $1 WHERE id = $2', [amount, from]);
  if (amount > 1000) throw new Error('limit');
  await client.query('UPDATE accounts SET balance = balance + $1 WHERE id = $2', [amount, to]);
  await client.query('COMMIT');
  client.release();
}
What breaks under load? Any throw (the limit check or a failed query) skips ROLLBACK and release(): the transaction stays open holding a row lock and the client never returns to the pool. After max such errors, every request waits forever for a connection. Fix: try { … COMMIT } catch (e) { await client.query('ROLLBACK'); throw e; } finally { client.release(); }, and validate the limit before BEGIN.

12.CProduction scenarios

Your backend API normally responds in 500 milliseconds. Suddenly, it takes five seconds. What changed (deploy, config, traffic, data volume), which endpoints are slow (all → shared dependency; one → its code path), and the latency breakdown per stage for one slow request. Query timing logs, pg_stat_statements for the slowest/most frequent queries, EXPLAIN (ANALYZE, BUFFERS) on them, lock waits (pg_stat_activity, pg_locks), pool wait time vs query time, missing indexes after data growth. Time every outbound call (LLM, embeddings, payments) with status and retry count; compare to their status pages; check whether retries are hiding failures. Following one request across components with a shared trace id: each component records spans (start, end, attributes), so you see a waterfall of where the 5 seconds went (OpenTelemetry is the standard). p50/p95/p99 latency per endpoint and per dependency, request rate, error rate, saturation (CPU, event-loop lag, DB pool in-use/waiting, queue depth), LLM tokens and time to first token. “I’d find which stage got slower using traces and per-dependency timings, check what changed, then dig into that dependency: slow queries with EXPLAIN, pool waits, or provider latency and hidden retries.” Your application starts returning database connection errors. Leaked clients (no release on an error path), long transactions (an LLM call inside a transaction), traffic spike beyond pool size, too many app instances × pool size above the server’s max_connections, slow queries holding connections, idle-in-transaction sessions. A fixed set of reusable DB connections lent to requests; requests queue when all are busy. Pool metrics (totalCount, idleCount, waitingCount) climbing and never returning; pg_stat_activity showing many idle in transaction sessions from the app; code review for pool.connect() without finally { release() }; set idle_in_transaction_session_timeout. Short term: restart instances to free connections, kill stuck sessions, add a server-side pooler (PgBouncer / provider pooled endpoint). Root cause: fix the leak, move slow work out of transactions, size pools against max_connections, add connection and statement timeouts and alerts. “Usually a leak or long transactions. I’d confirm with pool metrics and pg_stat_activity, fix the release/transaction code, and add timeouts and a pooler so it fails fast next time.” A user uploads the same document three times accidentally. Hash the file bytes (SHA-256) at upload and look for an existing document with the same hash for that user. Yes for exact duplicates (cheap, reliable). Near-duplicates (re-exported PDF) need text or embedding similarity, usually only worth it later. A unique constraint on (user_id, sha256); on conflict return the existing document (200) instead of creating a new one; the job id = document id so it can’t be queued twice. Let the unique constraint decide: three concurrent inserts → one wins, two get a conflict and return the winner’s row. Check-then-insert in code would race. Also disable the upload button while uploading. DocMind has jobId = documentId (one job per document) but no file hashing, so three uploads make three documents (and count toward the 5/10 cap). “Hash the bytes, put a unique constraint on owner + hash, return the existing document on conflict, and keep jobs keyed by document id.” Your LLM provider becomes unavailable. No. Login, documents, history and anything non-LLM should keep working; AI features degrade with a clear message. A provider-neutral interface with an ordered fallback list per task; on timeout/5xx/429 after retries, try the next model or provider; validate its output the same way; log which provider answered. A wrapper that counts failures; after a threshold it “opens” and fails fast (or goes to fallback) without calling the provider for a cool-down period, then lets a few test calls through (“half-open”) and closes if they succeed. It stops you from piling timeouts onto a dead service. Honest, specific UI: “The AI service is temporarily unavailable.

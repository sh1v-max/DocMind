14.AThe design

A user enters a topic, level and number of modules. The system generates an outline, waits for the user to approve it, generates lessons and quizzes, checks quality, and publishes the course.

14.1Architecture

What problem does this application solve?Creating a structured, reviewed course (modules, lessons, quizzes) from a topic in minutes instead of days, with the human staying in control of the outline.Purpose. How does the course-generation process start?POST /courses with a validated body and an idempotency key; the API creates (or finds) the course row and starts a workflow run with the user as the resource owner.Flow. What components are involved?API, workflow engine with Postgres storage, LLM service, app tables, and the frontend’s review and progress screens; optionally a queue for very large courses.Components. Why did you choose a workflow-based architecture?The steps and order are known, it runs for minutes, it must pause for approval, survive restarts, retry single steps and never duplicate content. Those are exactly what workflows give; an agent would add unpredictability for no gain.Architecture reasoning. What is the role of the LLM?Content generation inside specific steps (outline, lessons, quizzes, optional quality judging), always with a schema. The LLM never decides the process.Separation. How do you structure the generated course?Course → modules (title, objectives) → lessons (title, Markdown body) → one quiz per module (5 questions × 4 options), each level validated by a Zod schema.Modelling. How do you store the output?Course row (status, outline JSONB, request key), lesson_drafts keyed by (course, module, lesson), module_quizzes keyed by (course, module); publish flips the status in one transaction.Data design. How do you validate generated content?Schema validation (Zod) on every LLM output, deterministic checks (unique titles, lesson length, distinct quiz options, valid answer index), and an optional judge pass for relevance; failures retry the step.Quality control.

14.2Workflow design

Explain the complete course-generation workflow.prepare (dedupe, create row) → outline (LLM, schema) → approve (suspend until the user answers) → lessons (foreach, concurrency 3, retries) → quizzes (foreach per module) → quality checks → publish (transaction).End to end. What are the individual steps?Validate and dedupe; generate outline; human approval; generate lessons; generate quizzes; check quality; publish.Recall. Which steps are deterministic?Validation, dedupe, mapping the outline to work items, quality checks, and publishing. Their output depends only on input and data.Distinction. Which steps require an LLM?Outline, lessons, quizzes, and optionally a judge for relevance.Distinction. Which steps can execute in parallel?Lessons across modules (and within a module if they don’t depend on each other), and quizzes per module once that module’s lessons exist. Capped concurrency for rate limits.Parallelism judgement. How do you pass data between steps?Each step’s output is the next step’s input; .map() turns the outline into lesson items; later steps read the approved outline with getStepResultAsync; large content goes to the database, and steps pass ids rather than big blobs.Data flow. What happens when one step fails?It retries (step retries: 2); if it still fails the run fails, the course is marked failed with the reason, completed drafts stay, and a re-run continues from the failed step.Failure handling. How do you implement retries?Step-level retries for LLM steps, transport retries with backoff inside the LLM client for 429/5xx, and no retries on deterministic validation failures that would fail again.Retry discipline. How do you prevent duplicate course generation?Unique (user_id, request_key) on courses with an upsert, so a repeated POST finds the same course (and returns it if published); the approval endpoint claims the waiting state once.Idempotency. How do you persist workflow state?Mastra storage on Postgres saves a snapshot per step; app tables hold the content and user-visible status.Persistence.

14.3Suspend and resume

Why would you suspend course generation?To let the user approve or reject the outline before spending tokens on 30 lessons, and to keep a human in control of what gets generated.Purpose. How would you request user approval?The approval step suspends with the outline; the API returns 202 with status awaiting_approval and the outline; the UI shows it with Approve and Reject (with feedback).Flow. Where is the workflow state stored?In Postgres: Mastra’s snapshot table for the run, and the course row for status and outline.Storage. How does the frontend know the workflow is waiting?The course status is awaiting_approval (returned by POST and by GET /courses/:id); polling or an SSE event updates the screen.UX. What happens after user approval?The endpoint checks ownership and claims the waiting state, then resumes the run in the background; the approval step re-runs with resumeData, marks the outline approved, and lesson generation begins; the client watches progress.Resume flow. What happens if the user rejects the outline?Either end the run with bail({ outcome: 'rejected' }) (status success, outcome rejected) and mark the course rejected, or loop back to regenerate the outline with the feedback, a bounded number of times (e.g. .dountil or a new run).Design choice. What happens if the server restarts during suspension?Nothing is lost and nothing is running: the snapshot is in Postgres. After restart the approval can arrive and createRun({ runId }) + resume() continues it. Runs that were running (not suspended) are re-driven by recovery at boot.Durability understanding. How would you handle an approval that arrives twice?The first request claims the state with a conditional UPDATE (awaiting_approval → resuming) and wins; the second updates 0 rows and gets 409. Mastra’s own resume claim (suspended → running) throws WORKFLOW_RESUME_ALREADY_CLAIMED as a second guard.Concurrency.

14.4Content quality

How do you ensure lessons are relevant to the course topic?Give each lesson call the course topic, module title, objectives and sibling titles; check relevance with embedding similarity between lesson and module objective (threshold) or a judge; regenerate outliers.Quality methods. How do you prevent duplicate modules?Instruct uniqueness in the outline prompt, then check in code: normalised title equality and embedding similarity between module titles/objectives; regenerate the outline if duplicates appear; the user also sees it at approval.Dedup. How do you validate quiz questions?Zod (5 questions, 4 distinct options, index 0–3), answerable from the module’s lessons (a judge answers each question from the lesson text and must match the key), shuffle option order in code, no duplicates across modules.Validation. How do you ensure generated answers are correct?You can’t guarantee it with an LLM alone: ground quizzes in the generated lessons, verify with a second model or a judge, flag low-confidence items for review, let users report errors, and for factual domains retrieve trusted sources (RAG) before generating.Honest limits. How would you evaluate course quality?Automatic checks (coverage of objectives, readability, duplicate rate, quiz validity), judge scores on a rubric, human review of samples, and learner signals (completion, quiz scores, ratings, reports).Evaluation. How would you reduce the cost of generating large courses?Approve the outline before spending on lessons; smaller models for quizzes and checks; cap lesson length; reuse content for repeated topics (cache by normalised topic + level); never regenerate finished lessons on retry; batch where possible; log tokens per course and enforce per-user budgets.Cost engineering.

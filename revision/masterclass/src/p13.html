13.AThe system

DocMind lets a user (a silent guest by default) upload PDFs, chat with them with memory and streamed answers, and generate a validated 5-question quiz. Free-tier stack: Express 5 + TypeScript on Render, React on Vercel, Neon Postgres with pgvector, Upstash Redis + BullMQ, Gemini (Flash-Lite for generation, gemini-embedding-001 with 3072 dimensions) over plain REST.

13.1Architecture walkthrough

What problem does DocMind solve?Asking questions about your own PDFs and getting answers grounded in them, with sources, plus quick self-testing with generated quizzes. For me it was also the project to learn every part of an AI backend properly.Clarity of purpose. Explain its complete architecture.React frontend on Vercel talks to an Express 5 API on Render with a Bearer JWT. Uploads are parsed and chunked in the request, saved as processing, and embedded by a BullMQ worker into Neon Postgres with pgvector. Chat embeds the message, routes it (smalltalk, document question, quiz offer), and document questions go to an agent loop on Gemini with two tools; the answer streams back over SSE.

Step through the DocMind animation above while saying it. Layers: routes (HTTP only) → services (no req/res) → repositories (the only SQL, every function takes userId).

End-to-end ownership. What are the main backend components?Auth (guest/register/login, requireAuth), upload + ingestion service, the queue and worker, the chat pipeline (prepareChat, router, agent, tools), the quiz service, the LLM and embedding services (plain fetch to Gemini), repositories over Drizzle, and the SSE streaming layer.Component map. How does the frontend communicate with the backend?JSON over HTTPS with the token in the Authorization header via one authFetch helper; multipart for uploads; and POST /chat-stream read with fetch + a hand-written SSE parser, because EventSource can’t send an Authorization header. The frontend polls GET /documents while anything is processing.Protocol reasoning. What database do you use, and why?Postgres on Neon with pgvector. My data is relational (users, documents, messages, ownership), and pgvector keeps embeddings next to it, so one query can join chunks to documents and filter by owner and status. One system, free tier, SQL I already know.Not at this scale. With many millions of vectors or heavy QPS I’d first add an index (needs halfvec or fewer dimensions at 3072), then consider a dedicated store.Justified choice. What is the role of your embedding model?It turns every chunk, every chat message and the router’s example phrases into 3072-number vectors, so search and routing work by meaning. The message is embedded once and reused for routing and the first search.Understanding. How do you store documents?I don’t keep the PDF. A documents row stores filename, size, text length, chunk count, owner, status (processing/ready/failed) and an error; the chunk texts and embeddings go into chunks.No re-chunking or re-embedding without a re-upload, and no “view original page”. Object storage would fix both.Honest design. How do you organize document chunks?One row per chunk: content, vector(3072) embedding and document_id. No user_id on chunks on purpose: ownership lives on the document, and every search joins through it.Data modelling. How does the application handle multiple users?Every visitor is a real user row (guests too), every data route requires a JWT, the user id only ever comes from req.user.id, and every repository function that reads or deletes user data takes userId as a required parameter. Someone else’s document behaves like a missing one (404).Making userId required turned 15 call sites into compile errors, which became the to-do list. The one thing the compiler can’t catch is two string arguments swapped, so I check argument order.Security ownership. What are the major technical challenges you encountered?Three good ones: (1) Gemini rejects a resent function-call turn without its thoughtSignature, so model turns are sent back byte for byte; (2) the rate limiter keyed on proxies until I measured the right trust-proxy hop count on Render (3); (3) making the ingest job idempotent and safe when a user deletes the document mid-job.Real problem solving.

13.2Document ingestion

Explain what happens when a user uploads a PDF.Auth → document cap checked before multer reads the file → multer (memory, 10 MB) → pdf-parse → 400 if there’s no text → ~500-word chunks → row saved as processing → job queued with jobId = documentId → 202. The worker embeds and stores the chunks and marks it ready; the frontend polls until then.Precise flow. How do you extract text?pdf-parse v2 (new PDFParse(...), getText()). It needs a real text layer; there’s no OCR.Facts. How do you handle empty or corrupted PDFs?A PDF with no text layer gets a 400. I check the per-page texts, because pdf-parse adds a “-- 1 of N --” marker per page and a textless PDF still returned 12 characters. A file that fails to parse ends in a JSON error from the last-resort handler; oversize is a 413.Edge cases. How do you chunk the extracted text?Split on whitespace into words and take 500 at a time, no overlap. It’s a deliberately simple baseline.Honesty. How do you generate embeddings?In the BullMQ worker, with gemini-embedding-001 over the REST API (key in the x-goog-api-key header), then the chunks are inserted with their vectors.Facts. How do you store embeddings in PostgreSQL?A vector(3072) column via pgvector, written through Drizzle; search uses Drizzle’s cosineDistance, which builds the <=> expression.Facts. Why did you choose your chunk size?Honestly, as a simple starting point: 500 words is about 650–700 tokens, fits the embedding model’s input comfortably, and keeps three chunks small in the prompt. I didn’t tune it with an eval; the next step is overlap and paragraph-aware splitting, compared on my question set.Pretending it was chosen by experiment.Honest reasoning. How do you handle ingestion failures?The job retries 3 times with 5 s then 10 s backoff. It’s idempotent: it deletes the document’s chunks first, then inserts all of them. After the last attempt (checked with job.getState() === 'failed'), the failed handler deletes partial chunks and sets status failed with a short reason. If Redis is down at upload, the row is removed and the user gets 503.Reliability depth. Can the user query a document before ingestion completes?No. Chatting with one specific processing or failed document returns 409 before any Gemini call; search and quiz only read ready documents; the UI only lets you pick ready ones.Correctness. How would you implement ingestion status?It’s implemented: documents.status (processing/ready/failed) with DEFAULT 'ready' so adding it to the live table was safe, plus an error column; the frontend polls every 2 s, slowing to 10 s after a minute, only while something is processing.Implementation detail.

13.3Agent architecture

How does DocMind identify the user’s intent?A hybrid router. The message is already embedded, so I compare it with example phrases for three intents (smalltalk, document question, quiz request) for free. Document-question guesses are accepted; smalltalk needs a margin of at least 0.03; any quiz guess and close calls go to an LLM classifier (JSON mode, temperature 0, Zod). Anything unsure becomes a document question.Found while building: vectors route by shared words (“compare the two pdfs” looked like “quiz me about the pdf”), which is why quiz guesses always get the LLM.Design + evidence. How does the router select an agent?It doesn’t pick between agents: there’s one agent. The router picks one of three paths: smalltalk (one LLM call, no search), document question (the agent loop), or quiz request (an offer written by code, no LLM).Correcting the premise. Why did you use multiple agents?I didn’t, and that was deliberate. Only document questions need tool choices; smalltalk and the quiz offer are better as plain code paths: cheaper, predictable, and nothing to go wrong.Judgement over buzzwords. Could you have implemented the same system with one agent?It is one agent. I could even drop the router and let that agent handle smalltalk too, but then every “thanks!” would cost tool-capable calls and might search. The router saves calls on the free tier (15 requests/min).Trade-offs. What responsibilities does each agent have?The agent answers questions about the user’s documents: it decides what to search (it writes the query, resolving follow-ups like “who founded it?”), can list documents, and must answer only from tool results. Smalltalk replies without searching and refuses general-knowledge questions; the quiz path only offers a button.Clear responsibilities. How do agents communicate?They don’t need to: there’s one agent. The router hands one message to one path through prepareChat; the agent talks only to its tools and the model.Accuracy. How do you handle invalid agent outputs?Tool arguments are validated with Zod; an unknown tool, bad arguments or a throwing tool become { error } data the model sees. An invalid classifier reply falls back to document question. If steps run out, a give-up line is streamed (and saved). Every model turn is sent back unchanged.Robustness. How do you maintain context?The last 8 messages of this session, for this user, are loaded and sent as real user/model turns plus a system instruction. The session id comes from the client, but every lookup filters by session and user.Memory design. How do you handle tool failures?The tool wrapper catches the error and returns { error } to the model; the loop is capped at 3 calls with the last one tool-free, so the model has to give an answer. Embedding a query is reused when possible to save calls.Robustness. How would you prevent one agent from accessing another user’s documents?Already prevented in code: searchDocuments only takes { query }; userId and document scope are closed over from the session before the loop starts, and the SQL joins documents on user_id and status = 'ready'. The model can’t name a user or document id.Security design.

13.4Tool implementation

Explain your searchDoc tool.It’s called searchDocuments. The model passes a standalone query; I validate it (trimmed, 1–500 chars), embed it, run the owner-scoped vector search (top 3), add new chunks to the turn’s sources, and return { results: [{ filename, content }] }, or a “nothing relevant” note. The status line shows the model’s query (“Searching for …”).Implementation detail. Explain your listDoc tool.listDocuments takes no arguments and returns the user’s documents: filename, status, chunk count and upload date. It answers “which files do I have?”, which chunk search can’t.Facts. What inputs do these tools accept?searchDocuments: { query: string }. listDocuments: nothing. Scope never comes from the model.Facts. How do you validate their arguments?Zod safeParse, exactly like a request body: the model is an untrusted client. Bad arguments become an error result, never an exception.Practice. What does each tool return?searchDocuments: results with filename and content (not the distance, which the model would over-read). listDocuments: an array of documents with filename, status, chunkCount, uploadedAt.Facts. What happens when no documents are found?Search returns an empty results list with “Nothing relevant was found in the documents.” and the instruction makes the model say so. In “All documents” mode with nothing ready, the request gets a 404 before the agent runs; a quiz request with no documents gets a sentence, not an error.Edge cases. How does the agent use tool results?The results go back as a function-response turn; the next model call reads them and answers with them, citing filenames in all-documents chats. The sources list sent to the UI is every chunk the searches returned, deduplicated.Flow. Can multiple tools be called in a single turn?Yes: Gemini can return several function calls in one turn, and I run them all. In testing it ran two searches in one step for a two-part question. The limit is 2 rounds of tool calls, not 2 searches.Precision. How would you implement a new document-deletion tool?A deleteDocument({ documentId }) tool with the id validated as a UUID; it wouldn’t delete directly: it would return a proposal that the UI shows as a confirm button (like the quiz offer’s action), and the click calls the existing DELETE /documents/:id, which checks ownership and deletes the row first, then chunks and messages.Safe design. How would you secure that tool?Owner-scoped SQL with userId from the session, a validated single id (no wildcards or bulk delete), human confirmation by click, a rate limit, an audit log, and the system instruction to only offer deletion when explicitly asked.Defence in depth.

13.5Architecture decisions

Why did you choose Mastra?DocMind doesn’t use Mastra yet: I wrote the agent loop myself on Gemini’s REST API to understand it. I’ve planned Mastra for the next phase, workflows only: durable suspend/resume on Postgres, so a pending quiz offer can survive between two requests. I checked its 1.82 package first: CommonJS build, Zod 4, it can reuse my pg pool, and resume claims are atomic.Claiming you built it with Mastra.Honesty and reasoning. Why did you choose PostgreSQL?Relational data with ownership, transactions and joins, plus pgvector and full-text search in the same database, on a free managed host.Justification. Why did you use pgvector?So vector search can join documents and filter by owner and status in one query, with no second system to keep in sync.Justification. Why did you choose your embedding model?gemini-embedding-001 comes with the same Gemini key and free tier I already use. Its default 3072 dimensions are a trade-off: more storage, and pgvector indexes cap the plain vector type at 2,000 dimensions, so before adding an index I’d use halfvec or ask the model for shorter vectors.Trade-off awareness. What would happen if you changed the embedding model?Every stored vector becomes incompatible. I’d add a new column, dual-write new uploads, re-embed old chunks in a background job, evaluate, then switch queries and router example vectors together. The router’s example vectors are computed lazily per process, so they’d follow automatically.Operational thinking. Why did you choose your particular chunking strategy?Simplest thing that works, so I could build the rest first. Its weaknesses are known: no overlap and no structure awareness, so answers can be split across chunks.Honesty. What would you improve in DocMind?Real document summaries (written by the worker at upload, since a top-3 search can’t summarise a long PDF), fair search across several documents, chunk overlap + hybrid search, timeouts/retries/fallback on Gemini calls, and automated tests.The first two are logged as important in ISSUES (#36 summary, #37 multi-document search).Self-critique. What technical debt exists?No automated tests; no migrations (hand-run SQL on Neon); no foreign keys; no timeout or retry on Gemini fetches; no message length cap; history counted in messages not tokens; sources and tool calls not saved with messages; in-memory rate limiter; a bad API key shows a “check your connection” message; no token/cost logging. I keep them in a numbered issues file.Ownership. How would you make DocMind production-ready?Tests + CI, drizzle-kit migrations with a baseline, foreign keys, timeouts/retries/circuit breaker and a fallback model, structured logs with request ids and token costs, a separate worker service, a Redis-backed rate limiter, object storage for originals, OCR, an eval set run in CI, refresh tokens, and paid API tiers.Production thinking. What would happen if 1,000 users used DocMind simultaneously?The Gemini free tier breaks first: 15 generation requests per minute means 429s within seconds. Then: one small Render instance with the worker in the same process and concurrency 1 (upload backlog), an in-memory limiter per instance, Neon free connections, and cross-region latency. Fixes: paid tiers and per-user quotas, horizontal API instances, a separate autoscaled worker, a shared Redis limiter, a pooled DB endpoint, and queueing or shedding load gracefully.Scaling realism.

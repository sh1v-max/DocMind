PART 1 · THE IDEA IN 60 SECONDS

An LLM call is an HTTP request. Everything around it is your job.

Calling Gemini is a POST with some JSON, and the answer comes back as JSON. That part is easy. The backend developer's real work is everything around it: building the request (instructions, history, context, settings), keeping the API key secret, checking what comes back before trusting it, and coping when the model is slow, busy or down.

Analogy: briefing a brilliant freelancer who has no memory. Every call, you must give the full brief: who they are, the rules, the material, the exact format you want back. They bill per word, read and written. Sometimes the line is busy (429, 503) and you call back later. And you check their work before you hand it to a customer.

Build

System instruction, conversation turns, retrieved context, generation settings. The prompt is code: version it, test it.

Protect

The key lives on the server only. The browser talks to your API, never straight to the model.

Check and survive

Status code, finish reason, format. Timeouts, retries with backoff, and a clear message when it still fails.

PART 4 · PROMPTING TECHNIQUES

The handful of techniques that cover most real work

Zero-shot

Just the instruction, no examples. "Summarise this in 3 bullet points." Fine for clear, common tasks.

Few-shot

Add a few input → output examples. Best for tricky labels and exact formats. Pick examples that cover the edge cases.

Role and rules

"You are DocMind, an assistant that answers questions about the user's PDFs." Then the rules: answer only from the documents, say so when it's not there.

Clear structure

Separate instructions from material with headings or tags (Context:, <document>). Put the question last.

Ask for the format

Say exactly what to return. For code to read it, use JSON mode with a schema, then validate (lesson 8).

Think step by step

For reasoning tasks, asking the model to work through steps first improves answers ("chain of thought"). Costs more tokens. Reasoning models do this internally.

Say what to do when unsure

"If the context doesn't contain the answer, say so plainly." Without it, models fill gaps with guesses.

Treat prompts as code

Keep them in one place, version them, and re-run a fixed set of test inputs after every change.

How DocMind's chat prompt evolved

  1. One big string: rules → retrieved chunks → history as "user: … assistant: …" text → question last (buildChatPrompt).
  2. Fixing the tone: answers kept opening with "Based on the provided context…", so a rule now says to answer directly.
  3. Small talk split off: "hi" got "the context doesn't mention that". The router now sends small talk to its own short prompt.
  4. Refusing outside knowledge: "capital of France?" got "Paris!". Now the model is told it only answers from the documents.
  5. Real structure (agent): rules moved to systemInstruction, history became real user/model turns, and document text is labelled as material, never instructions.

ISSUES #8

DocMind has no timeout or retry yet

Every Gemini fetch is a single try with no time limit. A 503 "high demand" fails straight away, and a hung call hangs the request. The first fix to make.

ISSUES #1

Every failure looks the same

A bad API key shows "check your internet connection", because withErrorHandling doesn't tell failure types apart. A 401 should say "server misconfigured", not blame the user's wifi.

PART 6 · LIMITS, COST AND KEYS

How far does the free tier go?

Gemini Flash-Lite's free tier on your account: 15 requests per minute, 500 per day. Every model call counts, and some questions take more than one.

Calls per document question

0questions per day before the 500 limit

Ignores small talk and quiz offers, which cost less. Embeddings have their own separate limit (100 per minute).

Keeping the API key secret

  • The key lives in server environment variables (.env locally, Render's dashboard in production).
  • Never in frontend code: anything in the browser bundle is public, including VITE_* variables.
  • Never in git. .env is gitignored.
  • If it leaks: rotate it (make a new one, delete the old), don't just delete the file.
.history/

A real leak in DocMind

VS Code's Local History extension saved snapshots of every file, .env included, into a .history/ folder that wasn't gitignored. The secrets got exposed that way. Now both are gitignored. Lesson: check what your tools write to disk.

Cost in one line

(input tokens × input price) + (output tokens × output price), for every call. Log the token counts from usageMetadata so you know what each feature costs. DocMind doesn't log them yet (ISSUES #21).

SDK, REST, or a wrapper?

DocMind calls the REST API with plain fetch to learn the protocol. Most teams use the provider's SDK. Either way, keep every model call behind one module (llm.service.ts), so switching model or provider is a one-file change. bonus The model name is hard-coded today; an environment variable would allow switching when one model is overloaded (ISSUES #10).

PART 8 · INTERVIEW DRILL

24 questions you could get. Answer out loud first, then open.

Say it in 60 seconds: "How does your backend call the LLM?"

"The browser only talks to my Express API; the Gemini key stays on the server. For each request I build the call in one service: a system instruction with the rules, the recent conversation as user and model turns, any retrieved document text, and generation settings, for example temperature 0 and JSON mode for my intent classifier. I send it with fetch, check the status and finish reason, and validate structured output with Zod before using it. Answers are streamed back to the user. What I'd add next: a timeout and retries with backoff on every call, because Gemini's free tier sometimes returns 503 or takes far longer than usual."

Each answer opens with Say this first: the 10-second version to lead with. bonus questions go beyond most intern interviews.

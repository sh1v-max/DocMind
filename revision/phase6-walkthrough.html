DocMind · Phase 6 · Background jobs · BullMQ + Redis

The upload stopped waiting for Gemini

Uploading a PDF used to mean one HTTP request that stayed open while every chunk got embedded. Phase 6 split it in two. The request parses and chunks the PDF, saves the document as processing, puts a job in a Redis queue and answers 202. A BullMQ worker picks the job up, embeds the chunks, and flips the document to ready, retrying on its own when Gemini fails.

~2 slive upload answer (202), down from "one Gemini call per chunk"
4.4–4.8 slive, upload → document ready (Render and Upstash both in Oregon)
204% → 33%of Upstash's free 500K commands/month, idle worker, defaults vs tuned
3.5KUpstash commands used that month, all testing included (read 2026-10-15)

If an interviewer says "explain your background jobs" (30 seconds)

"Uploading a PDF needs one embedding call per chunk, so I moved that out of the request. The request parses and chunks the PDF, inserts the document as processing, adds a BullMQ job to Redis with only the chunk texts, and returns 202. A worker embeds and stores the chunks, then marks the document ready. The job is idempotent: it deletes the document's chunks before inserting, so retries and crash re-runs never duplicate anything. BullMQ retries three times with exponential backoff; after the last failure the document is marked failed. Chat and quiz return 409 until the document is ready, and the frontend polls the document list. I also tuned the worker for Upstash's free plan, because an idle BullMQ worker with default settings would have used twice the monthly command limit."

browser ── POST /upload ──► parse + chunk (fast, needs the PDF bytes) insert documents row, status = 'processing' queue.add('ingest', { documentId, userId, chunks }) ──► Redis ◄── 202 { documentId, status: 'processing' } worker (inside the same Node process on Render) ◄── takes the job delete old chunks → embed + store each chunk → status = 'ready' throws? BullMQ retries (5 s, then 10 s) → after 3 attempts: 'failed' browser polls GET /documents every 2 s while anything is 'processing'

Problem 1: a long open request

A 30-chunk PDF kept one HTTP request open from 15 s to a few minutes. Proxies (Cloudflare and Render's own) and browsers give up on very long requests.

Problem 2: all-or-nothing

A Gemini 503 on chunk 17 threw away chunks 1–16. The only retry was "upload again".

Problem 3: deploys

Render restarts the process on every deploy. An upload in progress died with it.

The split is called the offline / online split. Chat is online work: someone is waiting for each word. Ingestion is offline work: nobody needs to watch it happen, they only need to know when it's done.

The words

vocabulary

A restaurant works the same way. The waiter (the request) takes your order, pins a ticket on the rail (the queue) and goes back to the tables. The cook (the worker) takes tickets in order. If the cook burns a dish, they make it again; you don't have to order again.

Why not just setTimeout or a promise you don't await? Fire-and-forget work lives only in memory. A restart loses it, nothing retries it, and nobody can see it. A queue writes the job to Redis first, so it survives the process, can be retried, and can be inspected.
04

Redis in 5 minutes

concept

Redis is a server that keeps its data in memory. It's a key → value store, but the values are real data structures, and every command on them is atomic.

Fast

Data lives in RAM, so a command takes well under a millisecond on the server. From the laptop (India → Oregon) the round trip was ~250 ms; on Render it's the same region.

Atomic

Redis runs one command at a time. "Move this job from waiting to active" can't be half-done, and two workers can never both take the same job.

Blocking waits

A client can say "wait up to N seconds until something arrives". An idle worker doesn't hammer Redis with "anything yet?"; it waits once per drainDelay.

Lua scripts

BullMQ sends small Lua scripts that run inside Redis as one atomic step: take the job, set its lock, update its hash, write an event.

The data structures BullMQ uses

Redis typeWhat it isBullMQ uses it for
Stringone value, can expire (TTL)the job's lock (expires after lockDuration), the stalled-check throttle
Listordered, push/pop at either endwait (jobs ready to run), active (jobs running now)
Hasha small object: field → valueone per job: data, opts, attemptsMade, failedReason…; also the queue's meta
Sorted setmembers ordered by a scoredelayed (score = when to run), completed / failed (score = when it finished)
Setunordered, unique membersstalled (active jobs suspected dead)
Streaman append-only logevents: added, waiting, active, completed, failed…
None of these key names appear in DocMind's code. BullMQ builds them (in its queue-keys.js) from the prefix and the queue name: <prefix>:ingest-pdf:wait, <prefix>:ingest-pdf:<jobId>, and so on. The simulator in 06 shows them changing as a job moves.
Why Redis must not evict. A cache is allowed to throw away old keys when memory is full. A queue isn't: an evicted job hash is a lost upload. Upstash was checked at BG.0: maxmemory_policy: noeviction, so a full Redis refuses new writes instead.

08

The request side: POST /upload

player

The request keeps only what the user waits for: checks, parse, chunk, one row, one job. Each tab is a path that was tested over HTTP in BG.3.

Why parsing stays in the request (D2)

The PDF bytes only exist here: multer keeps them in memory. Parsing takes milliseconds to about a second. The job then carries chunk text (~100–300 KB for 50 pages), never a 10 MB file and never a token.

Why the 400 comes early

A scanned PDF has no text layer. Refusing it while the user is still waiting beats queueing a job that fails later. Before BG.3, such a PDF was saved with 0 chunks and every chat with it answered "No document found".

src/services/ingestion.service.ts · queuePdfIngestion() (shortened)

const { text, chunks, hasText } = await parsePdf(file)
if (!hasText || chunks.length === 0) return { ok: false, status: 400, error: 'This PDF has no text layer…' }

const documentId = randomUUID()
await insertDocument(documentId, userId, file.originalname, file.size, text.length, chunks.length, 'processing')

try {
  await enqueueIngest({ documentId, userId, chunks })   // userId came from req.user.id, never the body
} catch (err) {
  await deleteDocument(documentId, userId)            // no job = nothing would ever finish this row
  return { ok: false, status: 503, error: 'The upload queue is unavailable right now. Try again shortly.' }
}
return { ok: true, document: { documentId, …, status: 'processing' } }   // route answers 202
Same shape as every other service: { ok: false, status, error }, never touching req/res. That rule (from the start of the project) is exactly what let the slow half move into a worker that has no request at all.
09

The 5 s enqueue race

player · F27

If Redis has been unreachable since the server started, BullMQ's add() waits for a first connection that never comes (found by reading bullmq 6's source). Without a limit, the upload would hang forever instead of getting its 503.

src/queue/ingest.queue.ts · enqueueIngest()

export async function enqueueIngest(data: IngestJobData) {
  let timer: NodeJS.Timeout | undefined
  const timeout = new Promise<never>((_, reject) => {
    timer = setTimeout(() => reject(new Error(`Redis didn't accept the job within 5 s`)), ENQUEUE_TIMEOUT_MS)
  })
  try {
    return await Promise.race([getIngestQueue().add('ingest', data, { jobId: data.documentId }), timeout])
  } finally {
    clearTimeout(timer)   // the winner was add(): don't leave the timer running
  }
}
t = 0.0 s
Measured in BG.3 with an unreachable REDIS_URL: the upload got its 503 in 7.4 s (5 s of race plus parsing and the database round trips), no row was left behind, and chat still answered 200 because chat never touches Redis. If Redis does come back and the job lands late, the worker finds the row already deleted and exits quietly.
10

Two connections with opposite settings

connection.ts

When Redis drops, the two sides want opposite things. An upload should fail now. A worker should wait it out.

'queue' connection · used by POST /upload

enableOfflineQueue: false, maxRetriesPerRequest: 1

While disconnected, ioredis refuses a command instead of holding it in memory until Redis returns. The upload answers 503 at once. One connection, shared by the whole process.

'worker' connection · BullMQ's blocking waits

maxRetriesPerRequest: null

A command survives reconnects. The worker spends its life in long "give me the next job" waits; they must keep waiting through a blip. BullMQ requires this and warns without it.

src/queue/connection.ts · connect()

const connection = new Redis(url,
  role === 'queue' ? { maxRetriesPerRequest: 1, enableOfflineQueue: false } : { maxRetriesPerRequest: null })

let lastError = ''
connection.on('error', (err) => {                    // without a listener: "Unhandled error event" + stack, every ~2 s
  const summary = summarizeError(err)
  if (summary !== lastError) console.error(`[redis:${role}] ${summary}`)   // each DIFFERENT error once
  lastError = summary
})
connection.on('ready', () => { if (lastError) console.log(`[redis:${role}] reconnected`); lastError = '' })

Lazy

Nothing connects on import. A script that imports these modules doesn't open a connection and spend Upstash commands.

Tracked

Every connection goes in openConnections, so shutdown can quit() them all.

quit(), not disconnect()

quit() sends QUIT and waits for replies to commands already sent. disconnect() just drops the socket.

The worker, line by line

ingest.worker.ts

No Express, no req/res. The same function runs inside the API process (Render) or on its own (npm run worker).

src/workers/ingest.worker.ts · processIngestJob() (comments shortened)

export async function processIngestJob(job: Job<IngestJobData>): Promise<void> {
  const { documentId, userId, chunks } = job.data
  // attemptsMade counts FAILED attempts so far, so +1 is this one
  pipelineStart('queue', `ingest job ${id8} — attempt ${job.attemptsMade + 1}/${job.opts.attempts}`)

  // 1. Still there? Scoped by owner, like every read since auth.
  const document = await getDocumentForUser(documentId, userId)
  if (!document) {
    await deleteChunksByDocumentId(documentId)   // a previous attempt may have stored some
    return                                       // "completed": retrying can't bring the document back
  }
  await deleteChunksByDocumentId(documentId)     // THE idempotent part: start from a clean slate

  // 2. The slow part: one Gemini call per chunk
  await embedAndStoreChunks(documentId, chunks)   // a throw here = this attempt failed → BullMQ retries

  // 3. Done. false = no row was updated = the user deleted it while we worked
  const stillExists = await setDocumentStatus(documentId, userId, 'ready')
  if (!stillExists) await deleteChunksByDocumentId(documentId)
}
LineWhy it's there
return = success, throw = failureThe whole contract with BullMQ. There's no retry loop in DocMind's code; attempts + backoff do it.
getDocumentForUser(documentId, userId)Auth rule: every read of user data is scoped to its owner, the worker included. userId was put in the job by /upload from req.user.id.
Missing document → return, not throwThrowing would retry 3 times for nothing.
Delete chunks firstA retry or a crash re-run finds whatever the last run left (maybe chunks 1–2 of 5). Delete, then insert all: same result every time. See 12.
setDocumentStatus returns a boolean"Is the row still there?" and "mark it ready" in one UPDATE, so there's no gap between checking and writing. See 13.

src/repositories/documents.repository.ts · setDocumentStatus()

const updated = await db.update(documents).set({ status, error })
  .where(and(eq(documents.id, id), eq(documents.userId, userId)))
  .returning({ id: documents.id })
return updated.length > 0      // 0 rows = the document is gone

Idempotency: why "delete first"

player · rule 3

Attempt 1 stores chunks 1 and 2, then Gemini returns 503 on chunk 3. BullMQ runs the job again. Compare what the chunks table ends up holding.

0 / 0
READYPress Play.

chunks table, rows for this document

Tested both ways in BG.2 and BG.3: a forced failure on chunk 2 (retry → ready, 5 rows, 5 distinct, 7 embedding calls = 1 ok + 1 throw + 5), and a hard kill mid-job with 2 of 5 chunks stored (resumed → 5 rows, 5 distinct). Idempotency held both times.

Also idempotent: jobId = documentId

The same document added twice → one job (BG.2 test D). Idempotency at the queue level, delete-first at the database level.

Why not "skip chunks that exist"?

Chunks have no stable per-chunk key in the table, and a half-written row is possible after a crash. Wiping and redoing is simpler and always correct. The cost: a retry re-embeds every chunk.

The failed handler: ask the state, don't count

widget

The failed event fires after every failed attempt, including the ones BullMQ will retry. Only the last one should mark the document failed. How do you know it's the last?

The plan's sketch: arithmetic

What was built: the job's state

src/workers/ingest.worker.ts · onJobFailed() (shortened)

async function onJobFailed(job, err) {
  failed(`ingest job ${id8} attempt ${job.attemptsMade}/${attempts}`)
  console.error(summarizeError(err))           // the real cause: terminal only, never the client
  try {
    const state = await job.getState()
    if (state !== 'failed') { detail(`will be retried (job state: ${state})`); return }
    await deleteChunksByDocumentId(documentId)                                   // partial chunks
    await setDocumentStatus(documentId, userId, 'failed', INGEST_FAILED_MESSAGE)   // short + safe
  } catch (cleanupErr) {
    // nothing awaits an event handler: an uncaught rejection here would crash Node
    console.error(`[ingest worker] could not mark document … failed: …`)
  }
}
worker.on('failed', (job, err) => void onJobFailed(job, err))

User sees

Could not process this PDF. Delete it and upload it again. The Gemini 503 or the SQL error with its parameters stays in the terminal (summarizeError()).

Off-by-one trap (T5)

Inside the processor, attemptsMade doesn't include the current run yet (hence + 1). In the completed event it already does, so + 1 there double-counted in the BG.1 script.

Stalled jobs: why a crash costs ~10 minutes

player · measured 624 s

A running job holds a lock that the worker renews in the background. If the process dies (crash, out of memory, a kill), the renewals stop, the lock expires, and some worker's stalled check puts the job back in the queue. With stalledInterval at 5 min, that took 624 s in the BG.3 crash test.

t = 0 s
READYPress Play: a worker is killed with the job at chunk 2 of 5.

Kill and resume times are measured (15:54:11 → 16:04:35, +624 s). The positions of the two checks in between are the model that explains the number, not measured times.

Pass 1 marks

A stalled check copies every active job id into a stalled set. It doesn't move anything yet.

Pass 2 moves

The next check looks at that set. A job whose lock is gone is moved back to wait. If it had already stalled once (maxStalledCount 1), bullmq 6 tags it with a deferred failure, and the next worker to take it fails it at once.

The throttle

Each check sets a stalled-check key for one interval. The dead process's last key can block the restarted worker's first check. So: up to ~2 intervals, ~10 min.

A stalled re-run doesn't use an attempt (the log said "attempt 1/3" after the crash). And normal deploys never hit this: Render sends SIGTERM, and worker.close() waits for the job (16). Kept at 5 min on purpose: a check costs ~1 command, and the slow recovery only happens after a real crash. Logged as open item #15 in ISSUES.md.

Graceful shutdown

player · shutdown.ts

Render sends SIGTERM on every deploy and restart and kills the process about 30 s later. Ctrl+C sends SIGINT. Without a handler, Node exits on the spot, possibly mid-job.

0 / 0

src/queue/shutdown.ts · closeQueueOnShutdown()

async function shutdown(signal: string) {
  if (closing) return                  // a second Ctrl+C changes nothing
  closing = true
  setTimeout(() => { console.error('Shutdown took longer than 20 s — exiting anyway'); process.exit(1) },
             SHUTDOWN_TIMEOUT_MS).unref()   // unref: this timer alone mustn't keep the process alive
  await worker?.close()                // stop taking jobs, WAIT for the one in progress
  await closeIngestQueue()
  await closeRedisConnections()        // quit() each connection
  process.exit(0)
}
process.once('SIGTERM', () => void shutdown('SIGTERM'))
process.once('SIGINT',  () => void shutdown('SIGINT'))
Why 20 s: Render waits about 30 s after SIGTERM before it kills the process, so the app gives up first and exits on its own terms. A job cut off at 20 s isn't lost: it stalls, the restarted worker picks it up (15), and delete-first makes the re-run safe. Order matters too: the worker closes before the connections it runs on.

409, not 404

The document exists and it's yours; it just isn't usable yet. 409 Conflict says exactly that.

Ownership before status

Telling a stranger "still processing" would confirm the id exists. Someone else's document stays a plain 404 (auth rule).

Before any Gemini call

Checked before the question is embedded, so a request that can't succeed doesn't spend an API call. searchSimilar and sampleChunks also filter status = 'ready' in their join.

The column itself: ALTER TABLE documents ADD COLUMN status TEXT NOT NULL DEFAULT 'ready' plus a nullable error. The default made it safe on a live table: every old row became ready at once, and the then-deployed code, which never wrote the column, kept inserting ready documents.

Check yourself

answer out loud, then open
1. Why does /upload return 202 and not 201?

201 means "created and ready". The document exists, but it isn't usable yet: it's processing until the worker finishes. 202 Accepted means "got it, still working on it", and the client finds out the rest by polling GET /documents.

2. Why does parsing stay in the request while embedding moves to the worker?

Parsing needs the PDF bytes, which only exist in the request (multer memory storage), and it's fast. Embedding is one Gemini call per chunk: slow, and the part that fails. Keeping parsing in the request also means a scanned PDF gets an immediate 400, and the job carries only text, never a 10 MB file.

3. What makes the job idempotent, and which two situations needed it?

It deletes the document's chunks before inserting all of them, so any number of runs leaves the same rows. Needed for BullMQ's retries after a throw (chunks 1–2 already stored) and for a stalled re-run after a crash. Plus jobId = documentId so the same document can't be queued twice.

4. Why two Redis connections with opposite settings?

The upload side wants to fail fast (enableOfflineQueue: false): a 503 now beats a hanging request. The worker wants to survive reconnects (maxRetriesPerRequest: null, required by BullMQ) because it lives in long blocking waits.

5. Why getState() === 'failed' instead of attemptsMade >= attempts?

A job that stalls more than maxStalledCount (1) times is failed by BullMQ with "job stalled more than allowable limit", an unrecoverable error, before its attempts run out (stalls don't count as attempts). The arithmetic would say "will retry" and the document would stay processing forever. The state is the truth.

6. A user deletes a document while chunk 4 of 5 is embedding. Why are no chunks orphaned, whichever side finishes first?

The route deletes the row first. If the worker's final UPDATE comes after that, it updates 0 rows, sees false, and deletes its own chunks. If the worker finishes first, the route's chunk delete runs afterwards and removes them all. The old order (chunks, then row) let a worker store its last chunk in between and leave orphans.

7. Why does an idle worker cost Redis commands, and which settings fixed it?

It keeps doing blocking "next job?" waits (one per drainDelay) and stalled checks (one per stalledInterval). Defaults 5 s and 30 s cost 118 commands per 5 idle minutes (204% of the free plan 24/7). 30 s and 5 min cost 19 (33%).

8. Why can crash recovery take ~10 minutes with a 5-minute stalledInterval?

One check only marks active jobs; the next one moves those whose lock expired. And each check sets a throttle key for one interval, so the dead process's last key can make the restarted worker skip its first check. Measured: 624 s.

9. What happens on a Render deploy while a job is running?

SIGTERM → worker.close() stops taking jobs and waits for the current one → queue and connections close → exit 0. If it takes over 20 s, the app exits anyway; the job stalls and is re-run after the restart, safely, because of delete-first.

10. Redis is down. What does an upload get? What about chat?

Upload: the enqueue fails (at once, or after the 5 s race if Redis was never reachable), the new row is deleted, and the user gets 503. Chat keeps working: it never touches Redis.

11. Why must the Redis behind a queue be noeviction?

Under memory pressure an evicting Redis deletes keys, and a deleted job hash is a lost upload with no error anywhere. noeviction refuses new writes instead, which surfaces as a failed add() → 503.

12. How did production end up sharing a queue with the laptop, and how was it caught?

Render's BULLMQ_PREFIX was docmind-dev, copied from .env. The live test passed, because it only checked "job hash gone". Counting keys showed 0 under docmind:. Fix: set docmind on Render, re-test asserting the job's events in docmind:ingest-pdf:events. Lesson: an assertion has to be able to fail.

13. Why is the worker in the API process, and what would change to move it out?

Render's free tier has no background-worker service. Moving it out means starting a second service with npm run worker (src/worker.ts) and setting RUN_WORKER=false on the API. No code change.

14. Why is 409 the right status for chatting with a processing document, and why is ownership checked first?

The document exists and it's yours; it's in the wrong state for the request, which is what 409 Conflict means. Ownership comes first because answering "still processing" to someone else would confirm the id exists. Theirs stays a 404.
